# One connection per Shopify store, and per Amazon seller

Status: done
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

None: a feature of its own, found while building `connection-onboarding/03` on
2026-10-29. Not blocked. Redrafted 2026-10-30, when an Amazon connection became one per
seller rather than one per seller and marketplace.

## Problem

Nothing stops two active connections reading the same orders. An operator created a
second Amazon connection to the same seller and marketplace, and nothing objected.

Imported Shipments are unique per connection, not per order: the key is
`(data_source_id, source_record_id)` (`shipments_data_source_record_unique`), and
`ShipmentBatchWriter` upserts on it. Two connections to the same account each import their
own copy of every order. The packing queue shows two Shipments for one order, and either
can be packed and given a Label. Once one copy ships and its tracking is confirmed, the
other connection's next import should close its copy, because the source now reports the
order closed. That limits the damage but does not prevent it: both copies are open until
then.

The same is true of two Shopify connections to one shop domain.

`import_account_key` does not help. It names the account a connection last read from, so
the connection can reset its own import cursor when its account changes. It is never
compared with another connection's.

An Amazon connection also holds a single `settings.marketplace_id`, so a seller who sells
in the US and Canada from one unified North America account needs two connections, and
each goes through OAuth separately. That is the wrong shape for how Amazon authorizes:

- A grant is per seller and region, not per marketplace. A live probe on 2026-10-30 found
  that each of two grants to the same seller reads all of that seller's marketplaces;
  the marketplace is only a PolyBag setting.
- A second grant did not revoke the first, immediately or two hours later. But Amazon's
  renewal guidance for public apps says to store the new refresh token and delete the old
  one, so several live grants per seller rely on behavior Amazon allows but does not
  promise.
- Each grant expires on its own 365-day schedule, so a seller with three marketplaces
  would re-authorize three times, on three dates.

Captures, hashes only: `.scratch/connection-identity-token-probe/`.

## Desired behavior

### One Amazon connection reads several marketplaces

`settings.marketplace_id` is replaced by:

- `settings.marketplace_ids`: the marketplaces this connection imports from. A subset of
  the supported ones (`AmazonMarketplace`) that discovery reports the seller participating
  in. Required, at least one.
- `settings.primary_marketplace_id`: one of `marketplace_ids`. Used where there is no order
  to take a marketplace from: the product catalog sync, and Amazon Shipping sold to other
  channels' orders. Defaults to the US when it is selected, otherwise the first selected.

Each order carries its own marketplace (`salesChannel.marketplaceId`, already stored in
the Shipment's `amazon_sales_channel` metadata). Every call that is about one order uses
that order's marketplace, not the connection's:

| Path | Today | After |
|---|---|---|
| Order search (`searchChangedOrders`) | one `marketplaceIds` value | every selected marketplace in one search (the parameter takes up to 50) |
| Shipment confirmation (`confirmShipment` body) | connection's marketplace | the order's, falling back to the primary when the metadata is missing |
| Buy Shipping observed services (`AmazonBuyShippingAdapter::ratesFrom`) | connection's marketplace | the order's |
| Amazon Shipping for other channels (`AmazonShippingAdapter::ratesFrom`) | connection's marketplace | the primary |
| Catalog look-up during import (`AmazonCatalogIdentifiers`) | connection's marketplace | the order's, so an ASIN listed only in Canada is found |
| Product catalog sync (`AmazonListingCatalog`) | connection's marketplace | the primary only |

`AmazonBuyShippingService::marketplaceIdFor(DataSource)` becomes a question about a
Package's order, with the primary as the fallback, rather than about the connection.

The import cursor is per seller. `DataSource::importAccountKeyFor()` hashes the
seller (or the manual refresh token, as now) without the marketplaces, so ticking another
marketplace does not restart the import from the full lookback. The next sweep picks up
the new marketplace's open orders, because the sweep reads every open order in the
lookback whatever the cursor says.

Removing a marketplace stops importing from it. Its open Shipments stay open, can still be
packed and shipped, and still confirm to their own marketplace. But Amazon closes a
Shipment only from the orders its own changes search returns closed
(`order-reconciliation/07`), so an order cancelled in a marketplace no longer searched
would stay open here. Saving the form with a marketplace removed while that
marketplace has open Shipments warns with their count, rather than refusing.

### Choosing marketplaces

- **After OAuth**, discovery selects the seller's only supported marketplace, as now.
  With several, it selects none and the callback asks for a choice, as now. Nothing is
  imported from a marketplace no one chose: an order from another country is an
  international shipment from a US Location, which needs customs data.
- **On the form**, `settings.marketplace_ids` is a multi-select of the discovered
  marketplaces, labeled as the current single select is (country code, "Listings
  suspended"). `settings.primary_marketplace_id` is a select limited to the chosen ones,
  shown only when more than one is chosen.
- **A connection with its own refresh token** (no broker) chooses from all supported
  marketplaces, as the single select does now.
- **On reconnect or refresh**, a selected marketplace that discovery no longer reports
  stays selected and is flagged, as `selectedMarketplaceUnavailable` does now for the
  single one, per marketplace.
- The Setup Wizard and `demo:provision` set `marketplace_ids` and `primary_marketplace_id`
  instead of `marketplace_id`.

Existing rows are converted in a migration: `marketplace_id` becomes a one-element
`marketplace_ids` and the `primary_marketplace_id`.

### No two active connections share an account

A connection's **account identity** is what it reads orders from:

- **Shopify:** `settings.shop_domain`, compared case-insensitively.
- **Amazon:** the seller ID OAuth records (`amazon_selling_partner_id`). Marketplaces play
  no part. A connection with its own refresh token records no seller ID, so it has no
  identity to compare and is not checked. In Production and Demo with the broker, that
  field is hidden (`connection-onboarding/02`).

No two **active** connections share an identity. An inactive one may, so an old
connection can be kept for history while a new one replaces it.

Where it is enforced:

- **Shopify, on create and save.** The shop domain is known on the form, so this is
  validation on `settings.shop_domain`: "Another active connection, *{name}*, already
  reads this store." Also when an inactive connection is made active.
- **Amazon, after OAuth.** The seller ID is only known once the callback returns. When
  another active connection already holds this seller, the callback stores the grant but
  makes the new connection inactive, skips discovery, and says so: "Another active
  connection, *{name}*, already reads this seller account. Add marketplaces to it
  instead." The operator can delete the new connection or deactivate the old one.
- **Amazon, on save.** Activating a connection fails validation on `active` when another
  active connection holds this seller.
- **Amazon, on reconnect.** A connection reconnected to a different seller is checked the
  same way as after OAuth.

The rule lives in one place, something like `DataSource::conflictingConnection(): ?DataSource`,
and the form and the callback both ask it.

## Out of scope

- **Currency.** Order values are imported as plain numbers and treated as USD. A Canadian,
  Mexican or Brazilian order is priced in its own currency, so its customs values are
  wrong. That is already true of a single connection set to one of those marketplaces, and
  is `order-currency`.
- **Buy Shipping for orders outside the US marketplace.** Every Shipping API request sends
  `x-amzn-shipping-business-id: AmazonShipping_US`. Whether Buy Shipping quotes a Canadian
  or Mexican marketplace order that way is unverified. Like currency, it is not new with
  this change.
- **Multi-Location Inventory.** Amazon's per-location inventory is US-only and seller-wide,
  not per marketplace. The Orders API v2026-01-01 schema has no field naming the supply
  source an order should ship from (v0 had `FulfillmentInstruction.FulfillmentSupplySourceId`),
  so it needs a probe against an MLI seller before it can be designed.
- **Regions other than North America.** The connector talks to the NA endpoint, and
  `AmazonMarketplace` lists only the US, Canada, Mexico and Brazil. A seller in Europe
  would be a second connection in another region, and its identity would need the region
  too.

## Notes

- One seller is one client: a connection carries one `client_id`. A 3PL that treats two
  brands sold from one seller account as separate clients cannot split them by connection
  after this, and could not cleanly before (both connections imported every order).
- Existing duplicate connections are not repaired. There are no live tenants.
- A unique index cannot express the identity rule: it spans a JSON setting and a secret, and
  applies only to active rows. Enforce it in the application.
- The Shopify half does not depend on the Amazon half and can land first.

### 2026-10-31 — shipped

> *This was generated by AI.*

- **Built.** `marketplace_ids` and `primary_marketplace_id` replace `marketplace_id`
  (migration `2026_10_30_230341_…`, which also rewrites a stored `import_account_key` that
  named the connection's account and marketplace, so no import restarts on deploy; a key
  naming anything else still restarts). The rule is `DataSource::conflictingConnection()`,
  asked by the form (`settings.shop_domain` for Shopify, `active` for Amazon), the OAuth
  callback and the Setup Wizard. Each Amazon order's marketplace is read through
  `Shipment::amazonMarketplaceId()`; the paths in the table use it or the primary as
  specified. Tests: `ConnectionIdentityTest` plus the Amazon import, export, Buy Shipping,
  Amazon Shipping, catalog sync, discovery and wizard suites.
- **Where the spec was silent.**
  - The callback deactivates and skips discovery in `OAuthService`; the controller asks the
    same rule for the notice, which says "was made inactive" or "stays inactive".
  - The catalog look-up during import asks each ASIN once: in the primary when any of its
    orders is there, else the first order's marketplace. Asking every marketplace would pay
    for duplicate calls, and an empty answer could overwrite a found barcode.
  - Adding a marketplace clears `import_swept_at` and a stored sweep read, so the next run
    sweeps every selected marketplace instead of waiting up to a day. A stored search for
    changes is kept: the added marketplace has nothing imported to close, and its open
    orders are the sweep's.
  - The removal warning counts open Shipments whose recorded marketplace was removed; one
    with none recorded is not counted.
  - An OAuth connection with a discovery list chooses from the discovered marketplaces;
    without one, or with its own refresh token, from all supported.
  - The Setup Wizard keeps a conflicting connection's previous active state and says why.
  - `config('demo.amazon_shipping.marketplace_id')` (`DEMO_AMAZON_MARKETPLACE_ID`) keeps its
    name; `demo:provision` converts it.
- **Known limitation, accepted.** Two OAuth callbacks for the same seller at the same moment
  are not atomic: each can find no other active holder and both stay active. A unique index
  cannot express the rule (see Notes), and the window is one human's two browser tabs.
