# Deleting a connection that has Shipments

Status: needs-triage
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

None. Related to `01`: both are about a connection standing for one store or seller
account. Not blocked.

## Problem

An admin can delete a connection that has imported Shipments, from its edit page or the
table's bulk action (`DataSourcePolicy::delete()` checks only the role). `DataSource` is
not soft-deleted, so the row is gone and the foreign keys decide the rest:

- **Shipments** keep their rows with `data_source_id` set to null
  (`nullOnDelete`). Nothing can tell afterwards which store or seller they came from.
- **Packages, Labels and Offers** bought through the connection's postage keep their rows
  with `postage_data_source_id` null. `PostageSourceDispatcher::resolve()` then finds no
  source type, so voiding or tracking a Shopify or Amazon Label goes to the
  unrecognized handler.
- **Export history** (`package_exports`), **location mappings**
  (`data_source_locations`), **Amazon catalog look-ups** and **Amazon Shipping scopes**
  (`carrier_account_scopes`) are deleted with it (`cascadeOnDelete`).

The orphaned Shipments still open get no closure from the source, no tracking export back
to it, and no origin-bound Shopify or Amazon postage.

Creating the connection again does not help. Nothing re-attaches Shipments. The new
connection has a new ID, so its first import writes a second Shipment for every order
still in its feed, beside the orphan. That is `01`'s duplicate, with no connection left to
close the orphan.

## Options

1. **Refuse to delete a connection that anything references.** Shipments, Packages,
   Labels or Offers. The delete action says to make the connection inactive instead,
   which already stops imports and postage. An unused connection, such as one created by
   mistake, can still be deleted. Reconnecting to a store goes through Reconnect on the
   same record, which already exists. **Recommended:** it is the smallest change, and it
   keeps the record that voids, tracking and exports need.
2. **Soft-delete connections**, and treat a deleted one as inactive everywhere. This keeps
   the foreign keys, but every query that lists connections then has to exclude deleted
   ones, and a deleted connection still cannot be seen or reconnected without a restore
   screen. That is most of option 1's behavior, done the long way round.
3. **Re-attach orphans when a connection is recreated.** Not possible from the data as it
   stands: an orphan's only link to its account was the deleted row. It would need the
   account identity from `01` copied onto every Shipment.

## Open questions

- Is option 1 right, or should an admin be able to delete a connection and its history
  deliberately, for example after a client leaves? If so, that is a separate, explicit
  action that also deals with the Shipments, not today's delete.
- Bulk delete: refuse the whole action if any selected connection is referenced, or
  delete only the unreferenced ones and report the rest?

## Acceptance (for option 1)

- [ ] Deleting a connection with Shipments, Packages, Labels or Offers is refused with a
      message to make it inactive instead; nothing is deleted
- [ ] A connection nothing references can still be deleted
- [ ] Bulk delete follows whichever answer the open question gets
