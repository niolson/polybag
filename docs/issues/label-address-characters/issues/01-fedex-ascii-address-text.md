# FedEx: send label text as ASCII so diacritics do not print as `?`

Status: ready-for-agent
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Problem

A production FedEx International Connect Plus label to a consumer in Poland, bought
2026-10-01 while verifying `eu-product-identifiers/05`, printed the street
`Zwycięstwa 27B` as `ZWYCI?STWA 27B` on the label and `Zwyci?stwa 27B` on the air waybill
copy. The `?` is in the ZPL FedEx returned (a literal `0x3F` under `^CI13`), not a
printer fault, and the address encoded in the 2D barcode drops the letter entirely
(`Zwycistwa 27B`). The mixed-case waybill copy shows the same `?`, so it is not a side
effect of FedEx upper-casing the label. The label was voided.

`FedexAdapter` sends every text field exactly as it was imported. Nothing in the
adapter transliterates; the only `Str::ascii()` calls in the app are lookup keys in
`FedexSubdivision` and `AddressReferenceService`, which never reach a label.

A `?` in a street name is a routing and delivery risk on exactly the lanes — Poland,
Czechia, Germany, the Nordics, Iberia — that the EU product identifier work is about.

## Desired behaviour

Every free-text field `FedexAdapter` puts on a `CreateShipment` body is sent as ASCII,
transliterated with `Str::ascii()` (`ę` → `e`, `ł` → `l`, `ß` → `ss`, `ø` → `o`):

- recipient and shipper contact: person name, company name
- address: street lines, city
- commodity `description` and `name`, which print as `DESC1`–`DESC4` on the waybill
  copy

Codes (country, state, postal code) and anything already ASCII pass through unchanged.

The rate request needs no change for the address itself — FedEx rates on postal code and
country — but should use the same helper for any city it sends, so the two bodies
cannot drift.

If transliteration would leave a required field blank (a name written wholly in a
script `Str::ascii()` cannot map, such as CJK), send the original text rather than an
empty field; FedEx refusing it with a named error is better than a nameless label. Log
that case on `fedex-validation`.

## Acceptance criteria

- [ ] `FedexAdapterTest`: a recipient with `Zwycięstwa 27B`, city `Łódź` and name
      `Zoë Ørsted` is sent as `Zwyciestwa 27B`, `Lodz`, `Zoe Orsted`; the shipper is
      transliterated the same way; a commodity described `Café crème` is sent as
      `Cafe creme`
- [ ] A field that transliterates to blank is sent as the original, and logged
- [ ] `fedexShip.json` still validates every body
- [ ] One production label to a destination with a diacritic, voided straight away,
      prints with no `?` (record it here; the raw capture goes in `.scratch/`)

## Out of scope

- Storing the transliterated address anywhere: the Shipment keeps what was imported,
  and the pack slip keeps printing it
- Requesting the commercial invoice (`shopify-shipping-carrier/23`)
