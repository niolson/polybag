# Sync a connection's product catalog

Status: reference

Repo: `polybag`

Background for the issues in this directory. Not a work item.

> *This was generated by AI during triage.*

## Problem

Products reach PolyBag only through orders. `ImportReferenceResolver::productIdFor()`
creates or updates a Product for each line an import brings in, so a SKU that has never
been on an imported order has no Product.

That breaks **Manual Ship with scan-to-add**. Pack's scan-to-add looks the scan up as a
Product barcode or SKU in the Shipment's client (`Pack::addItemByScan()`), so an item no
order has brought in cannot be scanned in. Typing the item in instead leaves it without
the weight and identifiers an international label needs.

## Goal

An Admin can pull a connected Shopify or Amazon account's whole product catalog into
PolyBag's Products, **with whatever the source holds**. The first scan of any listed item
then finds a Product, and its gaps can be seen and filled before the first international
label.

What each source can supply:

| Product field | Shopify | Amazon |
|---|---|---|
| `sku`, `name` | Yes | Yes |
| `weight` | Variant weight | Seller's listing (93% of listings in `03`) |
| `barcode`, `gtin` | Variant barcodes | Catalog identifiers |
| `manufacturer_part_number` | Typed `NS_PID`, else the connection's metafield | Catalog summary |
| `hs_tariff_number` | `inventoryItem` | **No.** In neither listings nor catalog (`03`) |
| `country_of_origin` | `inventoryItem` | **No.** None in listings. The catalog's origin fields cover under 7% of ASINs and are mostly free text (`03`) |

So a synced Shopify Product can be customs-ready. A synced Amazon Product will normally
still need an HS code and an origin. The existing *Missing Customs Data* filter cannot
find them: it lists only Products on an unshipped international Package, and a synced
Product is on none. `02` adds an **Incomplete Customs Data** filter over every Product (no
weight, origin or HS code) for this. Filling HS codes automatically is a separate concern ([`05`](issues/05-suggest-hs-codes.md)).

Keeping PolyBag in step with the store *automatically* is not a goal (see *Out of scope*):
each sync is started by hand.

## What already exists

- **The write path.** `productIdFor()` upserts a Product by `(client_id, sku)`. It keeps
  `_fill_only` fields that already have a value (`product-identifier-import/01`), treats
  blanks as "no value" (`release-polish/39`), and leaves a hand-set `is_media` alone.
- **Shopify field mapping.** `ShopifySource::mapFulfillmentOrderLineItem()` maps a
  variant's barcodes, the part-number metafield chosen on the connection
  (`product-identifier-import/03`) and `inventoryItem { harmonizedSystemCode
  countryCodeOfOrigin }` (`product-identifier-import/04`). The import already requires
  `read_products` (`product-identifier-import/02`).
- **Amazon catalog lookup.** `AmazonCatalogIdentifiers` batches ASINs into
  `SearchCatalogItems` for the barcode and part number.
  `AmazonCatalogIdentifiers::asinsNeedingLookup()` decides which: an ASIN with any SKU
  whose Product is missing a barcode **or** a part number and has not been answered for
  within `RECHECK_DAYS` (`identifiers_checked_at`). Pacing and retry live in
  `AmazonRequestPacer`. *(Moved out of `AmazonSource` in `04`.)*
- **Amazon listings access.** The 2026-10-05 probe (`product-identifier-import/06`) called
  `searchListingsItems` with `includedData=attributes` on an OAuth connection: 33 calls,
  all 200. The app has the Product Listing role, and every OAuth connection stores the
  seller ID (`settings.amazon_selling_partner_id`). `item_weight` was among the attributes
  returned. Only counts were kept from that probe, not the responses.
- **Customs-gap filters.** `ProductResource` has *Missing Weight* over every Product, and
  *Missing Customs Data* (`Product::scopeMissingCustomsData()`), which is a packing
  worklist limited to Products on unshipped international Packages.

## Constraints the design has to respect

- **Products are not unique by SKU.** `(client_id, sku)` has a plain index, and
  `productIdFor()` reads with `firstOrNew()` and then saves, so two writers can create the
  same SKU twice. Scan-to-add then picks whichever comes first. In production, imports run
  through a single `imports` worker, which hides this, but nothing enforces it. A catalog
  sync adds a long-running writer, so [`01`](issues/01-make-products-unique-by-sku.md)
  makes `(client_id, sku)` unique first.
- **`SHIPMENT_IMPORT_AUTO_UPDATE_PRODUCTS=false`** makes `productIdFor()` read-only: it
  returns existing IDs and creates nothing. That setting means Products are kept
  somewhere else. When it is off, the sync action is hidden and the Connection says why.
  A sync never runs and reports success having written nothing.
- **Amazon caps a listings search at 1,000 results**, pages included. Following
  `nextToken` stops at the thousandth listing (see *Amazon*).

## Shopify

Page through the store's variants of active products (`productVariants`, sized under the
1,000-point query cost the fulfillment-order query is already measured against). Each
variant becomes the item array `productIdFor()` takes:

| Product field | From |
|---|---|
| `sku` | `ShopifyGoodsFingerprint::skuFor()`: the variant SKU, else `SHOPIFY-V-{variant id}` |
| `name` | Product title, plus the variant title when it is not `Default Title` |
| `weight` | `inventoryItem.measurement.weight`, through `ShopifySource::poundsFrom()` |
| `barcode`, `gtin`, `manufacturer_part_number` | The existing barcode and metafield rules |
| `hs_tariff_number`, `country_of_origin` | `inventoryItem` |

- **Variants with no SKU** use the order import's `skuFor()` rule, so a later order lands
  on the same Product. Scan-to-add still finds them by barcode.
- **Shared fields, separate inputs.** The fields read from the variant itself (barcodes,
  GTIN, part number, HS code, origin) move into one method both paths call. Order imports
  do not change: they keep naming a Product by the line's `productTitle` and weighing it
  by the fulfillment-order line's `weight`. The sync names it product plus variant title
  and weighs it by `inventoryItem.measurement`.

## Amazon

### Listing every SKU

`searchListingsItems` (`GET /listings/2021-08-01/items/{sellerId}`) returns at most 1,000
listings per search, however it is paged
([Amazon](https://developer-docs.amazon/sp-api/docs/search-for-listings-items-by-id)).
It also accepts `createdAfter`, `createdBefore` and `sortBy=createdDate`. So:

1. Search a creation-date window with `pageSize=20`.
2. If the first page's `numberOfResults` is 1,000 or more, discard the window and search
   its two halves instead. `numberOfResults` is the window's true total, not capped, so
   this needs no paging to the cap (`03`: it equaled the listings fetched in 157 of 157
   windows).
3. Otherwise follow `nextToken` to the end. Start from one window covering the account's
   whole history.

This fails in one case: a bulk upload can create more than 1,000 listings within a
single second, and no window can split them. If a one-second window still reaches the
cap, the run carries on but is recorded as **incomplete**, naming the window. It is never
reported as complete. In `03` the busiest second held 310.

The merchant listings report (`GET_MERCHANT_LISTINGS_ALL_DATA`) is open to the app's
roles, but `03` found it is **not a complete SKU list**: it left out 525 of 29,728 listings,
most of them recent. Its only extra rows were listings with no ASIN. It is not used.

A listing with no summary (no ASIN, typically one Amazon rejected) has no `createdDate`
and is never returned by a date search. It has nothing to scan by, so that is accepted.

Rate: `03` measured a 29,728-SKU account at 1,762 listing calls in 16 minutes. The
calls are latency-bound well under the 5-per-second limit. The catalog step for the same
account took 1,277 calls in 11.5 minutes at 2 per second.

### What to read

From each listing: `sku`, `name` from the summary's `itemName`, the ASIN, and the weight.
Attribute values are lists. Take the entry for the connection's marketplace, else the
first. Then the existing catalog lookup runs over the synced SKUs, filling blanks only, under
`AmazonCatalogIdentifiers::asinsNeedingLookup()`'s rule: missing barcode **or** part number, and
not checked within the recheck window.

A manual (non-OAuth) connection has no seller ID, so the action is hidden, with a note
to connect through OAuth.

### Weight

`Product.weight` is a per-unit weight in pounds, used for package and customs weights. In
order:

1. The listing's `item_package_weight`. The item ready to ship is the closer match to what
   goes in the box. Rare in practice: 1 listing in 29,728 in `03`.
2. The listing's `item_weight` (93% filled in `03`, all in pounds, at most 16 lb).
   `website_shipping_weight` is not a further fallback: in `03` it repeated `item_weight`
   and was never present without it.
3. Nothing from the catalog. Its merged ASIN record carries obviously wrong weights often
   enough that a blank is better: a blank shows up under *Missing weight* and gets fixed,
   but a wrong weight goes onto a customs declaration. `03` found weights in milligrams
   and up to 2,410 lb in it, and listing and catalog differing by more than ×2 on 16–27%
   of products.

Convert `pounds`, `ounces`, `grams` and `kilograms`. Ignore other units, values that are
not positive, and values above **150 lb**, the largest parcel the direct carriers accept.
No listing weight in `03` came near it.

## Shared

- **Queued jobs, in short slices.** `SyncProductCatalogJob`, on the `imports` queue,
  writes about a minute of pages and then queues the next slice at the back of the queue,
  so order imports run between slices on the one `imports` worker. The run records its
  cursor, page and counts as each page commits, and the next slice resumes from there.
  The run, not a lock, keeps two syncs of a connection apart: a sync starts only when no
  run is running or the running one has stalled, and a sync started after one that failed
  or stalled partway carries on from its cursor and counts. `failed()` records the run, so a crash
  never leaves it showing *running*. It needs the connection `active`, not
  `import_enabled`. *(Revised in `02`: one 30-minute job held up every order import.)*
- **Client.** Products land in the connection's assigned client, else the default client,
  as `productIdFor()` already resolves.
- **The action.** *Sync Product Catalog* on the Connection. Connections are Admin-only, so
  the action is too. It is shown for active Shopify and Amazon connections, and offered
  once after a new connection finishes connecting, but never started automatically.
- **Overwrite rule.** An order import writes every non-blank value over the Product
  except the `_fill_only` ones. A catalog sync does the same: the store's non-blank values
  overwrite PolyBag's, and a blank at the store (or a Shopify weight of 0, which means no
  weight entered) leaves PolyBag's value. PolyBag is not the source of truth for product
  data; a correction belongs in Shopify or the ERP. The **name** is the exception, written
  only where a Product has none: an order import names a Product by its line's title, and
  overwriting it with "Product - Variant" would flip the name on every import and sync.
  `identifiers_checked_at` is bookkeeping, not data, and always updates, or an expired
  look-up could never be renewed and the catalog would be asked again on every run.
  *(Revised 2026-10-28: the sync first filled blanks only.)* Amazon's **catalog look-up**
  is not the seller's data but Amazon's shared record, and about one in five of its part
  numbers is really the UPC (`03`), so its barcode and part number only fill blanks, as
  in the order import. The rule above covers what the seller's listing provides: weight,
  and the name. *(Decided in `04`.)*
- **Search indexing.** The sync saves inside `Product::withoutSyncingToSearch()` and, after
  each page commits, queues index updates for that page's Products on the `low` queue. A
  run that fails partway leaves everything saved so far searchable. Search may lag by
  minutes.
- **Run status.** The connection records the last run: started, finished, Products
  created, updated and unchanged, and its outcome. That is *complete*, *incomplete* (an
  Amazon window that could not be split) or *failed*, with the page or window it stopped
  at and the error. Counts are kept up to date as pages commit, so a failed run reports
  what it saved. The Connection shows it.
- **Read-only at the source.** Nothing is written back to the store, so it is safe in
  demo mode (`live-store-demo/01`).

## Discontinued products

Products removed from the store **stay**. The sync never deletes or deactivates a Product.

A Product with items on it cannot be lost: `shipment_items.product_id` and
`package_items.product_id` are foreign keys with no cascade, so a Package's contents stay
visible as long as the Package exists. Items point at the live Product row, so a later
change to a Product's name or weight shows on old Packages too.

Two existing behaviors make `active` weaker than it looks. They are noted here for later,
not fixed here:

- `productIdFor()` sets `active => true` on every import, so the next order undoes a
  manual deactivation.
- Scan-to-add ignores `active`.

## Out of scope

- Scheduled or webhook-driven syncs: keeping Products in step with the store
  automatically. A sync started by hand overwrites from the store (see *Overwrite rule*).
- Deactivating Products that leave the store, and the `active` behaviors above.
- Database connections, which already map any column through their item query.
- Reading the catalog's weights.
- HS code classification ([`05`](issues/05-suggest-hs-codes.md)).
- Inventory, prices and images.
