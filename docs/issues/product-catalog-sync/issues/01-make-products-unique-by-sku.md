# Make Products unique by client and SKU

Status: ready-for-agent
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), *Constraints*. Blocks `02` and `04`.

## Problem

`products` has a plain index on `(client_id, sku)`, and
`ImportReferenceResolver::productIdFor()` reads with `firstOrNew()` and then saves. Two
writers handling the same SKU at the same moment both find nothing and both insert, which
creates two Products for one SKU. Scan-to-add (`Pack::addItemByScan()`) then picks
whichever row comes first, and the other Product's weight or identifiers are silently
ignored.

Today the risk is hidden because the production stack runs one `imports` worker, but
nothing enforces that: a second worker, `composer run dev` alongside a scheduled import,
or a catalog sync running beside an order import from another connection of the same
client all overlap.

## Desired behavior

- **A unique index** on `products (client_id, sku)`, in a new migration that replaces the
  plain one. `sku` stays nullable. MySQL and SQLite both allow many NULLs under a unique
  index.
- **Existing duplicates are merged first,** in the same migration: for each
  `(client_id, sku)` with more than one row **and a non-NULL, non-empty SKU**, keep the
  lowest `id`, fill its blank columns
  from the others (lowest `id` first), repoint `shipment_items.product_id` and
  `package_items.product_id` (and any other foreign key to `products`) at it, then delete
  the rest. There are no live tenants, but development and demo databases may have
  duplicates. **NULL SKUs are never grouped:** SQL `GROUP BY` puts them together, but they
  are distinct Products that the unique index deliberately allows, and merging them would
  repoint one Product's history onto another. An empty-string SKU is not NULL, so the
  unique index treats two of them as a clash. Set empty SKUs to NULL before adding the
  index, and have the model do the same on save.
- **The resolver survives the race.** Creating a Product goes through Laravel's
  `createOrFirst()` (or catches `UniqueConstraintViolationException` and re-reads), then
  applies the same update and fill-only rules to the row that won. The returned
  `created`/`updated` flags stay accurate: the writer that lost the race reports
  `created: false`.
- Anywhere else that creates a Product by SKU (the Products form, the factory's default
  state) respects the index. The form shows a validation error, not a database exception.

## Acceptance criteria

- [ ] Inserting a second Product with the same `client_id` and `sku` fails at the database
- [ ] Two Products with the same SKU in different clients are allowed, and so are many with
      a NULL SKU
- [ ] The migration merges seeded duplicates: one survives with the merged values, and the
      Shipment and Package items that pointed at the others now point at it
- [ ] Several Products in one client with NULL SKUs, and with empty SKUs, all survive the
      migration as separate rows, each keeping its own items
- [ ] `productIdFor()` given a SKU whose row appears between its read and its insert
      (simulated) returns the existing row's id with `created: false` and applies the update
- [ ] Creating a duplicate SKU on the Products page shows a validation error
- [ ] Runs in the `mysql` test group as well as SQLite
