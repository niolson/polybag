# Client and catalog service in the shipping rollup; Volume by client and service

Status: done

> *This was generated by AI during the reports review.*

## Problem

`daily_shipping_stats` has no `client_id`, so a 3PL sees volume per client only through
Client Billing (`release-polish/33`, architecture finding).

## Fix

- Add `client_id` to `daily_shipping_stats` and to the rollup's grouping key, taken from the
  Package's Shipment.
- Rebuild the rollup after the migration. There are no live tenants, so no backfill logic
  is kept beyond the rebuild.
- In multi-client mode, Volume gains a **Client** grouping and a Client filter.
- Add the active Label's `carrier_service_id` to the rollup too, and group Volume by
  **Service** on it, with "Not a catalog service" for the rest. Its drill-down then uses
  the Packages list's existing catalog Service filter, so the count matches (moved here
  from `02`).

## Done when

Tests that the rollup splits by client and that Volume's grouping and filter use it.

## Comments

- 2026-11-25 — Done. `daily_shipping_stats` gained `client_id` (the Shipment's) and `carrier_service_id` (the active Label's), both in the unique key; the migration rebuilds the whole rollup with `stats:aggregate --from=2000-01-01`. Volume groups by Service (shown after the carrier's display name; "Not a catalog service" links to the Packages filter's unmapped value) and, in multi-client mode, by Client, with a Client filter that the Share column and the drill-downs honor. One local probe showed why: several reported USPS service names roll up under one catalog service. Tests in `AggregateShippingStatsCommandTest` and `VolumeReportTest`.
- 2026-11-25 — Review fixes. The migration rebuilds with its own frozen INSERT…SELECT rather than calling `stats:aggregate`, which will change with the schema and could otherwise break a fresh install. It runs on MySQL only, since SQLite is only ever a fresh test database. `down()` empties the rollup before restoring the narrower key; otherwise rows split by client or service collide and, with MySQL's non-transactional DDL, leave the table with no unique key. After a rollback, run `stats:aggregate --from=2000-01-01`. Up, down, up verified on MySQL 8.4. Known gap: a shipped package with no active Label (legacy rows; the daily Label-integrity check flags them) counts under "Not a catalog service", which the Packages filter cannot list.
