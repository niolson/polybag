# Let a 3PL's Client connect their own store or seller account

Status: needs-triage
Category: enhancement
Created: 2026-10-29

## Problem

A 3PL onboards a Client by connecting the Client's Shopify store or Amazon seller account
as a Connection. Today only an Admin can run that OAuth flow: `DataSourcePolicy` is
Admin-only and `/oauth/{provider}/receive` requires `auth` and `admin`. So the 3PL either
gets the Client's store credentials, or sits with the Client while the Client signs in.
Neither is good. The Client owns the store, so the Client should approve the consent screen.

Later, the same Client would want to see their own volume and costs, and eventually their
invoices (`ClientBillingReport` already computes much of this).

## The constraint that shapes the design

Inside one installation, every staff member can see every Client's data, and that is
deliberate: PolyBag is a 3PL's own staff tool. Real tenant isolation is per installation,
not per `Client`. The code assumes this everywhere:

- `User::canAccessPanel()` only checks `active`.
- `ShipmentPolicy::viewAny()` and `view()` return `true`, and so do several other
  policies' read methods.
- Roles are a single ladder (`Role::isAtLeast()`: Packer < Manager < Admin).

A Client-facing account would be the first time `client_id` scoping acts as a security
boundary rather than a convenience. **So this must not be a new rung below Packer**, such
as `Role::Client` at level 0. Every read that returns `true` today would let a Client see
other Clients' orders, addresses and costs. "Is this a Client user" is a different
question from "how senior is this staff member", and it has to be answered on its own.

## Proposed direction

Two steps. Each is useful on its own.

### Step 1: a connect link, with no Client account

Staff create the Connection as they do now, assign it to a Client, and fill in what has to
be known before consent (a Shopify connection's `shop_domain`). Then they generate a
**connect link** to send to the Client:

- Signed, single-use, expiring (e.g. 7 days), and bound to one `DataSource` and one
  provider. It can be revoked, and generating a new link invalidates the old one.
- Opening it shows a minimal page outside the Filament panel: the 3PL's name, the Client's
  name, what is being connected, and a "Connect" button that starts the existing broker
  flow (`OAuthService::initiateAuthorizationForDataSource()`).
- The OAuth return needs a path that does not require a logged-in Admin. The link's
  session must carry the `DataSource` binding and the nonce, so the existing
  `oauth_data_source_id.{provider}` / `oauth_state.{provider}` session handling works
  unchanged. On return, show a success or failure page, not the Filament edit page.
- The Client can only authorize the Connection the link names. They cannot change its
  Client, Location, import, export or postage settings, and they never see a token.
- The audit log records who generated the link, when the Client used it, and the result.
- Staff see on the Connection whether a link is outstanding, used or expired.

This covers the onboarding need now and adds almost no new attack surface. No Client
user, no new panel, and no change to any policy.

### Step 2: Client accounts in their own panel (when reporting or invoicing is built)

A persistent login is worth having once there is something to come back to.

- **A separate Filament panel** (e.g. `/portal`) with its own `canAccessPanel()`. The
  staff panel's `canAccessPanel()` rejects Client users. The portal is empty except for
  what is put there on purpose. That's safer than taking the staff panel, where
  everything is visible, and hiding things one resource at a time.
- **A Client user is a different kind of user from staff**, not a role on the ladder:
  a required `client_id` (or a separate guard/model; to decide), and every portal query
  explicitly scoped to it. No fallback to `ClientContext` defaults, which exist for
  staff convenience.
- First contents: the Client's Connections (connect, reconnect, see status), the same
  flow as step 1. Then a scoped volume and cost report, then invoices.
- MFA and SSO need decisions for external users. The staff `require_mfa` setting
  probably should not govern them by default.

## Decisions still needed

1. Is step 1 enough for the first Clients, with step 2 waiting for reporting?
2. Should the connect link also cover carrier accounts, for a Client bringing their own
   UPS or FedEx account (`OAuthService::initiateAuthorization()` with an account ID)?
   Same shape, but a carrier account has routing scopes the Client must not edit.
3. Step 2: is a Client user a `User` with a `client_id` and a separate kind, or its own
   model and auth guard? A separate guard makes it impossible for a policy to forget the
   distinction. Sharing `User` keeps password policy, MFA and audit code in one place.
4. Can one Client user belong to more than one Client (a brand group with several
   Clients at the same 3PL)?
5. Does the OAuth broker need anything to accept a return to a non-panel URL, or is
   `return_url` (`config('app.url')`) enough as long as the receive route branches?

## Completion criteria (step 1)

- [ ] Staff can generate, view and revoke a connect link for a Shopify or Amazon Connection.
- [ ] Someone who is not logged in can complete the OAuth flow from a valid link, and the
      tokens land on that `DataSource` only.
- [ ] An expired, used, revoked or tampered link is refused, before any broker redirect.
- [ ] The link page and OAuth return expose no other Connection, Client or Shipment data.
- [ ] The Admin-only `/oauth/{provider}/receive` behavior for staff is unchanged.
- [ ] Audit entries for link creation, use and revocation.
- [ ] Feature tests covering each refusal, plus a test that a link for one Connection
      cannot be redirected to another by editing the session or query string.
