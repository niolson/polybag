# Record each order's currency, and convert where a rule is in dollars

Status: done
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

None: a feature of its own, split out of `connection-identity/01` on 2026-10-30. Not
blocked. `02` and `03` build on it.

## Problem

A Shipment's `value` and its items' `value` are bare numbers, and everything downstream
treats them as US dollars:

- **Amazon** sums `proceeds.breakdowns[type=ITEM].subtotal.amount` and drops the
  `currencyCode` beside it (`AmazonSource::sumItemProceeds()`). An Amazon connection set to
  Canada, Mexico or Brazil imports CAD, MXN or BRL amounts as dollars.
- **Shopify** reads `originalUnitPriceSet.shopMoney.amount`, the shop's currency, without
  its `currencyCode`. A store whose currency is not USD imports its prices as dollars.
- **Database** sources have no currency field to map.

Then:

- `CustomsTermsResolver` says "Customs values are USD" and converts them to EUR, GBP or
  NOK for the IOSS, UK and VOEC thresholds from USD.
- `CustomsReadiness::ITN_THRESHOLD` compares the value per classification with $2,500 to
  decide whether an export filing (EEI) is needed.
- `SpecialServiceResolver::declaredValueForPackage()` turns the Shipment's value into a
  carriage declared value, which every carrier receives as USD.

So 1,000 MXN of goods, about US$55, is held for an export filing it does not need, is
insured for $1,000, and is measured against EU thresholds as $1,000.

Converting to USD at import would not fix it. The amount the order was paid is a fact; a
dollar figure for it depends on the day it is converted, and the import day is no better
than any other. Store what the order said, and convert when a rule needs a dollar figure.

## Desired behavior

- **`shipments.currency`**, a three-letter ISO 4217 code, not null, default `USD`. The
  Shipment's `value` and every item's `value` are in it. One currency per Shipment, since
  an order is paid in one.
- **Amazon** records the `currencyCode` of the item proceeds. Items on one order in
  different currencies fail the row, as malformed data does now, rather than being summed.
- **Shopify** records `shopMoney.currencyCode`, keeping the amounts it reads today. Which
  amounts Shopify should send is `03`.
- **Database** sources can map a `currency` field; unmapped means `USD`. A value that is not
  a three-letter code fails the row. `docs/data-sources/database.md` documents it.
- **Manual Ship and the Shipment form** show the currency beside the value, defaulting to
  `USD`, editable on a Draft Shipment and on a Shipment with no Label.
- **The Shipment and its items show the currency** wherever they show a value.

A rule stated in dollars converts from the Shipment's currency through
`ExchangeRateConverter`, at the Shipment's pinned `customs_rate_date` (pinned on first use
as now, so the answer cannot move when a later day's rates arrive):

- the EEI threshold in `CustomsReadiness`
- the carriage declared value from `SpecialServiceResolver`, which stays a USD amount
- the customs thresholds in `CustomsTermsResolver`, which convert from the Shipment's
  currency instead of from USD; a EUR order into the EU needs no conversion at all

A Shipment in a currency the ECB does not publish, and with no USD shortcut, cannot be
converted. It is held the way a missing rate is held now: the registration is withheld and
`CustomsReadiness` blocks the EEI decision with a message naming the currency.

## Notes

- The ECB publishes against EUR; `ExchangeRateConverter` already crosses through it, so
  CAD to USD works. MXN and BRL are in the ECB set.
- The label cost, Offer price and carrier charges are a separate matter: they are in the
  currency the carrier bills, already recorded on the Offer.
- What a Label declares to customs is `02`. This issue changes the values PolyBag checks,
  not the ones it sends.

## Acceptance

- [x] An Amazon order priced in CAD imports with `currency = CAD` and its CAD amounts
- [x] A Shopify order imports with the shop currency's code
- [x] A Database source with a mapped currency imports it; unmapped imports `USD`; an
      invalid code fails the row
- [x] An order worth 3,000 MXN of one classification does not require an EEI filing; an
      order worth 3,000 USD does
- [x] The carriage declared value of a CAD Shipment is its USD equivalent at the pinned
      rate date
- [x] The IOSS threshold check for a EUR order compares the EUR value without conversion
- [x] A Shipment in a currency with no ECB rate is held with a message naming the currency

## Comments

**2026-10-31 — built.** `shipments.currency` (`char(3)`, default `USD`), set by every
import: Amazon from the ITEM proceeds' `currencyCode`, Shopify from
`originalUnitPriceSet.shopMoney.currencyCode`, Database from an optional `currency`
mapping (documented in `docs/data-sources/database.md`). `ShipmentRowPreparer` upper-cases
it, reads blank or absent as `USD`, and rejects anything that is not three letters. An
Amazon order whose items are in more than one currency fails its row through a new
`_row_errors` key the preparer adds to its own errors.

The pin moved out of `CustomsTermsResolver` into `ExchangeRates\ShipmentAmountConverter`,
which all three dollar rules share: the IOSS/UK/VOEC thresholds (now converted from the
Shipment's currency), the EEI threshold in `CustomsReadiness`, and the carriage declared
value in `SpecialServiceResolver` (still sent as USD). An amount already in the rule's
currency needs no rate and pins nothing. Its warnings now name the currency pair.

Decisions the issue left open:

- **EEI holds on a missing rate.** A currency no stored rate converts blocks with
  `export_itn_required`, naming the currency; entering an ITN clears it. The registration
  path withholds and warns as before, its message naming the pair.
- **Declared value with no rate** refuses the purchase through `MissingDeclaredValueException`,
  with a message naming the currency, rather than declaring an unconverted amount.
- **The code is checked for shape, not membership.** Any three letters import; one the ECB
  does not publish is then held by the rules above. No ISO 4217 table is in the app.
- **Manual Ship has no value field**, so it shows no currency: its Draft Shipments are
  `USD` with no value. The Shipment form edits the currency until a Package has an active
  Label; the item relation manager and the Shipment view show values in it, as does the
  archive export.
- **Not converted, and not in the spec:** the shipping rule's *order value* condition
  (`RuleEvaluator::evaluateOrderValue()`) still compares the bare value. Left for a
  decision; see the report on the PR.


**2026-10-31, after review:** a re-import whose source supplies no currency now keeps the Shipment's stored currency instead of resetting it to USD. A new Shipment still defaults to USD. So a manager's correction survives the next import, as the address and customs fields already do. A re-import can still change the currency of an open Shipment with a labeled Package, as it can its value: the form lock covers manual edits only.
