# USPS: send ZPL label text as ASCII so it does not print as mojibake or `?`

Status: done — 2026-10-07
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

`02`, which found it.

## Problem

Every USPS label in ZPL misprints non-ASCII address text; the PDF of the same request
prints it correctly. Confirmed on a Zebra thermal printer, 2026-10-07 (`02`):

- **Domestic.** The template is single-byte: Ground Advantage selects `^CI27`
  (Windows-1252) and Priority Mail `^CI13` (code page 850), so the service banner can
  print `™` or `®`. Neither switches to `^CI28` (UTF-8) afterwards, but the address
  block is written as UTF-8 bytes, so each character prints as two wrong glyphs:
  `Zoë Łukasiewicz` printed as `ZOÃ? Å?UKASIEWICZ` and `ZO ├? ┼?UKASIEWICZ`.
- **International.** The template does switch to `^CI28`, and the printer decodes the
  characters, but the built-in font it selects (`^CF0`) has no glyphs for them:
  `Łukasz Wójcik, ul. Zwycięstwa 27B, Wodzisław Śląski` printed as `?OKASZ W?JCIK`,
  `UL. ZWYCI?STWA 27B`, `WODZIS?AW ?L?SKI`.

Domestic USPS covers Puerto Rico, where street names routinely carry `ñ` and accented
vowels (`Calle Muñoz Rivera`), and US recipients' names carry them anywhere. A validated
domestic street is usually ASCII already, because USPS standardizes it; names, companies,
unvalidated addresses and every international address are not.

## Desired behavior

When `UspsAdapter::createDomesticShipment()` or `createInternationalShipment()` requests
ZPL (`ZPL203DPI` or `ZPL300DPI`), every free-text field in `toAddress` and `fromAddress`
is sent as ASCII, transliterated with `Str::ascii()` (`ë` → `e`, `Ł` → `L`, `ñ` → `n`,
`ß` → `ss`): `firstName`, `lastName`, `firm`, `streetAddress`, `secondaryAddress`,
`city`, and the international `province`. Transliterate before truncating, as
`FedexAdapter::labelText()` does.

Leave alone:

- A PDF label, domestic or international: it prints the character, and transliterating
  would only lose it
- Codes (`state`, `ZIPCode`) and anything already ASCII

If transliteration would leave a required field blank (a name wholly in CJK or
Cyrillic):

- **Domestic:** send the original, as `01` does for FedEx: a garbled name is no worse
  than what is printed today, and a blank one can get the request refused.
- **International, in either format:** refuse before purchase with a message naming the
  field, so the operator can enter a romanized address. The International Mail Manual
  (IMM 122, *Addressing*) requires the complete address "with roman letters and arabic
  numerals", and an address in Russian, Greek, Arabic, Hebrew, Cyrillic, Japanese or
  Chinese characters to "bear an interline translation in English". The PDF would print
  the original script, but USPS does not accept it. Accented Latin letters are roman
  letters and are not refused.

Whether to share one helper with `FedexAdapter::labelText()` or keep a private one is the
implementer's call; the FedEx one logs on `fedex-validation`, which a USPS caller should
not.

## Acceptance criteria

- [x] `UspsAdapterTest`: a domestic ZPL label request for recipient `Zoë Łukasiewicz-Groß`,
      company `Café Niño`, street `Calle Muñoz Rivera 12`, city `Mayagüez` sends
      `Zoe`, `Lukasiewicz-Gross`, `Cafe Nino`, `Calle Munoz Rivera 12`, `Mayaguez`; the
      sender is transliterated the same way
- [x] An international ZPL request to `Łukasz Wójcik, ul. Zwycięstwa 27B, Wodzisław
      Śląski` sends `Lukasz Wojcik`, `ul. Zwyciestwa 27B`, `Wodzislaw Slaski`
- [x] The same requests in PDF send the text unchanged
- [x] A domestic field that transliterates to blank is sent as the original; an
      international one (PDF or ZPL) is refused before purchase, naming the field
- [x] One sandbox domestic and one international ZPL label with diacritics print ASCII
      only on a Zebra, cancelled straight away (record it here; the raw capture goes in `.scratch/`)

## Out of scope

- Rewriting the ZPL USPS returns (inserting `^CI28`, re-encoding the address block):
  editing a carrier's label is more fragile than sending text it can print
- Label references (`#1241` and the like), which are order numbers and already ASCII
- Customs item descriptions on the international CP72 (product names); worth checking
  once the address is fixed, but product catalogs are mostly ASCII
- Storing the transliterated address anywhere: the Shipment keeps what was imported

## Comments

- 2026-10-07 — opened from `02`'s sandbox labels.
- 2026-10-07 — widened from domestic-only after `02`'s printed international label
  showed `?` for every diacritic.
- 2026-10-07 — international fallback changed from "send the original" to "refuse",
  per IMM 122 (https://pe.usps.com/text/imm/immc1_008.htm).
- 2026-10-07 — Built. `UspsAdapter::labelText()` runs over every free-text field the
  domestic and international address builders send, for recipient and sender, before
  truncating: ZPL gets `Str::ascii()` (domestic text with no ASCII form is sent as
  entered); a domestic PDF is sent as entered; an international PDF keeps Latin letters,
  accents included, and romanizes runs in any other script (`Иван` → `Ivan`). Before the
  idempotency key is issued, `unromanizableAddressField()` refuses an international
  label, in either format, holding a letter or digit `Str::ascii()` cannot map. It drops
  CJK, Hebrew and Hangul silently rather than leaving the field blank
  (`山田 Taro` → ` Taro`), so "the field came out empty" is the wrong test. Testing each
  character alone is wrong too: the Cyrillic soft sign maps to nothing on purpose, so
  `Ольга` (`Olga`) would be refused. The check asks the same tables
  (`voku\helper\ASCII::to_ascii()`, keeping unsupported characters) what they
  cannot transliterate. Cyrillic, Greek and Arabic transliterate and pass. Digits are made
  ASCII first with `IntlChar::charDigitValue()`, because `Str::ascii()` maps
  Arabic-Indic `٢٧` but drops Persian `۲۷` and Devanagari `२७`, which would lose a
  house number (found in review). The refusal names the field (`recipient's last name`) and
  reaches the operator as an ordinary declined purchase.
- 2026-10-07 — Sandbox (TEM) check through the patched adapter, all four labels
  cancelled: the domestic and the international ZPL now contain no non-ASCII byte and
  carry `ZOE LUKASIEWICZ-GROSS`, `LUKASZ WOJCIK`, `UL. ZWYCIESTWA 27B`,
  `WODZISLAW SLASKI`; both PDFs still print `ZOË ŁUKASIEWICZ-GROSS` and
  `WODZISŁAW ŚLĄSKI`. The fixed ZPLs were read, not printed: an all-ASCII ZPL under font 0
  prints as written, and the earlier prints showed the bytes reach the printer intact.
