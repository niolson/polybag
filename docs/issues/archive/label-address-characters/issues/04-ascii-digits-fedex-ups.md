# FedEx and UPS: send non-ASCII digits as ASCII so house numbers survive

Status: done — 2026-10-07
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

`03`, whose review found that `Str::ascii()` maps Arabic-Indic `٢٧` but drops Persian
`۲۷` and Devanagari `२७` outright. `03` fixed USPS; `01`'s FedEx transliteration had the
same gap, and UPS had not been tested with them.

## Problem

- **FedEx:** `FedexAdapter::labelText()` sent `خیابان آزادی ۲۷` as `khyaban azady `:
  the house number was gone.
- **UPS:** `UpsAdapter` sends address text as entered and relies on UPS, which
  transliterates letters itself (`02`). A UPS sandbox (CIE) label to
  `ul. Zwycięstwa ۲۷B`, `Lokal २` printed `ZWYCIĘSTWA □□B` and `LOKAL □` on the
  GIF label (no glyph) and `Zwyciestwa **B`, `Lokal *` on the commercial invoice. The
  Cyrillic recipient name `Ольга` printed as entered on the label and as `Olga` on the
  invoice, so letters need nothing from us.

## Desired behavior

Every Unicode decimal digit is sent as its ASCII digit (`IntlChar::charDigitValue()`),
in one place shared by the three adapters:

- FedEx: everywhere `labelText()` already transliterates
- UPS: street lines and city, on the label and the rate request; letters stay as entered
- USPS: unchanged in behavior, moved to the shared helper

## Acceptance criteria

- [x] `App\Support\LabelText::ascii()` makes Persian, Devanagari, Arabic-Indic and
      fullwidth digits ASCII, and transliterates letters as `Str::ascii()` does;
      `asciiDigits()` changes the digits only
- [x] `FedexAdapterTest`: a street `خیابان آزادی ۲۷` is sent as `khyaban azady 27`
- [x] `UpsAdapterTest`: `ul. Zwycięstwa ۲۷B` and `Lokal २` go out as
      `ul. Zwycięstwa 27B` and `Lokal 2` on ShipTo, SoldTo and the rate request, and the
      name and city keep their letters
- [x] One UPS sandbox label prints the house number

## Comments

- 2026-10-07 — Built. `App\Support\LabelText` holds `ascii()` (digits, then
  `Str::ascii()`) and `asciiDigits()`. `FedexAdapter::labelText()` and
  `UspsAdapter::labelText()` call `ascii()`; `UspsAdapter::unromanizableAddressField()`
  calls `asciiDigits()`; `UpsAdapter::buildAddressLines()` (shared by label and rate
  request), `buildAddress()` and the rate request's destination city call
  `asciiDigits()`.
- 2026-10-07 — UPS sandbox (CIE) label through the patched adapter, GIF and ZPL: the
  request carries `ul. Zwycięstwa 27B`, `Lokal 2`; the GIF label prints
  `UL. ZWYCIĘSTWA 27B`, `LOKAL 2` and the commercial invoice `ul. Zwyciestwa 27B`,
  `Lokal 2`. CIE returns the placeholder tracking number `1ZXXXXXXXXXXXXXXXX` and
  creates no shipment, so the void answers 190102 and nothing was billed. UPS's ZPL is a
  single bitmap, so it was not read; it renders from the same request. Captures are in
  `.scratch/label-address-characters/`.
- Not changed: a UPS international label still prints a Cyrillic name in Cyrillic, as
  entered. Whether UPS wants international addresses romanized, as USPS does (IMM 122),
  is not established; nothing has been refused for it.
