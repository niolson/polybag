# UPS and USPS: find out what a diacritic in the address prints as

Status: done — 2026-10-07
Category: research
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

`01`, which fixes FedEx. Decides whether the same transliteration goes into
`UpsAdapter` and `UspsAdapter`.

## Question

`UpsAdapter::buildAddress()` and the USPS address builders send street lines, city and
names exactly as imported, the same as FedEx did. Whether UPS and USPS render `ę`, `ł`,
`ß` and friends correctly on the label, substitute `?` like FedEx, or refuse the
request is unknown — no label with a diacritic in the address has been read.

## What needs a person

1. **UPS:** buy one international label to an address with a diacritic in the street
   and city, in ZPL and in GIF, read both, and void it.
2. **USPS:** the same for one international label, and one domestic label with a
   diacritic in the recipient name (a US address can carry one too).
3. Record what each printed, in each format, and what the 2D barcode or IMb carries if
   it can be read. Raw captures go in `.scratch/`; nothing customer-identifying goes in
   this file.

## Outcome

- A carrier that prints the character correctly is left alone: transliterating would
  only lose information
- A carrier that substitutes or refuses gets the same treatment as `01`, as its own
  issue

## Comments

- 2026-10-01 — **UPS: no change needed.** One sandbox (CIE) international label in ZPL
  to a Polish address whose street carries `ę`, sent unchanged by `UpsAdapter`: UPS
  transliterated it itself, printing `ZWYCIESTWA` on the label and `Zwyciestwa` on the
  commercial invoice, with nothing dropped and no `?`. Production was not run; CIE
  renders labels through the same engine, so it is taken as representative unless a
  production label says otherwise. GIF not read. **USPS is still open.**
- 2026-10-07 — **USPS: PDF needs nothing; every ZPL label garbles non-ASCII text —
  fixed in `03`.** Sandbox (TEM) labels, all cancelled, bought
  through `UspsAdapter::createShipment()` with the recipient overridden in memory:
  - International, Priority Mail International to Poland, street `ul. Zwycięstwa 27B`,
    city `Wodzisław Śląski`, name `Łukasz Wójcik`. PDF (embedded Arial, Identity-H) and
    ZPL carry every character, upper-cased; the ZPL switches to `^CI28` (UTF-8)
    before the address block. The PDF prints them all (see the next comment for the ZPL).
  - Domestic, Ground Advantage, name `Zoë Łukasiewicz-Groß`. The PDF prints
    `ZOË ŁUKASIEWICZ-GROSS` (USPS upper-cases `ß` to `SS`, which is correct). The ZPL
    selects `^CI27` (Windows-1252) to print the `™` in the service banner, never switches
    back, and then puts the name in as UTF-8 bytes — so a Zebra prints
    `ZOÃ‹ Å?UKASIEWICZ-GROSS`. A domestic Priority Mail ZPL does the same under `^CI13`
    (code page 850, for the `®`): `ZO├ï ┼üUKASIEWICZ-GROSS`. No barcode field in either
    ZPL carries the name (the IMpb data is the ZIP and tracking number), so automated
    routing is unaffected; what a carrier employee reads is not.
  - The fault is in USPS's domestic ZPL template, not in what we send: the same request
    body renders correctly as a PDF. Raw captures and the probe script are in
    `.scratch/label-address-characters/`.
- 2026-10-07 — **Printed** all three ZPLs on a Zebra thermal printer through QZ Tray, from the app's
  Reprint action. Domestic came out as predicted: `ZOÃ? Å?UKASIEWICZ-GROSS` (Ground
  Advantage, `^CI27`) and `ZO ├? ┼?UKASIEWICZ-GROSS` (Priority Mail, `^CI13`). The
  international label, which reading the ZPL had suggested was fine, printed
  `?OKASZ W?JCIK`, `UL. ZWYCI?STWA 27B`, `WODZIS?AW ?L?SKI`: one `?` per character,
  so the printer decoded the UTF-8 correctly, but the built-in font USPS selects
  (`^CF0`, scalable font 0) has no glyph for any of them — not even `Ó`, which is in
  Latin-1. The domestic mojibake shows the bytes reach the printer intact, so this is
  not the print path. **Every USPS ZPL label needs ASCII text, international included;**
  `03` is widened to say so. A printer with a fuller font 0 might do better, but a fix
  cannot depend on which Zebra the warehouse owns.
