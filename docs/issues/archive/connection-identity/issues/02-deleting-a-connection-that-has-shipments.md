# Deleting a connection that has Shipments

Status: done
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

None. Related to `01`: both are about a connection standing for one store or seller
account. Not blocked.

## Problem

An admin can delete a connection that has imported Shipments from its edit page
(`DataSourcePolicy::delete()` checks only the role). The table's bulk delete was removed
on 2026-10-29. `DataSource` is
not soft-deleted, so the row is gone and the foreign keys decide the rest:

- **Shipments** keep their rows with `data_source_id` set to null
  (`nullOnDelete`). Nothing can tell afterwards which store or seller they came from.
- **Packages, Labels and Offers** bought through the connection's postage keep their rows
  with `postage_data_source_id` null. `PostageSourceDispatcher::resolve()` then finds no
  source type, so voiding or tracking a Shopify or Amazon Label goes to the
  unrecognized handler.
- **Export history** (`package_exports`), **location mappings**
  (`data_source_locations`), **Amazon catalog look-ups** and **Amazon Shipping scopes**
  (`carrier_account_scopes`) are deleted with it (`cascadeOnDelete`).

The orphaned Shipments still open get no closure from the source, no tracking export back
to it, and no origin-bound Shopify or Amazon postage.

Creating the connection again does not help. Nothing re-attaches Shipments. The new
connection has a new ID, so its first import writes a second Shipment for every order
still in its feed, beside the orphan. That is `01`'s duplicate, with no connection left to
close the orphan.

## Options

1. **Refuse to delete a connection that anything references.** Shipments, Packages,
   Labels or Offers. The delete action says to make the connection inactive instead,
   which already stops imports and postage. An unused connection, such as one created by
   mistake, can still be deleted. Reconnecting to a store goes through Reconnect on the
   same record, which already exists. **Recommended:** it is the smallest change, and it
   keeps the record that voids, tracking and exports need.
2. **Soft-delete connections**, and treat a deleted one as inactive everywhere. This keeps
   the foreign keys, but every query that lists connections then has to exclude deleted
   ones, and a deleted connection still cannot be seen or reconnected without a restore
   screen. That is most of option 1's behavior, done the long way round.
3. **Re-attach orphans when a connection is recreated.** Not possible from the data as it
   stands: an orphan's only link to its account was the deleted row. It would need the
   account identity from `01` copied onto every Shipment.

## Decisions

Settled 2026-11-02:

- **Option 1.** A connection with history is made inactive, never deleted. When a client
  leaves, disconnecting its OAuth grant at the store or seller account stops anything
  being sent or received, even if the connection is later made active again. Deleting a
  connection together with its Shipments is not offered.
- **Bulk delete** does not arise: the connections list has none, and a test keeps it so.

## Acceptance

- [x] Deleting a connection with Shipments, Packages, Labels or Offers is refused with a
      message to make it inactive instead; nothing is deleted
- [x] A connection nothing references can still be deleted
- [x] No bulk delete on the connections list

## Comments

### 2026-11-02 — shipped

> *This was generated by AI.*

- **Built.** `DataSource::hasShippingHistory()` asks for a Shipment from the connection, or
  a Package, Label or Offer whose `postage_data_source_id` names it.
  `DataSourcePolicy::delete()` denies with "This connection has shipments or postage
  history, so it cannot be deleted. Make it inactive instead." The edit page's Delete
  stays visible but disabled, with that message as its tooltip (`authorizationTooltip()`).
  Tests: `DataSourceResourceTest`.
- **Not changed.** The foreign keys still `nullOnDelete`. The policy is the only path that
  deletes a connection; making the database refuse too would rebuild four tables for a
  path nothing takes.
- **Export history does not block.** A connection that only receives exports (global
  export on, import off) can still be deleted, and its `package_exports` rows go with it.
  Exported Packages stay marked `exported`, so nothing is sent twice; only the record of
  where they went is lost. The other cascades are configuration or cache.
- **The Amazon reconnect notice** that tells an admin to delete a conflicting connection
  says to leave it inactive instead when it has history.
- **Any Offer counts**, expired or not, until `PurgeData` or archiving removes it. Some
  are never purged (consumed without a result, confirmed with no recorded Label, or
  retention set to 0), so a connection that only ever quoted may only ever be made
  inactive.
