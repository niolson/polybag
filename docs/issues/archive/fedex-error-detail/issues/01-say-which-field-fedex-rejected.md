# Say which field FedEx rejected, when buying and when rating

Status: done
Category: enhancement
Created: 2026-10-23

## Problem

Buying a FedEx label from a Location with no phone number showed only:

> Shipping Error
>
> Validation failed for object='shipShipmentInputVO'. Error count: 1

FedEx's reply said exactly what was wrong, in the error's `parameterList`:

```json
{
  "code": "INVALID.INPUT.EXCEPTION",
  "message": "Validation failed for object='shipShipmentInputVO'. Error count: 1",
  "parameterList": [
    {
      "key": "NotNull.shipShipmentInputVO.requestedShipment.shipper.contact.phoneNumber",
      "value": "phoneNumber cannot be null"
    }
  ]
}
```

`FedexAdapter::createShipment()` builds the failure from `$errors[0]['message']` alone,
so the field never reaches the person who can fix it. The full reply goes only to
`storage/logs/fedex-validation-*.log`, which a hosted user cannot read.

Rating is worse. When a rate request fails, `parseRateResponse()` logs the errors to
the same channel and returns an empty collection, so FedEx simply drops out of the rate
list with no message at all.

## What is needed

1. **A message built from every error, with its fields.** For each error, when
   `parameterList` has entries, show each entry's `value` and its `key` with the
   constraint and object prefix removed (`NotNull.shipShipmentInputVO.`), for example
   *"phoneNumber cannot be null (shipper.contact.phoneNumber)"*. FedEx's
   `Error count: N` means there can be several; show all of them. Keep `message` when
   there is no `parameterList`, and keep it ahead of the fields when it says more than
   the generic `Validation failed for object=…`.
2. **Plain language for the fields a user can fix**, starting with:
   - `shipper.contact.phoneNumber`: *"The ship-from location has no phone number. Add one under Locations."*
   - `shipper.address.*`: point at the ship-from location
   - `recipients[0].address.*` / `recipients[0].contact.*`: point at the shipment's address.
     (The recipient's phone already falls back to the shipper's, so the shipper's is the
     one that matters.)

   Anything else is shown as in 1. Put the mapping in one place, testable without a
   request.
3. **Rating reports its failure too.** A failed FedEx rate request should surface the
   same message on the Ship page rather than FedEx silently missing. The place exists:
   `ShippingRateService::exclude()` feeds `$options->exclusions`, which `Ship.php` shows
   as a "<carrier> excluded" warning with its reason. Today only
   `CarrierUnavailableException` reaches it, and that exception means a configuration
   problem, "not because a request failed", so do not throw it here. Instead:
   - give `CarrierRateFetchException` an optional reason, keeping the current
     "Failed to fetch rates from …" message when none is given;
   - have `parseRateResponse()` throw it with the formatted message instead of
     returning an empty collection;
   - have all three catch sites in `ShippingRateService` exclude the source with that
     message: the prepare phase, the synchronous fallback, and the concurrent parse
     phase (whose `catch (\Exception)` only logs today). Keep the existing log lines.

   This changes what any carrier's rate-fetch failure shows, not only FedEx's; that is
   intended.
4. **Scrub on the buy path, as now.** The new `createShipment()` message goes through
   `scrubCustomsIds()`, like the current one, since FedEx can echo submitted values back
   in `parameterList`. The rating path needs no scrubbing: `RateRequest` carries no
   recipient tax ID or exporter EIN, so do not change the scrubber's signature for it.

## Testing

- Unit tests on the formatter:
  - the reply above gives the phone-number message;
  - an error with no `parameterList` keeps its `message`;
  - two errors give both;
  - an unknown field path is shown cleaned, not dropped;
  - a customs ID in a value is scrubbed.
- A feature test that a failed `createShipment` returns that message in its
  `ShipResponse`.
- Feature tests that a failed FedEx rate request appears in `exclusions` with that
  message, on both the synchronous path (what Saloon fakes route through) and the
  concurrent path (resolve a mocked `GuzzleSender` from the container, as the comment
  above Phase 2 describes).

## Comments

- **2026-10-27** — Done. `FedexErrorMessage` builds the message from every error and every
  `parameterList` field, with the plain-language mapping in `describeField()`.
  `createShipment()` returns it, scrubbed. A failed rate request throws
  `CarrierRateFetchException` with it ("FedEx could not rate this package: …"), and
  `ShippingRateService` excludes the source with that message at all three catch sites, so
  the Ship page shows it as "FedEx excluded". The source is no longer also counted among
  the unrated sources.
- The shipper phone gets "has no phone number" only for a `NotNull` key. A phone FedEx
  rejects for another reason points at the location without claiming it is missing.
- **Found while building:** on the concurrent path Saloon rejects the promise for a 4xx or
  5xx, so before this no adapter's `parseRateResponse()` saw a failed reply there; it went
  to the "request failed" log line. A rejected `RequestException` is now parsed like a
  fulfilled reply, as FedEx's synchronous `getRates()` already did. Every adapter's parser
  already handled a failed response.
- Every carrier's `CarrierRateFetchException` now shows as an exclusion. UPS and Amazon
  have no reason to give, so theirs say "Failed to fetch rates from UPS".
- Left as they were: a transport failure (timeout, connection refused) on the concurrent
  path is still only logged, not excluded. Not checked against live FedEx; the replies in
  the tests are the one in the Problem section, sent as a 422.
