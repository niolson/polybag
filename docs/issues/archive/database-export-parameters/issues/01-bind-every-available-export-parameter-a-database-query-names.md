# A Database export query that names `:cost` or a dimension fails until a hidden setting is edited

> *This was generated by AI during release-polish pass 1.*

Status: done

Page or flow: Connections → a Database connection → Database Export → Export Query

Found: 2026-10-15, setting up the demo import database. The demo tools print an export
query naming `:cost`, `:height`, `:width` and `:length`. Every run of `demo:reset` then
aborted its write-back after ten failures with
`SQLSTATE[HY093]: Invalid parameter number`.

## Problem

`PackageExportService::buildExportData()` builds the parameter set from the connection's
`export_field_mapping`, which defaults to seven names: `tracking_number`, `carrier`,
`service`, `weight`, `shipment_reference`, `fulfillment_order_id`, `amazon_order_id`.
`DatabaseSource::exportPackage()` then binds only the parameters the query names, from
what the mapping supplied.

So a query that names `:cost`, `:height`, `:width` or `:length` is rejected by PDO, with
nothing in the UI to say why. `docs/data-sources/database.md` documents the trap ("the most
likely way to break a working export") and the way out: edit `settings.export_field_mapping`
directly. There is no form field, so an operator has to use tinker or the database.

`buildExportData()` already computes all eleven values (`tracking_number`, `weight`,
`height`, `width`, `length`, `cost`, `carrier`, `service`, `shipment_reference`,
`fulfillment_order_id`, `amazon_order_id`) before the mapping filters them down. For a
Database connection the mapping adds nothing but the trap: its only effect is renaming a
parameter, and a query author can do that with a column alias.

## Proposed direction

Not a form field for the mapping. That would make a setting nobody wants to maintain
easier to reach and leave the trap in place.

For a Database connection, bind every available value under its own name and keep
`DatabaseSource::exportPackage()`'s existing filtering, so a query binds exactly what it
names. A query naming `:cost` then works with no setting.

Leave the Shopify and Amazon paths as they are. `tests/Feature/AmazonImportExportTest.php`
sets `export_field_mapping` in several places, so those sources depend on it.

## Open question

`cost` and the dimensions are left out of the defaults today. If that was deliberate, for
example so a customer's database never receives what PolyBag paid for postage, then
binding everything by default reverses it. Decide that before building. If it was
deliberate, the alternative is to keep the defaults and make the failure legible: a
save-time check that names the parameters the query uses and the export cannot supply.

## Acceptance

- A Database export query that names any of the eleven values exports without editing
  `export_field_mapping`.
- A query naming a parameter that is not one of them fails when the connection is saved,
  or at the first export, with the parameter's name in the message instead of `HY093`.
- The Shopify and Amazon export paths behave as before.
- `docs/data-sources/database.md` drops the warning about the hidden setting.
- The demo tools' printed query runs on a new connection with nothing else configured.

## Comments

- 2026-10-15 — Worked around for the demo by setting `export_field_mapping` on the local
  connection with tinker. The demo instance needs the same, and so would any recreated
  connection.

- 2026-10-21 — **done.** The open question was settled first: nothing in the history
  shows `cost` or the dimensions were left out on purpose (`DataSourceFactory` even built
  an unused export mapping that listed them), and a value reaches the customer database
  only when their query names it. So a Database connection now binds all eleven values
  under their own names (`PackageExportService::ExportValues`) and ignores
  `export_field_mapping`; Shopify and Amazon still use it. The unused mapping in
  `DataSourceFactory` is gone. `DatabaseSource::namedParameters()` reads the names the
  way PDO does, skipping quoted text, comments and `::` casts. Saving the form refuses a
  parameter outside the eleven (`DatabaseSource::exportQueryParametersRule()`), and an
  export of a query saved before that check fails permanently with
  `Export query names :x, which the export does not supply.` instead of `HY093`. The
  helper text and `docs/data-sources/database.md` list all eleven, and the warning about
  the hidden setting is gone. Tests: `tests/Feature/DatabaseExportTest.php`.
