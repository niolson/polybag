# A Database connection that uses an SSH tunnel can import but never write tracking back

> *This was generated by AI during release-polish pass 1.*

Status: done

Page or flow: Connections → a Database connection with the SSH Tunnel enabled and Write
Tracking Back to Source Database on

Found: 2026-10-15, running `demo:reset` on the demo instance. Imports read 3,609 shipments
through the tunnel; the write-back then failed ten times in a row with
`SQLSTATE[HY000] [2002] Connection refused` and the reset aborted it.

## Problem

`DatabaseSource` opens the tunnel in the import connection check and in
`validateExportConfiguration()`, through `openTunnelIfConfigured()`, and closes it when the
driver is destroyed. `exportPackage()` does neither. Nothing else on the export path calls
`validateExportConfiguration()` either: `PackageExportService::exportPackage()` builds the
driver with `DataSourceFactory::make()` and calls `exportPackage()` on it directly.

So the export connects to the connection's configured `host` and `port`. For a tunnel those
are the address *as seen from the bastion*, commonly `127.0.0.1`, where nothing is
listening on the PolyBag side. The demo instance's connection has `db_host = 127.0.0.1` and
`ssh_host` set, and that is exactly what it did.

It is silent in the UI until an export is attempted. The import, the connection test and
Preview Queries all go through the tunnel and succeed. Every shipped Package then fails to
export, is retried by `packages:export --scheduled` every five minutes, and fills the
failed-export indicators.

No test covers a tunnelled connection together with an export query.

## Where it does not happen

- Importing: one tunnel per run, opened once by the driver that runs the shipments query,
  the items query, the status lookups and the mark-exported writes.
- `demo:reset` fabricating Packages: it writes only PolyBag's own tables. Only its
  write-back step reaches the export path.

## Open design question

`PackageExportService` builds a new driver for every Package, and a driver closes its
tunnel when it is destroyed. Opening the tunnel inside `exportPackage()` would therefore
cost an SSH handshake per Package. That is acceptable for the one export a label purchase
queues. It is not acceptable for a batch: `demo:reset` exports about 3,600 fabricated
Packages, and `packages:export --scheduled` retries a backlog in one run.

The fix has to share one tunnel across a batch, for example by having
`exportUnexported()` and `DemoReset` hold the driver for the run, or by keeping the driver
per source for the life of the service. Decide that before building; a per-Package
tunnel would fix correctness and make the demo reset take a long time.

## Acceptance

- A Database export through an SSH tunnel writes tracking back, with a test that uses a
  tunnelled connection and an export query.
- A batch export (`exportUnexported()`, `demo:reset`) opens one tunnel per source, not one
  per Package.
- The tunnel is closed when the batch ends, including when it aborts.
- A failure to open the tunnel during an export is reported as a tunnel failure, not as
  `Connection refused` on a local port.
- `docs/data-sources/database.md` says the tunnel applies to exports ("opened per import
  run" is no longer the whole story).

## Comments

- 2026-10-15 — Worked around on the demo instance by running `demo:reset --skip-export` and
  turning off Write Tracking Back on its connection. Until this is fixed, a tunnelled
  connection should not have it on.

- 2026-10-21 — **done.** `DatabaseSource::exportPackage()` opens the tunnel, which stays
  open for the driver's life. `PackageExportService::batch()` keeps one driver per
  Database connection for a batch and closes every tunnel in a `finally`.
  `exportPackage()` is a batch of one, and `exportUnexported()` and `demo:reset`'s
  write-back each run as one batch, so a backlog or a demo reset opens one tunnel per
  connection. Only Database drivers are kept for the batch; Shopify and Amazon drivers
  are still built per export. A tunnel that will not open fails the export as
  `SSH tunnel failed: …`, which is retryable, and the driver remembers the failure, so the
  rest of the batch does not try another handshake per Package. The tunnel is built
  through the container so tests can stand in for it. Tests:
  `tests/Feature/DatabaseExportTest.php`, covering a batch, a single export, an aborted
  batch, and a tunnel that will not open. The demo instance's workaround (Write Tracking
  Back off, `--skip-export`) can now be undone.
