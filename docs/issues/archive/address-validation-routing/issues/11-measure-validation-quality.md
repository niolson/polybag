## What to build

Validator answers (slice [04](04-record-every-validator-answer.md)) say what each API
thought, and FedEx shadow answers ([10](10-fedex-shadow-check.md)) say what FedEx would
have thought. To improve the routing and the deliverability mapping we also need to know
whether they were right. Google is expensive in aggregate and FedEx is free only for now,
so which validator to trust where is worth getting right from real orders.

The audience is us, deciding future releases, not tenants. Each hosted tenant has its own
database, so the answer has to be collected across tenants, and a screen inside one
tenant's app wouldn't help.

Everything here must follow [pii-retention](../../pii-retention/): record verdicts
and outcomes as facts on the answer or the Package when they happen, and never make
copies of addresses. A signal that can be read only from the address or from the audit
log has to be captured when it happens, or not used.

### 1. Which part of the address an edit changed

`address_changed_at` ([10](10-fedex-shadow-check.md)) says the address changed after
validation, but not how. Adding a missing unit and correcting a wrong street say very
different things about the validator. When `Shipment::stampAddressChanged()` stamps an
answer, it also sets four nullable booleans on it, comparing the old address with the
new one using the normalization `Shipment::addressChanged()` already applies:

- `street_changed`: `address1`
- `unit_changed`: `address2`
- `locality_changed`: `city` or `state_or_province`
- `postcode_changed`: `postal_code`

A change of `country` sets all four. The flags come from the first edit only, like the
stamp. `ShipmentBatchWriter`'s readdress path has the old and new rows to hand and must
set the same flags; it can't use one bulk update for Shipments whose edits differ.

Only `Shipment::ADDRESS_FIELDS` count. Name, company, phone and email changes don't stamp
anything, clear the validation result, or cause a re-validation.

### 2. The report command

`address-validation:report --since= --until= --json` outputs **counts only**. It carries
no Shipment IDs, references, addresses or client names. Our hosted deployment's
operations tooling, which lives outside this repository, runs it per tenant and
aggregates the results. An on-prem operator can run it too and will see only their own
data.

**What counts as one data point.** The latest live answer when the Shipment's first
Label was bought: the earliest `purchased_at` across its Packages' Labels, voided ones
included. That answer is usually the one that settled the address, but it is the last
inconclusive one when no validator settled it, which is how `unverified` results are
measured. Answers that a re-validation replaced before then are left out, and so are
Shipments that were never validated or never got a Label. Its shadow answer, if any, is
reported alongside it.

**The outcome.** Each data point gets exactly one, in this order of precedence:

| Outcome | Rule | Source |
|---|---|---|
| `returned` | any Package's `tracking_status` is `returned` | `packages.tracking_status` |
| `delivered` | otherwise, every Package has `delivered_at` or a `delivered` status | `packages.delivered_at`, `packages.tracking_status` |
| `exception` | otherwise, once the outcome counts as final, any Package's `tracking_status` is `exception` | `packages.tracking_status` |
| `pending` | otherwise | — |

Only Packages that are shipped now count, so a voided Package doesn't stop the others
from reading as delivered.

An outcome counts as final once every Package is delivered or any is returned. In all
other cases it is `pending` until the first Label is 30 days old, and after that it is
reported as it stands. `exception` is coarse (weather, damage and missed delivery attempts
all count) and is reported as its own column, never folded into `returned`.

Separately from the outcome, the edit columns: `address_changed_at` set, and each of the
four part flags. An edit is not proof of error, since customers also ask for changes, so
it stays its own column.

**No weighting.** There is no combined score. The report is a cross-tab: validator, live
or shadow, country, deliverability (or inconclusive and its reason) down the side;
outcome and the edit columns across. Rates are worked out by whoever reads it.

**The shadow comparison.** For each live answer with a shadow answer: a matrix of the live
deliverability against FedEx's (deliverability, or inconclusive and its reason), the count
of each of `10`'s difference flags, and for the cells where they disagree, the outcome.

**Sample size.** Every cell carries its *n*. The human-readable output marks a row with
fewer than 30 data points as too small to judge from. Nothing is hidden, since counts
carry no PII.

### Deferred signals

- **Carrier tracking exception for a bad address.** `TrackingStatus::Exception` is too
  coarse. Each event's carrier `statusCode` is kept in `packages.tracking_details`, so a
  later slice can map the codes that mean "bad address" for USPS, UPS, FedEx and Amazon
  and split `exception` into `bad_address` and the rest. That mapping is research.
- **Label purchase failed on the address.** The only record is
  `shipping_offers.purchase_failed_at` with a free-text carrier message, and offers are
  purged after 7 days. Blind Shopify purchases never have an Offer at all. Using it would
  mean classifying the message as address-related at failure time and stamping the
  Shipment's answers. Since validation runs before purchase, such failures should be
  rare. Revisit if the report shows many `delivered` outcomes after an operator edit.

## Comments

**2026-10-07 — triage.** Decided with the maintainer: v1 uses address edits, deliveries
and returns; tracking-exception codes and purchase failures are deferred. There is no
weighting, only a cross-tab. A data point is the answer current at first Label purchase.
Edits record which part of the address changed.

A finding outside this issue: `shipments:purge-pii` doesn't clear
`packages.tracking_details`. That field holds each tracking event's location and the
carrier's raw response, which may include the recipient's city or a signer's name. This
hasn't been checked per carrier and belongs with pii-retention, not here.

**2026-10-07 — implemented.** `Shipment::addressChanges()` returns the four part flags
(or null), `addressChanged()` is built on it, and `stampAddressChanged()` takes one
Shipment and its flags. `ShipmentBatchWriter` stamps each readdressed Shipment with its
own flags. `ValidationQualityReport` (`app/Services/Validation/`) builds the two
cross-tabs in chunks of 500 Shipments. `address-validation:report` prints them as tables,
or as JSON with `generated_at`, the range and `final_after_days`. `--since` and `--until`
take `YYYY-MM-DD` and filter on the first Label's purchase. Tests:
`tests/Feature/ValidationQualityReportTest.php`, plus part flags in
`tests/Feature/ShipmentImportServiceTest.php`.

The outcome order differs from the first draft: `delivered` is checked before
`exception`. A delivered Package's status is `delivered`, so the two can't both hold for
one Package, and `exception` only counts once the outcome is final. The data point is the
latest live answer whether or not it settled, so `unverified` results are included.

`shipments:archive` deletes archived Shipments, and their answers go with them. Run the
report before archiving a period you want to keep measuring.

**2026-10-07 — review fixes.** A Package with a `delivered` status counts as delivered
without `delivered_at`: Shopify can report delivery with no time and then stops polling,
which would have left it `pending` for good. `ShadowValidateAddress` now copies the four
part flags along with `address_changed_at` when an edit lands during its FedEx request.
The flag list lives in `AddressValidationAnswer::CHANGED_PARTS`.
