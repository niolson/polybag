# Normalize scanned references per connection

Status: wontfix
Category: enhancement
Created: 2026-09-30

## Parent

[pack-slips PRD](../PRD.md) (Out of Scope)

## Problem

Scan & Pack opens a Shipment by an exact match (after trimming whitespace) on
`shipment_reference`. An ERP-printed pack slip whose barcode differs slightly from the
imported reference will not match. For example:

- zero-padding: barcode `00012345`, reference `12345`
- a prefix or suffix: `SH12345`
- a trailing check digit
- a difference in case

The ERP workflow this was designed around encodes the ERP's shipment primary key
exactly, so it needs none of this.

## Direction, if needed

A normalization rule on the connection (for example strip leading zeros, or a regex
capture), applied to the scan before the exact match, for Shipments from that connection
only. It should not be global: a global rule could break other channels' references,
such as Shopify's `#1247`.

## Needs

A real tenant's ERP barcode alongside the reference its connection imports.

## Blocked by

None - can start immediately once the information arrives.

## Comments

### 2026-10-04 — wontfix

Closed without building. Scan & Pack already opens a Shipment when the scanned barcode
equals its `shipment_reference`, and an ERP that prints its own pack slips will almost
always encode the same value it exports as the reference. An ERP that keeps a reference
but prints it with a prefix, padding or a check digit is expected to be rare, and the
Setup Wizard's Shipment Reference note (`07`) already tells the tenant to import the
value their slip's barcode carries. Reopen if a real tenant's barcode cannot be made to
match that way.
