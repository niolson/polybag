# Connection onboarding: one mode, the right fields, and straight into OAuth

Status: reference

Repo: `polybag`

> *This was generated by AI during triage.*

Opened 2026-10-16.

## Why

A new Shopify or Amazon connection, or a new USPS, UPS or FedEx account, cannot be
connected until it has been saved. The Connect action exists only on the edit page, and
the create form says so for Amazon alone ("Save the connection, then use Connect
Amazon."). Shopify says nothing. An operator fills the form, looks for a Connect button,
and does not find one.

The forms also show credential fields that the install cannot use. A hosted tenant in
production sees FedEx sandbox API keys, and Shopify and Amazon app credentials that only
matter without our OAuth broker. What the app does in each environment is decided in
several places (`app()->isProduction()`, `SettingsService::isDemoMode()`,
`environment('local', 'testing')`), so "what should this field do here" has no single
answer to read.

The goal: **an operator who creates a connection or carrier account goes straight
through its sign-in and lands back on the new record, seeing only the fields that
apply to this install.**

## Three modes

| | production | demo | dev |
|---|---|---|---|
| `APP_ENV` | `production`, or any value not listed | `demo` | `local`, `testing` |
| Carrier sandbox | always off | always on | Dev Settings toggle |
| Dev Settings page | not reachable | not reachable | available |
| Multi-client / multi-location | `.env` | `.env` | `.env` |
| Shopify and Amazon connections, broker configured | OAuth only | OAuth only | every field |
| Carrier app credentials, broker configured | hidden | hidden | shown |
| Anything, no broker configured | client credentials shown | client credentials shown | shown |
| FedEx sandbox fields | hidden | shown | shown |
| FedEx production fields | shown | hidden | shown |

An unknown `APP_ENV`, such as `staging`, is Production, so a mistyped value fails closed.
A staging install that should not buy real postage or write to stores runs as `demo`.

Most of this already holds. `SettingsService::resolveSandboxMode()` forces sandbox off in
production and on in demo, and `DevSettings::canAccess()` is limited to `local` and
`testing`. What is new: multi-client and multi-location stop being toggles on Dev
Settings, credential fields follow the table, and one `AppMode` answers the mode question.

Demo uses the production rules for connections on purpose. Only its postage is sandbox:
a demo connection is signed in through OAuth like a production one. What makes that safe
against a real store is [`live-store-demo`](../live-store-demo/PRD.md).

## Decisions

1. **Multi-client and multi-location are `.env`-only, in every mode.** Turning either on
   and back off leaves rows scoped in a way the app no longer expects. A DB toggle on
   Dev Settings made that one click away.
2. **A self-hosted install without the broker keeps client credentials.** The broker
   holds our developer credentials and a self-hoster is never issued its secret, so
   without it the direct fields are the only way in (`docs/self-hosting.md`).
3. **Client credentials stay a first-class path for a carrier without OAuth.** OnTrac
   has none. A field is hidden only when the carrier's OAuth or broker path is actually
   available here, never just because the mode is production.
4. **FedEx is not an OAuth redirect.** Its registration is a multi-step wizard
   (`HasFedexRegistration`) through the broker's proxy connector. "Straight into
   sign-in" for FedEx means opening that wizard, not a redirect.

## Out of scope

- A multi-step wizard page in front of the create form. The OAuth callback already
  returns to the record's edit page (`OAuthCallbackController`), so redirecting on create
  gets the same result.
- Registering a self-hosted install with our broker.
