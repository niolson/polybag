# One app mode decides sandbox and Dev Settings

Status: ready-for-agent
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), the three-modes table and decision 1.

## Problem

Which environment the app is in is answered in several places with different
predicates:

- `SettingsService::resolveSandboxMode()`: `app()->isProduction()` → off,
  `isDemoMode()` → on, otherwise the `sandbox_mode` row.
- `SettingsService::resolveSuppressPrinting()`: off in production only.
- `SettingsService::resolveEnvOrDb()`: multi-client and multi-location come from the DB in
  `local`/`testing`, from `features.multi_*_enabled` everywhere else.
- `DevSettings::canAccess()`: `environment('local', 'testing')`.

They mostly agree, but a `staging` environment, for example, gets a DB-backed sandbox
toggle with no page to change it on. And multi-client and multi-location can be switched
on and back off from Dev Settings, which leaves rows scoped in a way the app no longer
expects.

## Desired behavior

- An `AppMode` enum, with `Production`, `Demo` and `Dev` cases, resolved from `APP_ENV`:
  `demo` → Demo, `local` and `testing` → Dev, anything else (`production`, `staging`, a
  typo) → Production. Use it wherever those
  four predicates sit today, and in `02`.
- Sandbox: Production off, Demo on, Dev the `sandbox_mode` row. Same as today.
- Suppress printing and real address validation in sandbox: Dev only, as the Dev Settings
  toggles they are.
- Dev Settings: reachable in Dev only (Admin and above, as now). Its "Mode Overrides"
  section goes.
- `multi_client_enabled` / `multi_location_enabled` always read
  `features.multi_client_enabled` / `features.multi_location_enabled`. `SettingsService`
  no longer reads those two keys from the settings table in any mode.

## Notes

- **Decided 2026-10-21:** an unknown `APP_ENV` is Production, so it fails closed. A
  staging install is not a fourth mode: it is what Demo already is (sandbox postage,
  no writes to a live store), so it runs as `demo`.
- About 17 test files turn multi-client or multi-location on through the settings table.
  They move to `config()->set('features.multi_client_enabled', true)`, or to a shared Pest
  helper if one reads better.
- A local install that relied on the Dev Settings toggles needs `MULTI_CLIENT_ENABLED` /
  `MULTI_LOCATION_ENABLED` in `.env`. Say so in the PR. There are no live tenants, so no
  migration of existing rows is needed; a stale row is simply ignored.
- The panel's "(sandbox mode)" badge (`AppPanelProvider`) is unchanged.

## Acceptance

- [ ] `AppMode::current()` returns the case for `production`, `demo`, `local`, `testing`
      and an unknown value (Production)
- [ ] Sandbox resolves per mode as above; Dev reads the row
- [ ] Dev Settings is forbidden in Production and Demo, and has no multi-client or
      multi-location toggles
- [ ] A `multi_client_enabled` row set to true is ignored in every mode; the config value
      decides
- [ ] The suite passes after the test migration
