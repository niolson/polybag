# Direct UPS rates a declared UPS packaging

Status: done — shipped 2026-09-16; direct UPS sends the Box Size's packaging code on the rate and ship bodies and stamps every rate with it, so a declared UPS Letter, Pak or Express Box rates and buys as one — proved by a sandbox purchase in a Pak

Repo: `polybag`

## Parent

[ADR-0005](../../../adr/0005-packaging-form-and-carrier-identity.md), the UPS half of
decision 3 ("UPS from the `PackagingType` it sent"). Not scheduled by the ADR's
implementation order; optional, until a customer stocks UPS packaging.

## What to build

`UpsAdapter` hard-codes `PackagingType` / `Packaging` code `02` ("Customer Supplied
Package") on both the rate body (`buildRateApiRequest()`, ~line 527) and the ship body
(~line 613), so it never offers a UPS Letter, Pak, Tube or Express Box even to a
warehouse that has them. This is the UPS twin of `05`, and simpler: UPS puts packaging on
the *request*, so there is no discarded response to reinstate — the adapter sends what
the Box Size says and stamps what it sent.

### Mapping at the request boundary

One private method, `CarrierPackaging` → UPS packaging code, used by both bodies and
nowhere else — the same shape as `03`'s FedEx mapping:

| `CarrierPackaging` | Code | Description |
|---|---|---|
| `UpsLetter` | `01` | UPS Letter |
| `UpsTube` | `03` | Tube |
| `UpsPak` | `04` | PAK |
| `UpsExpressBox` | `21` | UPS Express Box |
| `UpsExpressBoxSmall` / `Medium` / `Large` | `2a` / `2b` / `2c` | Small / Medium / Large Express Box |
| null, or any non-UPS case | `02` | Customer Supplied Package |

Confirm the codes against the vendored `upsRating.json` / `upsShipping.json` enums before
relying on this table. UPS's 10 kg and 25 kg boxes (`25` / `24`) are additions to the enum
when someone stocks them, not part of this slice.

A non-UPS carrier packaging (a USPS flat-rate box) sends `02`: UPS rates it as customer
packaging and the shared filter drops every UPS rate anyway, because they say
`shipperPackaging()`. Same comment `03` asks for on the FedEx side.

### The rate says what was sent

Every rate parsed from a response to a request that sent a UPS code carries
`exactly($package->carrierPackaging)`; a request that sent `02` yields
`shipperPackaging()` rates. `resolvePreSelectedRate()` already passes the rule's rate
through the filter (`02`) and is otherwise untouched.

### Schemas

`upsRating.json` and `upsShipping.json` are vendored UPS specs; the packaging code enum in
them is the check that a mapped value is one UPS accepts. Rate and ship tests already run
through them.

### Sandbox

UPS's sandbox rates Letter and Pak; one rate-and-buy for a declared `UpsPak`, recorded in
a comment, is the proof the adapter's body is accepted rather than merely well-formed.

### 2026-09-16 — implemented

> *This was generated by AI during triage.*

Shipped as one branch, `feat/ups-carrier-packaging`. Full suite green (2531 passed, 2
skipped); Pint and PHPStan clean.

- **`UpsAdapter`**: one private `packagingCodeFor(?CarrierPackaging): string`, an
  exhaustive match — the seven UPS cases to their codes, null and every USPS and FedEx
  case to `02`. `buildPackaging()` wraps it with the spec's description for both bodies.
  `extractRateDetails()` takes the code the request sent and stamps it on every rate as
  `metadata['packagingCode']`; the Saturday follow-up request sends and stamps the same
  code. `classifyPackaging()` reads that key: missing or `02` is `shipperPackaging()` (a
  rate quoted before this change was quoted as `02`), a mapped code is `exactly(…)` by the
  same `array_find` reverse lookup FedEx uses, and a code this adapter never sends — `24`,
  `30`, anything a browser restates — throws `UnclassifiablePackagingException`, which the
  purchase path already turns into a packaging-mismatch refusal. That is `05`'s invariant
  (never default an unknown), not `03`'s (FedEx defaults an unknown to `YOUR_PACKAGING`);
  the two adapters now disagree on this and FedEx is the one to bring in line.
- **The ship body sends the Box Size's packaging, not the rate's metadata.** FedEx sends
  `selectedRate->metadata['packagingType']` back; here the code is re-derived from
  `packageData->carrierPackaging`. The purchase re-check already guarantees the rate's
  requirement accepts the package's packaging, so the two agree whenever a label is
  bought, and the Box Size is server-side truth where the metadata is browser-restated
  (`postage-source-split/14`).
- **Tests**: a shared dataset drives the rate-body and ship-body tests for Letter, Pak,
  medium Express Box, null and a USPS box; the rate tests read
  `Saloon::mockClient()->getRecordedResponses()` for the reason `03` recorded. Plus: the
  Saturday follow-up carries the code, `exactly(UpsPak)` on every Pak rate, shipper's
  packaging for null and for a USPS box, a legacy rate, three unclassifiable codes, and
  `resolvePreSelectedRate()` keeping a Pak-quoted rate and dropping a rule's `02` rate for
  a Package in a Pak. `ShippingRateServiceTest` runs USPS, FedEx and UPS for real against
  a Pak and gets only UPS; `AmazonBuyShippingTest` gets nothing for a Pak.
- **Not done here**: UPS Letter still gets `Dimensions` on the ship body, which UPS
  documents as "not applicable" to a Letter; the sandbox did not object for a Pak and no
  Letter was bought. `24`/`25` stay out of the enum until someone stocks them.

## Sandbox rate-and-buy (added 2026-09-16)

Through the real `UpsAdapter`, sandbox (CIE). `PackageData` 15 × 12 × 1 in, 1.5 lb,
`carrierPackaging: UpsPak`, Woodinville WA 98072 to a residential address in Beverly
Hills CA 90210, services `01`, `02`, `03`, `13`.

`getRates()` returned **three** rates, every one `packagingCode = 04` and `exactly(UPS
Pak)`: `01` Next Day Air $135.73, `13` Next Day Air Saver $124.62, `02` 2nd Day Air
$54.64. The same parcel rated as the shipper's own box (`02`) returned **four** — the same
three at the same prices plus `03` Ground $17.02. UPS dropped Ground for the Pak, which
is UPS reading the code (a Pak is air-only packaging), not just tolerating a well-formed
body; the identical air prices are the sandbox's rate card, where a Pak and a 1.5 lb box
both bill at 2 lb. `PackagingFilter::keepCompatible()` for the Pak kept all three.

`createShipment()` with 2nd Day Air — label body `Packaging.Code: 04`,
`Description: PAK`, nothing else changed — succeeded: `ResponseStatus` Success, a
37 KB label, `ShipmentCharges.TotalCharges` **$50.47** against the $54.64 quote. The two
are itemised differently — the quote carries a $7.00 code-`270` charge and alert `110971`
"Your invoice may vary from the displayed reference rates"; the label a $38.53 base plus
$11.94 code-`375` — and the own-box quote for the same service was the identical $54.64,
so the gap is the sandbox's usual quote/label difference, not a packaging effect. Billing
weight 2.0 lb on both. The tracking number is the CIE placeholder `1ZXXXXXXXXXXXXXXXX`,
so there was nothing to void.
`upsShipping.json` needed no extension.
