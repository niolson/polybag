# A tracking answer for a just-voided Label is written onto the unshipped Package

Page or flow: a tracking refresh racing a void

Severity: low — cosmetic until the Package is bought again, which resets it.

Verified: plausible.

## Problem

`TrackingService::record()` (`app/Services/TrackingService.php:80`) saves the model it loaded
before the carrier call. If the Label is voided in the meantime, the save writes the dead
Label's `tracking_status` and `tracking_details` onto the now `Unshipped` Package. It does not
touch `status`. It may also notify managers of an exception.

The project-review dropped the re-ship form of this race. This form needs no re-ship.

## Scenario

1. `RefreshPackageTrackingJob` loads shipped Package P.
2. An operator voids P.
3. The carrier answers `InTransit`.

P is now `Unshipped` with a tracking status of In transit, until it is bought again.

## What to build

Write tracking with a conditional update (`status = shipped` and the same
`tracking_number`), as `recordInferredService()` does.
