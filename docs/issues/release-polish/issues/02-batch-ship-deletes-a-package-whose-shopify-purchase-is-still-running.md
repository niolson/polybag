# Batch ship deletes a Package whose Shopify purchase is still running

> *This was generated by AI during release-polish pass 4.*

Status: ready-for-agent

Pass: 4 — bug (review of label purchase and automation)

Page or flow: batch ship with a Shopify blind purchase, when a rule names it or it is the
sole eligible choice

Severity: high — a Shopify label can be paid for with no record in PolyBag, and the order
becomes eligible to be bought again.

Verified: confirmed. The test below fails at `12592f33`, and line numbers are at that
commit.

## Problem

A blind purchase has no Offer, so its recovery record lives on the Package.
`ShopifyShippingLabelService` saves `metadata.shopify_purchase_result_id` as soon as Shopify
accepts the purchase mutation, and `metadata.shopify_shipping_label_id` once a label exists
(`app/Services/ShopifyShippingLabelService.php:950-993`). When polling runs out, it keeps the
result ID on purpose, so that "the next attempt resumes it instead of buying" (`:881-884`,
resumed at `:347`). `ShopifyAdapter` turns that exception into a plain
`ShipResponse::failure()` (`app/Services/Carriers/ShopifyAdapter.php:431-438`), which
`buyPostage()` reports as a decline
(`app/Services/PackageShipping/EloquentPackageShippingWorkflow.php:616-622`).

`GenerateLabelJob::handleFailure()` keeps a Package only when
`OfferStore::hasUnresolvedPurchase()` is true (`app/Jobs/GenerateLabelJob.php:85-92`), and
that method reads Offer rows only (`app/Services/PostageSources/OfferStore.php:313-317`). So
the job deletes the Package, and the marker goes with it. The `project-review/01` fix chose
the Offer check over `leavePackageIntact` because it is more precise, and the Offer check
cannot see blind purchases.

After the delete, the Shipment has no unshipped Package and nothing shipped, so the next
batch takes it again. `ShopifyAdapter::shipmentAlreadyBoughtALabel()` looks only at the
markers of *sibling* Packages (`ShopifyAdapter.php:375-383`), so nothing stops a new
Package's purchase mutation against the same fulfillment order. Meanwhile the first purchase
completes at Shopify. The result is a paid label and a fulfillment that PolyBag never
records.

The same delete follows when Shopify sold a label but `markShipped()` then failed
(`labelNotRecorded`, with no Offer to keep). In that case the deleted Package carries
`shopify_shipping_label_id`.

## What to build

Make "a purchase may exist for this Package" one question that covers blind purchases.
Ask it in both cleanup paths: `GenerateLabelJob::handleFailure()` and
`EloquentPackageShippingWorkflow::cleanupPackage()`. Either of these would do it:

- Add a method to `BlindPurchaseSource` that Shopify answers from
  `shopify_purchase_result_id` and `shopify_shipping_label_id`. Then
  `OfferStore::hasUnresolvedPurchase()`, or a sibling service, consults it.
- Have the Shopify path set `leavePackageIntact` once Shopify has accepted a mutation, and
  make the job honor it.

The batch item should then carry the same "a label may already exist" note it gets for an
unresolved Offer. Widening `shipmentAlreadyBoughtALabel()` beyond siblings is not enough on
its own, because the deleted Package is the one holding the marker.
