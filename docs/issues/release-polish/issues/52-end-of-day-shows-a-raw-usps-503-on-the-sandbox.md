# End of Day showed a raw USPS 503 on the sandbox, which cleared by itself

> *This was generated by AI during release-polish pass 1.*

Status: wontfix

Pass: 1 — does it work? (End of Day on the USPS sandbox)

Page or flow: End of Day, Generate Manifest, USPS, with `sandbox_mode` on

Severity: was medium, because End of Day is demo step 6. Closed 2026-10-19: the 503 no
longer happens, so there is nothing to work around.

Verified: probed 2026-10-15 and again 2026-10-19 against `apis-tem.usps.com`; USPS
answered the support ticket the same day.

## What happened

Generate Manifest for USPS on the sandbox answered `USPS rejected the SCAN form request
(HTTP 503): Not found` on 2026-10-15, 2026-10-17 and the morning of 2026-10-19. (Before the
message was fixed on 2026-10-15 it said only `Syntax error`, because
`ManifestService::createUspsScanForm()` read a non-JSON error body as JSON.)

The probes, all through the app's own connector and USPS account:

- Without a token, `/scan-forms/v3/scan-form` answers 401. The endpoint exists.
- With a token, a request that matches no label is rejected normally with a JSON body:
  bad sender address `010007`, unknown barcode `160039`, unknown MID `160037`.
- A request that matched a real label answered `503`, a bare `Not found` with no JSON and
  no `Content-Type`. This held for `trackingNumbers` and for the account's `MID` alone.
- `trackingNumbers` and `MID` together is a schema error (HTTP 400): `shipment` takes
  exactly one of `trackingNumbers`, `MID` or `manifestMID`.

## What changed

USPS's API team could not reproduce it and got a successful response. Later on 2026-10-19
the same request began to work on our account too: a first label already showed as
manifested on USPS's side (`160398`), and the next two labels produced SCAN forms. The
cause was never identified, so it is best read as a test-environment problem on USPS's side
that has cleared. It was not rate limiting (the 503 followed the request's content, not its
frequency) and not the non-breaking spaces USPS pointed to, which came from pasting into the
ticket; the request body is plain ASCII.

The sandbox is therefore **not** a place where SCAN forms cannot be made, and the earlier
proposal — say "SCAN forms are not available in the USPS test environment" on a 503 — is
dropped. It would have been wrong today and hid a real error behind a guess.

## Follow-up that did come out of it

The endpoint honors `X-Idempotency-Key`. On the sandbox a second request under the same key
returned a form for barcodes that a request under a new key refused as already on another
SCAN form. `ManifestService` now stores the key before sending (`scan_form_requests`) and
reuses it for the same date and set of tracking numbers, so End of Day can be repeated after a
reply that never arrived (PR 460).

Not tested: how long USPS remembers a key, and whether the replayed form is the same form
(same manifest number) as the first.

## If it comes back

Send USPS the tracking number, the time, and the `Akamai-GRN` and `x-request-id` response
headers; they can find the request from those. Production has never been run against this
endpoint at volume, so a recurrence there is a different question from this one.
