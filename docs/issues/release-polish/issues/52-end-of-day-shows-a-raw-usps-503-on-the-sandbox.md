# End of Day shows a raw USPS 503 on the sandbox, where SCAN forms cannot be made

> *This was generated by AI during release-polish pass 1.*

Status: needs-triage

Pass: 1 — does it work? (End of Day on the USPS sandbox)

Page or flow: End of Day, Generate Manifest, USPS, with `sandbox_mode` on

Severity: medium — End of Day is demo step 6. On the sandbox it fails, and the message
does not say that the sandbox is the reason.

Verified: probed 2026-10-15 against `apis-tem.usps.com`. That USPS's test environment is
the cause is the best reading of the probes, not something USPS has confirmed.

## Problem

Generate Manifest for USPS on the sandbox answers `USPS rejected the SCAN form request
(HTTP 503): Not found`. (Before the message was fixed on 2026-10-15 it said only `Syntax
error`, because `ManifestService::createUspsScanForm()` read a non-JSON error body as JSON.)

The probes, all from this machine through the app's own connector and USPS account:

- Without a token, `/scan-forms/v3/scan-form` answers 401 on both `apis-tem.usps.com` and
  `apis.usps.com`, like the rates and labels endpoints. The endpoint exists.
- With a token, a request that cannot match any label is rejected normally: a bad sender
  address gets `010007`, an unknown barcode gets `160039`, an unknown MID gets `160037`
  (no labels met the criteria).
- A request that does match real labels answers `503`, an empty-looking `Not found` of
  three bytes. This holds for a list of tracking numbers and for the account's `MID`
  alone, and the MID form covers every label of the day, including ones bought hours
  earlier, so it is not labels that are too new for USPS to find.

So the test environment validates a SCAN form request and then fails to build the form.
The tracking endpoint does the same (`503 Not found`, see the USPS tracking notes), so
this is probably the same kind of test-environment gap. A production account should not be
affected, but no one has run it there.

## Proposed direction

- On the sandbox, say so. When `sandbox_mode` is on and USPS answers the SCAN form request
  with a 503, the page should read something like "SCAN forms are not available in the USPS
  test environment", not the raw status and body.
- Do not hide real 503s in production. The explanation applies only to the sandbox.
- For the demo, show End of Day on the fake-carrier instance, which makes a sample SCAN
  form (`01`). The sandbox instance skips step 6.

## Not part of this fix

The `shipment` object of the SCAN form request takes exactly one of three shapes, which
USPS's schema check enforces with `oneOf`: `trackingNumbers`, `MID` alone, or `manifestMID`
alone. PolyBag always sends `trackingNumbers`. A MID request builds the form from every
label under that MID for the mailing date and entry ZIP, so it needs no barcode list. That
could matter for a customer with thousands of labels in a day, since a barcode list that
long is a heavy request, but it is a feature and does not fix this.

## Acceptance

- Generate Manifest on the USPS sandbox says that SCAN forms are not available in the test
  environment, in place of the HTTP 503 text.
- The same 503 outside the sandbox still shows the status and the start of the body.
- A test covers both.
