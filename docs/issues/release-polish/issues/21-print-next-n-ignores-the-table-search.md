# "Print next N" ignores the table search the page shows

> *This was generated by AI during release-polish pass 4.*

Status: ready-for-agent

Pass: 4 — bug (review of pack slips and pick-batch printing)

Page or flow: Print Pack Slips, Not printed tab

Severity: low — the operator sees one list and prints another, but only with a search typed

Verified: plausible. Line numbers are at `12592f33`; this area is unchanged on `dfd842c5`.

## Problem

The Reference column is `->searchable()`
(`app/Filament/Pages/PrintPackSlips.php:125`), and Filament applies the search to the
table. "Print next N" builds its run from `PackSlipQueue::next()` with
`queueFilters()` only (`:229-231`, `:282-293`), which reads the three select filters and
not the search. The class comment says the queue applies the filters "so the table and
'Print next N' read the same state"; the search breaks that.

## Evidence

Scenario: 30 Shipments waiting, batch size 25. Type one order's reference
into the search; the table shows that one row. Click "Print next 25": 25 slips print, the
top 25 of the unsearched queue, and the searched order is among them only if it is urgent
enough.

## What to build

Either pass the search term into `PackSlipQueueFilters` and apply it
in `inStates()`, or hide/disable "Print next N" while a search is active and point the
user at Print selected. Product call; the second is smaller.
