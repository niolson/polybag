# Batch jobs are queued before the batch's transaction commits

> *This was generated by AI during release-polish pass 4.*

Status: done — 2026-10-14

Pass: 4 — bug (review of label purchase and automation)

Page or flow: batch ship

Severity: low — a rare race. A Shipment silently gets no label and the batch never finishes,
but nothing is bought twice.

Verified: plausible. Line numbers are at `12592f33`.

## Problem

`BatchLabelService::createBatch()` dispatches `Bus::batch($jobs)` inside its
`DB::transaction()` (`app/Services/BatchLabelService.php:166-234`). The `redis` queue
connection has `after_commit => false` (`config/queue.php:68-73`). So each job is pushed to
Redis before the `label_batches`, `label_batch_items` and `job_batches` rows commit, and
before `bus_batch_id` and the audit row are written.

## Scenario

1. A batch request is between `dispatch()` and its commit.
2. The `queue` worker finishes another job, such as a second batch, and pops the new batch's
   first job.
3. `$this->batch()` finds no `job_batches` row, and `LabelBatchItem::find()` returns null
   (`app/Jobs/GenerateLabelJob.php:36-44`). The job returns having done nothing.
4. With no batch visible, the worker records no success on the bus batch either. Its
   pending count never reaches zero, so the `finally` callback never runs.

The batch stays *Processing* and the item stays *Pending*. The draft Package keeps the
Shipment out of later batches as "Has existing unshipped packages".

## What to build

Dispatch after the commit. Any of these works:

- call `->dispatch()` outside the transaction
- wrap the dispatch in `DB::afterCommit()`
- set `after_commit => true` on the queue connection
