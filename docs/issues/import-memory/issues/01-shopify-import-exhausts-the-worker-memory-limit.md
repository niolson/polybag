# A Shopify import of a real store exhausts the import worker's memory

Status: needs-triage
Category: bug
Created: 2026-10-23

## Problem

The first import of a real Shopify store, on a hosted demo tenant on 2026-10-23,
died with a PHP fatal error:

```
Allowed memory size of 134217728 bytes exhausted (tried to allocate 2097152 bytes)
at vendor/saloonphp/saloon/src/Http/Response.php:211
```

The import worker runs `queue:work` with PHP's default `memory_limit` of 128M. Nothing
in the Dockerfile, the entrypoint or `docker-compose.yml` raises it. A fatal error is
not an exception, so neither the job's `maxExceptions` nor the `catch` around
`fetchShipments()` in `ShipmentImportService::import()` sees it. It struck during the
fetch, before `ImportRunRecorder::started()`, so no import run is recorded and no admin
is notified: the worker process dies, Docker restarts it, and the only trace is the
container log.

This is not demo-specific. Any tenant connecting a store with enough open fulfillment
orders will hit it, on the first run and on every daily full read after it.

## Why it runs out

`ShopifySource::fetchFulfillmentOrderShipments()` reads every open fulfillment order,
250 to a page, and appends each page's rows to one array before returning the
collection. Each page asks for up to 40 line items per fulfillment order, with
barcodes and the part-number metafield, so a single decoded page is several megabytes
of PHP arrays. And every fulfillment order is held twice: `importedRow()` keeps the
mapped row, and also stores the whole raw node, with all its line items, in
`orderCache` for `fetchShipmentItems()`. So the store's entire open book sits in
memory twice over, beside the decoded `json()` of the page being read. Peak memory
grows with the size of the store, and the limit is a fixed 128M.

`ShipmentImportService::import()` then needs the whole set: it chunks the writes into
batches, but `reconcileSupersededRecords()` and `closeRecordsClosedAtSource()` run
against everything fetched ("Run against the whole fetched set, never a chunk"). So
streaming pages straight to the writer is not a drop-in fix.

## A second effect: "Run import now" silently waits for half an hour

`RunDataSourceImportJob` takes a `WithoutOverlapping` lock that expires after
`$timeout + 60` seconds (31 minutes) and releases a blocked job after 60. When the
worker dies holding the lock, nothing releases it. Every import of that connection,
scheduled or from "Run import now", is released back to the queue once a minute until
the lock expires. The UI shows the import as queued and nothing happens, with no
message saying why. When the lock expires the next attempt runs into the same memory
limit, and the cycle repeats.

## Options

Not decided; for triage.

1. **Raise the worker's limit.** `php -d memory_limit=…` in the `import-queue`
   entrypoint, or an ini file in the image. Quick, and buys headroom, but the peak
   still grows with the store and the hosted servers are small. It needs a number
   chosen against the largest store we expect.
2. **Hold less per fulfillment order.** Keep only what `fetchShipmentItems()` needs
   in `orderCache` rather than the raw node, or derive the items from the mapped row,
   and drop the decoded page before fetching the next. Probably the cheapest real
   gain. Lowers the slope rather than removing it.
3. **Two passes.** Fetch IDs (and whatever reconciliation and closure need) for the
   whole set cheaply, then fetch and write the full rows a page at a time. Removes the
   dependence on store size, at the cost of more requests against Shopify's query
   budget.

Whichever is chosen, the stale lock should stop being silent: either catch the case
where the lock is held past a normal run and say so in the UI, or shorten the expiry.

## Acceptance

- An import of a store with several thousand open fulfillment orders completes under
  the worker's configured limit, with peak memory measured and recorded here.
- A worker that dies mid-import does not leave "Run import now" silently queued for
  half an hour.

## Notes

- Seen on the first full read of a newly connected store. How many open fulfillment
  orders it had is not known; the import never finished.
- The hosted instance worked around it for that one tenant by running the import
  worker with `-d memory_limit=512M`. That is a stopgap for a demo, not a fix.
