# Concurrent packers share five php-fpm workers

Status: needs-triage
Category: performance
Created: 2026-10-24

## Problem

The `app` image runs php-fpm with the image's default pool: `pm = dynamic`,
`pm.max_children = 5`. The `Dockerfile` writes `zz-docker.conf` with only `listen` and
`daemonize`, so nothing overrides it. One instance serves at most five PHP requests at
once, and the next request waits in the listen backlog.

Every Livewire round trip counts toward those five: a scan on Pack, a scale reading
written to the page, a table filter. Rate shopping on Ship and a label purchase hold
a worker until the carriers answer, which takes seconds. So a handful of people
packing at once can hold all five, and everyone's scans stall. To them, the app just
looks slow.

## To measure

- Wall time of the requests that hold a worker longest: rate shopping across every
  eligible source, label purchase per carrier, a Pack scan, Batch Ship's start.
- Peak memory per request for the same, to size `pm.max_children` against the
  container's memory: workers × peak must fit.
- A load test with N simulated packers looping scan → rate → buy against fake
  carriers with realistic latency (`FAKE_CARRIERS=true`, plus a configurable delay
  if the fakes have none). Record p50/p95 latency of a scan as N goes from 1 to 20.

## Options

1. Set the pool explicitly in the image, for example `pm.max_children` from an env
   var with a default chosen from the measurements. The default matters most for
   on-prem installs, which never tune it.
2. Shorten what holds a worker. Rate shopping already quotes concurrently inside one
   request; check that nothing on Pack waits on a carrier.

## Acceptance

- Scan latency is measured for 1, 5, 10 and 20 concurrent packers, and recorded here.
- The php-fpm pool size is set on purpose in the image, documented in
  `docs/self-hosting.md`, and holds a stated number of concurrent packers within the
  container's memory.
