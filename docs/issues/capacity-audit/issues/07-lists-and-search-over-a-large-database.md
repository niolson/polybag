# Lists and search over a large database

Status: done
Category: performance
Created: 2026-10-26

## Problem

Every other workload in the audit grows with one request or job. This one grows with the
database: the Shipments, Packages and Products lists, their search, the dashboard and the
reports. Nothing had measured them above a few thousand rows, and they hold the data of
every order a tenant has shipped.

## Measured

Docker image (standalone profile, 128M `memory_limit`, `LOG_REQUEST_TIMING=true`), MySQL
8.4 with encryption at rest on a workstation disk. Seeded in bulk with SQL
(`.scratch/capacity-audit/07/bigseed.sql`): 200,000 Shipments (10,000 open, 186,000 shipped,
4,000 cancelled, over about 700 days) with 400,000 items, 186,000 Packages and Labels with
372,000 package items, and 20,000 Products. Package `label_data` (about 15 KB) is kept on
the last 90 days' 26,000 Packages, as the PII purge leaves it. A browser drove the pages
(`bigtable.mjs`); the times are the server's, from the request-timing log.

| Page or search | Server time | Peak memory |
|---|---|---|
| Shipments list, first page | 0.6-1.2 s | 10-12 MB |
| Shipments, page 6,000 / filter open / sort | 0.3 s | 6-10 MB |
| Shipments search, one match (a last name) | **3.3 s** | 4 MB |
| Shipments search, an email | 1.5 s | 4 MB |
| Shipments search, a city (25,000 matches) | 0.2 s | 6 MB |
| Packages list, first page | **11.7 s** before the index, 0.7 s after | 10 MB |
| Packages search (tracking number, carrier) | 1.4-1.8 s | 4-8 MB |
| Products list; search (20,000 Products) | 0.4 s; 1.4 s | 4-6 MB |
| Print Pack Slips list | 0.3 s | 6 MB |
| Dashboard (all widgets) | 0.4 s over 6 requests | 6 MB |
| Pick batch page, End of Day, Batch Shipments, Audit Log | 0.1-0.6 s | 4-6 MB |
| Rate Comparison, Packing Validation, Client Billing | 0.05-0.6 s | 4-6 MB |
| Prepaid Duties report | **1.9 s** before the index, 0.2 s after | 6 MB |
| Global search (per keystroke, three resources) | 1.5-1.9 s | 6 MB |

Memory is not the constraint: no page above 12 MB, against the 128M limit. Time is, in two
shapes.

**An unindexed sort.** The Packages list sorts by `created_at` and nothing indexed it, so
MySQL read all 186,000 Packages with their `label_data` and sorted them to show 25. The
list took 11.7 s; with an index on `created_at` the same query takes 1.4 ms. The Prepaid
Duties report sorts by `package_labels.ship_date`, also unindexed, and dropped from 1.9 s to
0.2 s. Every other list's default sort was already indexed.

**Search that scans.** Shipments search matches `%term%` against eight columns, a leading
wildcard no index serves, so a search that matches few rows reads all of them: 3.3 s at
200,000 Shipments. It grows linearly: about 16 s at a million, well past what a packer waits for
and approaching nginx's 60 s limit. Packages and Products search, which go through Scout's
collection engine, cost 1.4-1.8 s at 186,000 and 20,000 rows, and global search runs all
three on every keystroke after Filament's debounce. A search for a city is fast only
because 25,000 matches fill the first page quickly.

## Built

- A migration indexing `packages.created_at` and `package_labels.ship_date`, and a test
  that both exist. The Packages list, the one outright failure, is 11.7 s to 0.7 s.
- Not changed: Shipments, Packages and Products search. Making it use an index means
  changing what a search matches (prefix on references and tracking numbers, or a
  `FULLTEXT` index and a different match rule), which is a product decision, not a fix.
  The options and what each costs are below.
- Dashboard and reports are fine at this size: the dashboard reads `daily_shipping_stats`
  (1,941 rows, rebuilt in 12 s for 800 days).

## Options for search, if it needs to scale

1. **Prefix matching for the columns people type exactly** (reference, tracking number,
   email): uses the existing indexes, instant at any size, but no longer finds a term in
   the middle of a value.
2. **`FULLTEXT` index** on the searchable columns and `MATCH ... AGAINST`: finds words
   anywhere, scales to millions, but matches whole words or prefixes of them, not
   substrings.
3. **Leave it** and cap the damage: at 200,000 Shipments a search is 3 s, which a packer
   waits through. It becomes a problem past a million.

## Not covered

- **Data volume beyond 200,000 Shipments.** The linear estimates above were not run.
- **A tenant with many Clients, Locations and Channels**, where the filters and the
  dashboard's per-client widgets do more.
- **Concurrent use.** One browser, one request at a time. Several people searching at once
  would hold several php-fpm workers for the 1-3 seconds each takes.
- **Hosted numbers.** The disk here is slow for commits, not for reads, so the read-heavy
  times above should hold or improve on hosted.
