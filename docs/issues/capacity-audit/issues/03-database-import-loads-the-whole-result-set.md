# The database import loads its whole result set

Status: needs-triage
Category: performance
Created: 2026-10-24

## Problem

`DatabaseSource::fetchShipments()` runs the connection's shipment query with
`DB::connection(...)->select($query)`. That returns every row as an array, and
`collect()->map()` then copies each row into a mapped one. For a table-based source,
`shipmentsTableQuery()->get()` does the same. Peak memory is the whole result set
twice over.

How big that set gets depends on the customer's query. A query that returns only
open orders stays small. One that forgets a status filter returns the whole order
history, and the run dies of a fatal error with no message (see
[`import-memory/02`](../../archive/import-memory/issues/02-a-queued-job-that-dies-says-so.md)).

The preview already reads lazily and stops at a limit (`takeRows()` over `cursor()`),
and its docblock notes that `pdo_mysql` buffers by default.

## To measure

Peak memory of a fetch against SQLite and MySQL source tables of 1,000, 10,000 and
100,000 rows with a typical column set.

## Options

1. Map rows as they are read, from an unbuffered cursor, so only the mapped row is
   held. This halves the slope but does not remove it.
2. Move to the paged-source interface from `import-memory/01`. A database source
   with a status query closes Shipments at source (`order-reconciliation/08`) and
   needs only identities for that.
3. A row cap per run, enforced with a message, as a guard against a query that
   returns the whole history: "Your shipment query returned more than N rows".

## Acceptance

- Memory per 1,000 rows is measured and recorded here.
- A query returning more rows than a run can hold fails with a message on the
  Connection, never with a silent fatal.
