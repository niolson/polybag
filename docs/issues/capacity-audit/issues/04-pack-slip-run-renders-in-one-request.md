# A pack slip run renders every PDF in one web request

Status: needs-triage
Category: performance
Created: 2026-10-24

## Problem

Print Pack Slips allows up to 1,000 slips in one run (`maxSelectableRecords(1000)` and
`maxValue(1000)`). `PackSlipRenderer::printJobs()` splits the run into print jobs of
`SLIPS_PER_PRINT_JOB` (200) and renders each one through Gotenberg, one after another,
inside the Livewire request. `PrintPackSlips::print()` then sends every job's PDF to
the browser in one `print-pack-slips` event, base64 encoded.

So a 1,000-slip run:

- holds a php-fpm worker for five Gotenberg renders in a row (and see
  [01](01-concurrent-packers-share-five-php-workers.md));
- holds all five PDFs in memory at once, then again as base64 (a third larger), then
  again in the JSON response, all under the 128M web limit;
- has to finish within the request timeouts of nginx and php-fpm.

None of this has been measured. 1,000 may work fine, or it may already fail.

## To measure

For runs of 50, 200, 500 and 1,000 slips, with realistic items per slip and client
branding images:

- the size of each 200-slip PDF;
- peak memory of the request;
- wall time end to end;
- whether the browser and QZ Tray accept the payload.

## Options

1. Lower the cap to what measures safe, with a message.
2. Render each print job separately: the browser asks for job 2 after job 1 is sent.
   That holds one PDF at a time and keeps each request short.
3. Render on the queue and hand the browser a URL for each job.

## Acceptance

- Memory, time and PDF size are measured for each run size and recorded here.
- The largest run the UI allows completes within the web memory limit and the request
  timeouts, with a stated margin.
