# Import product identifiers from Shopify and Amazon

Status: reference

Repo: `polybag`

Background for the issues in this directory. Not a work item.

> *This was generated by AI during triage.*

## Where this came from

[`eu-product-identifiers`](../archive/eu-product-identifiers/PRD.md) added
`products.manufacturer_part_number` and `products.gtin`, sends them to FedEx and UPS, and
refuses a label into the EU to a consumer when any line lacks a SKU or a manufacturer part
number. Its `01` left one thing out on purpose: *"Pulling a part number from the Amazon
catalog … or from a Shopify variant metafield — a follow-up once a client asks."*

This is that follow-up, investigated 2026-10-05. EU customs starts holding parcels on
**1 November 2026**. Without it, a client importing from Shopify or Amazon has to type a
part number into every product by hand before their first EU consumer label.

## What each identifier needs

| Identifier | Product column | Shopify today | Amazon today | Database today |
|---|---|---|---|---|
| M-PID (seller SKU) | `sku` | Imported | Imported (`sellerSku`) | Imported |
| NS-PID (manufacturer part number) | `manufacturer_part_number` | **Not imported** | **Not imported** | Mappable |
| S-PID (GTIN) | `gtin`, else `barcode` | Covered: `variant.barcode` goes to `barcode`, and `CustomsItem` uses it when it passes `App\Support\Gtin` | Covered the same way: the catalog lookup fills `barcode` | Mappable |

The part number is the only real gap. The GTIN needs no new work.

[international-customs-terms/05](../international-customs-terms/issues/05-customs-readiness-checker.md)
adds two more blocks at purchase: a line with no country of origin (every international
label) and a line with no HS code (EU and GB). Shopify already holds both on the inventory
item, and the Shopify import does not read them either, so this directory imports them in
the same query.

## Shopify

Shopify has no part-number field. Merchants keep it in a metafield, on the variant or the
product, under whatever namespace and key their store or a channel app chose. One store
might use `custom.mpn` and another a Google channel app's variant metafield.

- **The connection says which metafield.** A new connection setting holds the owner
  (variant or product) and the `namespace.key`.
- **Choosing it from a list.** The Admin GraphQL `metafieldDefinitions(ownerType:)` query
  lists every *defined* metafield. A metafield written by an app without a definition does
  not appear there. So the picker also samples recent variants' `metafields` to find
  undefined ones, and accepts a typed `namespace.key`.
- **Reading it.** `variant { metafield(namespace:, key:) { jsonValue } }`, and
  `product { metafield(...) }` for a product-owned one, added to both fulfillment-order
  line-item queries, with namespace and key passed as GraphQL variables. A list-typed
  metafield yields its first entry.
- **HS code and origin** come from `variant.inventoryItem { harmonizedSystemCode
  countryCodeOfOrigin }`.
- **The import already overwrites product fields.** `ImportReferenceResolver::productIdFor()`
  writes every non-null imported value over the Product. Shopify is the merchant's own
  record, so its value wins when it has one, and an empty metafield leaves a hand-entered
  value alone.

### Access scope

`ProductVariant`, `Product` and `InventoryItem` all require `read_products`
(`InventoryItem` accepts `read_inventory` instead). `ShopifyFulfillmentOrderActivationService::REQUIRED_SCOPES`
does not include it, and `docs/self-hosting.md` lists it only for buying Shopify Shipping
labels.

The import already reads `variant { id barcode }`. On a store whose app never declared
`read_products`, those barcodes may be arriving null without any error. That has not
been tested and is the first thing [`02`](issues/02-require-read-products-for-shopify-imports.md)
answers.

## Amazon

Orders carry no part number. Two SP-API sources do, and which one a connection can use
depends on how it was connected.

**The seller's own listing (Listings Items `2021-08-01`).** `searchListingsItems` at
`/listings/2021-08-01/items/{sellerId}` takes up to 20 SKUs per call
(`identifiersType=SKU`) and, with `includedData=attributes`, returns the attributes the
seller submitted. `part_number` and `model_number` are the candidates, and
`country_of_origin` comes back alongside them. This is the better source: it is the
seller's data, and it is keyed by SKU, as Products are. Its rate is 5 requests per second.

It needs the seller ID, and **OAuth connections already have it.**
`OAuthService::handleCallback()` stores the broker's `selling_partner_id` as
`settings.amazon_selling_partner_id` and refuses to finish the connection without one.
A **manual connection**, a refresh token typed into the form on a self-hosted install
without our broker, has no seller ID. `/sellers/v1/account` does not return one.

**The catalog (Catalog Items `2022-04-01`).** `ItemSummaryByMarketplace` has
`partNumber`, `modelNumber` and `manufacturer` under `includedData=summaries`. This is
Amazon's merged record for the ASIN, not the seller's. `AmazonSource` already calls this
endpoint during every import (`includedData=identifiers`, for ASINs with a SKU that has
no barcode), so asking for `identifiers,summaries` costs no extra requests.

So:

- **Every connection** gets the catalog part number from the call it already makes
  ([`05`](issues/05-amazon-catalog-part-numbers.md)).
- **A connection with a seller ID** asks its own listings first and uses the catalog only
  for SKUs the listing has no part number for
  ([`06`](issues/06-amazon-listing-part-numbers.md)). A manual connection can get there
  by entering its seller ID (the *Merchant Token* in Seller Central) in an optional
  field.
- **Fill only, from both.** The import looks up only Products missing a value, so an
  Amazon value never replaces one someone typed. The barcode already works this way
  through a one-off `_fill_missing_barcode_only` flag, which
  [`01`](issues/01-fill-only-import-fields.md) generalizes. One consequence: a part
  number later corrected in Seller Central does not reach a Product that already has one.
- **No repeat lookups.** A SKU with no part number anywhere would be looked up on every
  import. `products.identifiers_checked_at` records that Amazon was asked.

## What does not change

- **Re-imports.** `ShopifyGoodsFingerprint` hashes SKU quantities, so new fields leave it
  alone. `source_checksum` covers the item rows, so every open Shipment's checksum changes
  once after this ships. Under `on_existing: update_if_changed` each is rewritten once;
  under `skip` none are, but the Product is shared by SKU and the next order for it brings
  the value.
- **Products not on any open order** get a part number only when next ordered. A product
  only needs one to ship, so no backfill command.
- **The Database driver** already maps all four fields.

## Out of scope

- A bulk product editor or CSV product import. Still the fallback for clients whose
  sources hold no part number, but a separate issue when a client asks
- Writing a part number back to Shopify or Amazon
- USPS product identifiers, which wait on USPS publishing a field (see
  `international-customs-terms`)
