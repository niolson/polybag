# Import part numbers and origin from the seller's Amazon listings

Status: wontfix
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), *Amazon*. Blocked by `05`, whose lookup set, fill-only rule and
`identifiers_checked_at` this reuses.

## Problem

The catalog's `partNumber` (`05`) is Amazon's merged record for the ASIN, and may be
another seller's contribution, or empty. The seller's own listing holds the part number and
country of origin they submitted, keyed by their SKU. Reading it needs the seller ID, which
every OAuth connection already stores as `settings.amazon_selling_partner_id`
(`OAuthService::handleCallback()`). A manual connection has none.

## Desired behavior

**Seller ID.** `AmazonSource` uses `settings.amazon_selling_partner_id` when set. A
manual connection gets an optional *Seller ID* field (helper: "Your Merchant Token, under
Settings → Account Info → Business Information in Seller Central. Lets PolyBag read part
numbers from your own listings.") in *Amazon SP-API Connection*, shown only when the
connection is not OAuth (`auth_mode` is not `authorization_code`). It saves to the same
`amazon_selling_partner_id` key, so `AmazonSource` reads one place. An OAuth connection's
value comes only from the callback and is never editable.

**Request.** A new Saloon request, `SearchListingsItems`, for
`GET /listings/2021-08-01/items/{sellerId}` with `marketplaceIds`,
`identifiersType=SKU`, `identifiers` (at most 20, comma-separated),
`includedData=attributes` and `pageSize=20`. `pageSize` defaults to 10 (maximum 20), so
without it a full batch returns only half its listings and the rest silently fall back to
the catalog. If a response still carries `pagination.nextToken`, the next page is fetched
with `pageToken` until none remains. It is paced and retried by the same rate-limit
handling as the catalog request, generalized from `sendCatalogRequest()` rather than
copied.

**Lookup set.** `05`'s set, plus, when there is a seller ID, SKUs whose Product has no
`country_of_origin`: [international-customs-terms/05](../../international-customs-terms/issues/05-customs-readiness-checker.md)
will refuse any international label without one.

**Order of lookup:**

1. With a seller ID: listings for those SKUs. From the attributes for the order's
   marketplace: `part_number`, else `model_number`; and `country_of_origin`.
2. The catalog, as in `05`, for the barcode, and for the part number of any SKU the
   listing gave none.
3. Without a seller ID: step 2 only, exactly as `05`.

Attribute values are lists of `{value, marketplace_id}`. Take the entry for the order's
marketplace, else the first. Part numbers are trimmed and cut to 100 characters. Origins
are kept only when they are an ISO-3166 alpha-2 code. All three fields are `_fill_only`.

**Failure.** If the listings call fails (HTTP error, 429 after retries, or 403 because the
app lacks the Product Listing role), log a warning naming the reason and fall back to the
catalog for that chunk. The import never fails over it. A 403 is logged once per run, not
per chunk.

## Acceptance criteria

- [ ] An OAuth connection asks listings first; a SKU whose listing has `part_number` gets
      it, one with only `model_number` gets that, one with neither falls back to the catalog
- [ ] `country_of_origin` fills a blank origin and leaves a set one alone; a value that is
      not a two-letter code is ignored; a Product with a part number but no origin is
      looked up when there is a seller ID
- [ ] A manual connection without a seller ID sends no listings request; with one entered,
      it does
- [ ] The form shows *Seller ID* only on a manual connection, and saving the form does not
      change an OAuth connection's stored ID
- [ ] 25 SKUs make two listings requests (20 + 5), each sending `pageSize=20`, and all 20
      listings in the first response are applied to their Products, not just the first 10
- [ ] A response with `pagination.nextToken` is followed with `pageToken`, and the second
      page's listings are applied
- [ ] A 403 on listings falls back to the catalog and logs once
- [ ] Fixtures use synthetic seller IDs and SKUs

## Comments

**2026-10-05 — wontfix.** A production probe answered the question this issue assumed.
`searchListingsItems` with `includedData=attributes` works on an OAuth connection: 33
calls, all 200, so the app has the role. But none of the 617 listings returned had
`part_number`, `model_number` or `country_of_origin`. The attributes did come back, 41
names in all (`brand`, `manufacturer`, `item_weight`, `externally_assigned_product_identifier`
and so on), so the empty result is real, not a request error. That is what offers on
existing catalog pages look like: a reseller submits offer data, not product data, even
though every product type's schema marks `country_of_origin` as required.

The catalog had a part number for 98% of the same seller's ASINs (`05`), and the GTIN
fallback (`09`) covers most of the rest. A new request type, a Seller ID field and a
second rate-limited loop would add nothing for a reseller. Reopen this if a brand-owner
client, whose own listings define the ASIN, needs origin from Amazon. The catalog
record carried no `country_of_origin` either.
