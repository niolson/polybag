# Verify against a development store and a seller account

Status: done
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md). Blocked by `04`, `05` and `06`.

## Problem

`03`–`06` are built against the Admin GraphQL schema and the SP-API models, with mocked
responses. Neither source has been seen returning these fields to PolyBag. The SP-API
sandbox catalog returns nothing at all.

## Desired behavior

**Shopify, on a development store:**

1. Install a Google channel app (or any app that writes a part number), set one on a
   variant, and confirm whether its metafield has a definition. That decides whether
   `03`'s variant sampling earns its place.
2. Set a part number, an HS code and an origin on a variant, choose the metafield on the
   connection, import an order for it, and confirm all three land on the Product.

**Amazon, on a production seller account** (read-only, no label purchase), through an
OAuth connection:

3. Confirm the app's role set allows `searchListingsItems`. A 403 here means the Product
   Listing role is missing, and `06` silently falls back to the catalog.
4. Import orders and record, for the SKUs looked up, how many listings carried
   `part_number`, how many only `model_number`, how many `country_of_origin`, and, for the
   rest, how many catalog summaries carried `partNumber` or `modelNumber`. Counts only;
   no ASINs or SKUs in this file.
5. Confirm the attribute names: `part_number`, `model_number` and `country_of_origin` are
   per product type, and a seller whose product types name them differently gets nothing
   from `06`.

## Acceptance criteria

- [x] Steps 1–5 recorded under `## Comments`, with no store names, ASINs or SKUs
      (step 1 not run; see the closing comment)
- [x] Any mismatch with `03`–`06` fixed or opened as a new issue

## Comments

**2026-10-05 — Amazon steps 3–5 answered early**, by a read-only production probe run
before `05` was built. It used one seller's OAuth connection: 653 ASINs from its orders
(health, beauty and grocery), plus 600 more from a catalog keyword search across about 25
display groups. Raw responses stayed out of the repo.

3. **Listings role:** granted. All 33 `searchListingsItems` calls returned 200.
4. **Counts:**
   - **Listings:** 617 returned, none with `part_number`, `model_number` or
     `country_of_origin`, although attributes came back (41 names). So `06` is `wontfix`.
   - **Catalog summaries, seller's ASINs:** 619 of 633 had `partNumber`, 1 only
     `modelNumber`, and 13 had neither. 488 were usable once ASIN, brand and placeholder
     values were dropped and the item's own barcode was not counted as a distinct part
     number.
   - **Catalog summaries, keyword sample:** 535 of 600 had `partNumber`, 42 only
     `modelNumber`, and 23 neither.
   - **Attributes vs summary:** `attributes.part_number` never added a value or disagreed
     with the summary.
   - **Origin:** no catalog record in either sample had `country_of_origin`.
   - **Barcodes:** 627 of the seller's 633 had a valid GTIN in the catalog, and 451 of the
     600 sample. 130 of the sample had a part number but no GTIN.
5. **Attribute names:** all 63 product types seen define `part_number`, and 13, mostly
   food, have no `model_number`. All mark `country_of_origin` required for a listing.

Still to do here: Shopify steps 1–2, and the Amazon import of `05` once built. Checking
that import now means confirming that the stamped and filled counts match these rates,
not measuring them.
