# Require `read_products` for Shopify imports

Status: done
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), *Access scope*. No dependencies. `03` and `04` need it.

## Problem

`ProductVariant`, `Product` and `InventoryItem` require the `read_products` access scope
(`InventoryItem` also accepts `read_inventory`). The Shopify import already reads
`variant { id barcode }`, and `03`–`04` add metafields and the inventory item. But
`ShopifyFulfillmentOrderActivationService::REQUIRED_SCOPES` lists only `read_orders`,
`read_locations` and the two merchant-managed fulfillment-order scopes. `docs/self-hosting.md`
mentions `read_products` only for buying Shopify Shipping labels.

Not yet known: what Shopify returns for `variant` on a token without `read_products`. It
could be `null`, an access-denied error on the whole query, or a partial result with an
`errors` entry. If it is `null`, every barcode from such a store has been
silently missing.

## Why a human

Answering it needs a development store app whose declared scopes leave out
`read_products`, and changing declared scopes means releasing an app version and
reinstalling.

## Desired behavior

1. Against a development store, run the fulfillment-order query with and without
   `read_products` and record what `variant` and `errors` hold in each case under
   `## Comments`. No customer data in the comment; the shape is enough.
2. Add `read_products` to `REQUIRED_SCOPES`, so activation refuses without it. A
   connection already active is checked when an import starts. If the scope is missing,
   the run fails with the same "Reconnect Shopify with the required scopes" message rather
   than importing products without barcodes or part numbers.
3. If step 1 showed a query-level error, the import already fails today and the fix is
   only step 2's message. If it showed `null`, say so in the PR: barcodes from affected
   stores fill in on the next import once the scope is granted.
4. `docs/self-hosting.md` lists `read_products` among the import scopes.

## Comments

**2026-10-05 — done.** `read_products` is in
`ShopifyFulfillmentOrderActivationService::REQUIRED_SCOPES`, so activation and location sync
refuse a token without it. `ShopifySource::fetchShipments()` now checks the live token's
scopes before the first fulfillment-order request and fails the run with "Reconnect Shopify
with the required scopes before importing: …". `docs/self-hosting.md` lists the import
scopes by name.

Step 1 was waived. Shopify's documentation is clear that `ProductVariant` needs
`read_products`, and the PolyBag app already declares it (`read_fulfillments`,
`write_fulfillments`, `read_locations`, `read_merchant_managed_fulfillment_orders`,
`write_merchant_managed_fulfillment_orders`, `read_orders`, `write_orders`,
`read_products`), so the import can query what it needs. Running the "without" case would
take a separate development-store app, which isn't worth it. If Shopify reports a denied
field as `ACCESS_DENIED` in `errors`, as the label-path fixture in `ShopifyAdapterTest`
assumes, imports always failed without the scope, because
`fetchFulfillmentOrderShipments()` throws on any `errors` entry. The new check replaces
that raw GraphQL error with the reconnect message either way.
