# Read the part number and GTIN from Shopify's typed barcodes

Status: ready-for-agent
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), *Shopify*. Builds on `04`. Independent of `09`.

## Problem

`03` and `04` read the NS-PID from a metafield the connection names, because Shopify had
no part-number field. Admin API `2026-10` adds one. A variant now carries a list of up to
20 barcodes, `ProductVariant.barcodes`, each a `ProductVariantBarcode { type value }`.
`type` is a `BarcodeType`: `UPC`, `EAN`, `ISBN`, `GTIN`, `ASIN` or `NS_PID`, or null when
the merchant declared no standard. Shopify documents `NS_PID` as the manufacturer's code
"used to identify a product in EU customs declarations". It also validates `UPC`, `EAN`,
`GTIN` and `ISBN` values against their standards.

PolyBag is pinned to `2026-07`, which has neither field. So a store that records its
part numbers as `NS_PID` barcodes, and names no metafield, imports no part number, and
its EU consumer labels are refused.

In `2026-10`, `ProductVariant.barcode` is deprecated ("Use `barcodes` instead") and
returns "the first entry in `barcodes`" when a variant has more than one. The import
writes that field to `products.barcode`, which Pack scans. When a variant's first
barcode is its `NS_PID`, the part number becomes the scan barcode, and `CustomsItem` no
longer finds a GTIN in it.

**This is not a 1 November blocker.** The metafield path already supplies an NS-PID, and
`09` covers products that have a GTIN and no part number. This gives stores a better
source that needs no setting.

## Desired behavior

### 1. Move every Shopify call to `2026-10`

Its own commit, ahead of the import change, since every Shopify call path is pinned to
one version per connection (`ShopifyConnector`): import, location sync, metafield
choices, closed-order lookup, fulfillment export and cancel, the fulfillment
synchronizer, Shopify Shipping purchase and polling, and label cost.

- `config/services.php` `shopify.api_version` and the fallback in
  `ShopifyConnector::fromSettings()` become `2026-10`. Update
  `ShopifyConnectorAuthModeTest`'s URL.
- The `2026-07` notes in `ShopifyShippingLabelService` and
  `ShopifyClosedFulfillmentOrderCloser` describe when a field appeared, not the pinned
  version. Leave them unless the live check below finds a change.
- A connection whose `settings.api_version` names an older version gets a schema error
  on import once step 2 lands. There are no live tenants and nothing in the UI sets
  `api_version`, so no version check is added.

### 2. Read the typed barcodes in the import

Both line-item selections, in `IMPORTED_FULFILLMENT_ORDER_FRAGMENT` and
`FULFILLMENT_ORDER_ITEMS_QUERY`, replace `barcode` with `barcodes`:

```graphql
variant {
  id
  barcodes(first: 5) { nodes { type value } }
  inventoryItem { harmonizedSystemCode countryCodeOfOrigin }
  {{partNumberSelection}}
}
```

`barcode` is dropped. It is deprecated, and it is the first entry of `barcodes`, so it
carries nothing that `barcodes` lacks.

**`first: 5`, not 20, because of Shopify's cost limit.** On the development store,
`FULFILLMENT_ORDERS_QUERY` (250 fulfillment orders, 40 line items each) requests 541
points with a part-number metafield. With `barcodes(first: 5)` it requests 926. With
`first: 10` it requests 1,003 and Shopify refuses it: 1,000 is the most one query may
request. A variant with its NS-PID after its fifth barcode loses it. Accept that rather
than shrinking the page. Update the cost figures in that constant's docblock.

`mapFulfillmentOrderLineItem()` maps from `barcodes.nodes`, in order:

- **`manufacturer_part_number`**: the first `NS_PID` value, trimmed and cut to 100
  characters like `04`. Shopify allows 255. If there is none, the metafield the
  connection names, exactly as `partNumberFrom()` reads it today. The typed barcode wins
  over the metafield because it is the field Shopify made for the purpose. The metafield
  setting stays for stores that keep a part number there, for example from a channel
  app. Nothing about it changes.
- **`gtin`**: the first value typed `UPC`, `EAN`, `GTIN` or `ISBN` that passes
  `App\Support\Gtin::isValid()`. An ISBN-13 passes and an ISBN-10 does not, which is
  correct: only the 13-digit form is an EAN. `ASIN`, `NS_PID` and untyped values never
  fill `gtin`. An untyped value that is a GTIN still reaches customs through `barcode`
  and `CustomsItem`'s fallback, as today. `gtin` fills only when Shopify said what the
  value is.
- **`barcode`**: the first value not typed `NS_PID`, typed or not. If every entry is an
  `NS_PID`, it is null, which leaves the Product's barcode alone.

All three overwrite the Product the way `04`'s fields do, and a null leaves it alone.
None is `_fill_only`. Shopify is the merchant's own record.

`ShopifyGoodsFingerprint` is unaffected. `source_checksum` changes once for every open
Shipment, as `04` noted.

## Acceptance criteria

- [ ] Every Shopify request goes to `2026-10` unless the connection overrides it
- [ ] Before merging step 1, each read query in `ShopifySource`,
      `ShopifyClosedFulfillmentOrderCloser`, `ShopifyLabelCostRecorder` and
      `ShopifyShippingLabelService` is checked live at `2026-10`. Also check one
      fulfillment export, one cancel, and one label-cost read. A Shopify Shipping
      purchase buys a real label, so a human runs that one
- [ ] A variant with `[EAN, NS_PID]` imports the EAN to `barcode` and `gtin` and the
      NS_PID to `manufacturer_part_number`
- [ ] A variant with `[NS_PID, EAN]` imports the EAN to `barcode`, not the part number
- [ ] With a part-number metafield set, a variant with an `NS_PID` imports the `NS_PID`
      and a variant without one imports the metafield
- [ ] With no metafield set, an `NS_PID` is still imported, and the query has no
      metafield selection or variables, as in `04`
- [ ] An `EAN` that fails `Gtin::isValid()` and an `ASIN` do not fill `gtin`. An untyped
      valid GTIN fills `barcode` only
- [ ] A variant whose only barcode is an `NS_PID` leaves the Product's `barcode` alone
- [ ] `FULFILLMENT_ORDERS_QUERY` with a part-number metafield stays under Shopify's
      1,000-point limit. Assert the selection is `first: 5` in the unit test that builds
      the query
- [ ] Verified on the development store as in `08`: an order for a variant with typed
      barcodes imports the part number and GTIN onto its Product

## Comments

**2026-10-14 — triage.** Confirmed in Shopify's `2026-10` docs for `BarcodeType`,
`ProductVariantBarcode`, `ProductVariantBarcodeConnection` and `BarcodeInput`, and by
introspecting the development store at `2026-10` and `2026-07`:

- `ProductVariant.barcodes: ProductVariantBarcodeConnection!`, paginated. Its nodes have
  `type: BarcodeType` (nullable) and `value: String!` (at most 255 characters). There
  are at most 20 per variant
- `BarcodeType` is `UPC`, `EAN`, `ISBN`, `GTIN`, `ASIN`, `NS_PID`
- `ProductVariant.barcode` is deprecated in `2026-10` and returns the first entry when
  there is more than one. `2026-07` has no `barcodes` field and no `BarcodeType`
- Every read query the app sends passed schema validation at `2026-10` with and without
  the part-number selection. The mutations were not sent. `fulfillmentCreate`,
  `fulfillmentCancel` and `shippingLabelPurchase` are not deprecated there. Behavior
  changes between versions were not reviewed
- Of the development store's 187 variants, 101 carry `[EAN, NS_PID]` and 60 one untyped
  barcode. None has an `NS_PID` first. The 25 with a `custom.mpn` metafield have no
  typed barcode, so both sources can be tested on one store, but not their precedence
  on one variant. No open order includes a typed-barcode variant

Not confirmed: whether `2026-07`'s `barcode` already returns an `NS_PID` that the
merchant listed first. The app's token has no `write_products` to set one up. The
development store's typed barcodes were already there; nothing was written for this
issue.
