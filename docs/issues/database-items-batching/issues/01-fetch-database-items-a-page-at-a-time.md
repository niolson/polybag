# Fetch a Database connection's items a page at a time

Status: needs-triage
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Problem

A Database connection makes one round trip to the customer's database for each order's
items. Shopify and Amazon don't, so imports from those connections run much faster.

Every import asks its source for each order's items before the batch write, because the
items feed the order's change checksum (`ShipmentImportService`, the
`fetchShipmentItems($sourceRecordId)` call in the per-row loop). This is what each source
does when asked (as of commit `ad2bc291`):

| Source | What `fetchShipmentItems()` does | Cost per order |
|---|---|---|
| Shopify | Returns `$pageItems[$id]`. The line items came in the same GraphQL page as the orders | None |
| Amazon | Reads `orderItems` from `$orderCache[$id]`. `searchOrders` returned them with the order | None |
| Database | Runs `shipment_items_query` with `:shipment_reference` bound to the one order, or `WHERE shipment_id = ?` on `shipment_items_table` without a custom query | 1 remote query, and with a custom query 1 `AuditLog` insert |

Why this costs a lot:

- **Round trips.** A Database connection often reaches its server over an SSH tunnel or a
  WAN link to an on-prem SQL Server. An import of 2,000 orders makes 2,000 sequential
  queries on top of the orders query. At about 20 ms each, that is 40 seconds of waiting.
- **Every order, every run.** The query runs for unchanged orders too, because the
  checksum needs the items to find out whether anything changed.
- **The audit log.** `executeLogged()` writes one `AuditLog` row each time the custom
  items query runs. The status query already audits once per run (`auditStatusLookups()`),
  but the items query does not.

Order volumes are bursty: pre-orders, merch drops and seasonal sales flood imports. The
time cost grows with the size of the feed, and the burst is exactly when it hurts most.

### What happens when the items query fails

The orders query and the items query can fail independently.

- **The items query throws.** The exception is caught by the per-row `try`, so the order
  is skipped and not written. Items are fetched before the order joins the batch, so
  nothing of it is written. The run records `Error importing shipment X: …` once for each
  order. A broken items query therefore imports nothing, makes one failed remote query
  per order, and logs the same error once per order.
- **The items query runs but returns no rows for an order** (a wrong join, or a reference
  in a different format). The order imports with no items and nothing reports it. An
  existing order keeps its items, because the authoritative delete in
  `ShipmentItemImporter` requires a non-empty item list. A new order lands with nothing
  to pack.

### What validates the items query today

Only `RawSqlGuard`, which checks that it is a single SELECT. Nothing checks that the
query uses `:shipment_reference`. The export query has this check
(`DatabaseSource::exportQueryParametersRule()`, built on `namedParameters()`), but the
items query does not. Preview runs the items query for the first previewed order only.

## Proposed decisions

Each one needs a maintainer to confirm it:

1. **A list placeholder for the custom items query.** A new placeholder,
   `:shipment_references`, is written inside an `IN` list:

   ```sql
   SELECT l.order_no, l.sku, l.qty, l.price
     FROM order_lines l
    WHERE l.order_no IN (:shipment_references)
   ```

   PolyBag expands it into one bound parameter per order on the page (`:r0, :r1, …`) and
   runs the query once per page. Values are bound, never interpolated, exactly as
   `:shipment_reference` is today.
   - The Database driver already reads in pages of `DatabaseSource::PAGE_SIZE` (250).
     That keeps the list well under SQL Server's 2,100-parameter limit.
   - A page could also be split into smaller groups of references if a server proves
     slow with a long `IN` list.

2. **The rows say which order they belong to.** The item field mapping gains a
   `shipment_reference` target. A batched query must map a column to it, so its rows can
   be grouped by order. A single-order query doesn't need one, because every row it
   returns already belongs to the order that was asked about.

3. **Existing single-order queries keep working.** A query that uses `:shipment_reference`
   runs per order as it does now. One that uses `:shipment_references` runs per page. A
   query that uses both, or neither, is refused when the form is saved.
   - This could instead be a hard switch to the batched form. Keeping both costs one
     branch, and spares anyone with a working query from converting it by hand. Which is
     preferred?

4. **The default path batches without any contract change.** When there is no custom
   query, `shipment_items_table` is read with `whereIn('shipment_id', …)` once per page,
   grouped by `shipment_id`.

5. **The audit log records the items query once per run**, the way the status query
   does: the query, how many times it ran, and how many runs failed. It no longer writes
   a row per execution.

6. **A failed items query fails the page, and the run stops.** The query is the same on
   every page, so it would fail the same way on each. The run records one error naming
   the items query instead of one error per order. The pages already written stay
   written.

### Validation, in three layers

PolyBag cannot parse arbitrary SQL across MySQL, SQL Server, PostgreSQL and SQLite well
enough to prove a filter correct. These checks catch the mistakes that matter.

**When the form is saved (static checks).** A new `ValidationRule`, alongside
`RawSqlGuard::rule()`, checks that:

- The query names exactly one of `:shipment_reference` and `:shipment_references`, found
  with `namedParameters()` so quoted text and comments don't count. A query that names
  neither is refused today too, which closes the gap described above.
- `:shipment_references` appears inside `IN ( … )`, matched on the comment- and
  string-stripped SQL with something like `IN\s*\(\s*:shipment_references\s*\)`. A list
  placeholder means nothing anywhere else, so this restriction costs nothing.
- A batched query has an item field mapped to `shipment_reference`.

**In Preview (the real query, run against the real database).** Preview binds every
previewed order, not just the first, and checks that:

- Every returned row's reference is one of the references bound. A filter that is
  ignored or wrong fails here.
- The reference column is present and mapped. A misspelled alias fails here.

Preview names the failing check, as it already names a failing query.

**On every page of an import.** The same checks run against what each page returns:

- A row whose reference wasn't asked for is dropped and counted. The run's errors report
  the count.
- If the query returns rows and none of them has a reference that was asked for, the
  mapping is broken. That fails the page and stops the run (decision 6), instead of
  importing every order with no items.

## Acceptance criteria

- [ ] A custom items query using `IN (:shipment_references)` runs once per import page,
      with one bound parameter per order on it
- [ ] Items are grouped to their orders by the column mapped to `shipment_reference`,
      compared as strings against each order's `source_record_id`, so an integer column
      still matches
- [ ] A query using `:shipment_reference` still runs once per order, unchanged
- [ ] Without a custom query, `shipment_items_table` is read once per page
- [ ] Saving refuses an items query that names neither placeholder or both, a
      `:shipment_references` outside `IN ( … )`, or a batched query with no
      `shipment_reference` mapping
- [ ] Preview binds every previewed order and fails, naming the check, when a row's
      reference wasn't asked for or the reference column is missing
- [ ] An import page whose rows carry no requested reference fails, and the run stops
      with one error naming the items query
- [ ] A failing items query records one error and stops the run, instead of one error
      per order
- [ ] The items query is audited once per run, with its execution and failure counts
- [ ] `docs/data-sources/database.md` documents `:shipment_references`, the
      `shipment_reference` item mapping, and the failure behavior, with an example
      for each supported database
- [ ] Tests cover both placeholders, the default path, each validation layer, and a
      failing query, with the query count asserted for a multi-page import

## Out of scope

- Flagging a new order imported with zero items. A real zero-item order can't be told
  apart from a bad join on one order, so this is a separate decision with its own
  false positives. Worth considering on its own
- Batching the status query (`closeRecordsClosedAtSource`), which also runs per open
  Shipment. It would follow the same pattern but runs after the import, not inside it
- Batching the mark-exported and export queries. They are writes capped by
  `max_affected_rows`, and they run per record on purpose
