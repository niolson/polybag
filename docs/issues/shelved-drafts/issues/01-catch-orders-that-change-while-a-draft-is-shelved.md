# Catch orders that change while a Package Draft is shelved

Status: needs-triage
Category: enhancement
Created: 2026-09-29

## Problem

A packed Package Draft can sit on a shelf for hours or days: waiting for a customer to
approve a substitution, for a manager to approve an expensive rate, for a payment check,
or simply because the packer set it aside. Meanwhile the order behind it can change at
the sales channel. It can be cancelled, have items edited, or be re-imported with
different contents.

When someone comes back to the draft, nothing tells them the order changed. Buying a
label then spends postage on an order that no longer wants it, or ships the wrong goods.
And there is no way to say a draft is deliberately on hold. A shelved draft waiting for
approval looks the same as one somebody forgot.

## Current state

- **Cancellation is invisible.** Shopify and Amazon imports fetch only open orders
  (Shopify fulfillment orders `OPEN`/`IN_PROGRESS`; Amazon `UNSHIPPED`/
  `PARTIALLY_SHIPPED`). A cancelled order drops out of the feed and nothing changes
  locally. The Shipment stays `open` and its draft stays buyable.
- **A database source's status change is not applied once a Package exists.**
  `ShipmentBatchWriter::shouldUpdate()` refuses to move an open Shipment to a non-open
  status when it has any Package, a draft included. That guard protects packed work,
  but it also means a cancellation reported by the source is dropped silently.
- **Removed items stay.** With `authoritative_shipment_items`, items that disappear at the
  source are deleted locally only while the Shipment has no Package
  (`ShipmentItemImporter`). Once a draft exists they remain.
- **Item mismatches are caught only by packing validation.** At purchase,
  `PackageDraftWorkflow::assertPackageReadyToShip()` compares packed items with the
  Shipment's current quantities when `packing_validation_enabled` is on. With it off,
  or for a scan-to-add Shipment, nothing compares them.
- **No hold state.** A Package Draft is Empty, Packing or Ready to ship (the Packages
  list's computed draft state). Nothing records that a draft is being held, why, or
  until when. Batch shipping and "Buy and print label" will buy a ready draft that
  someone meant to hold.
- **Weight can go stale.** "Buy and print label" on View Package shows the stored weight
  and when the draft was last saved before buying. Nothing stops a purchase at an old
  weight.

## Proposed direction

- **Detect cancellation.** On each import, find open Shipments from that source whose
  order has been cancelled. That may need an explicit cancelled-orders query per
  channel, because absence from an open-orders feed does not by itself mean cancelled.
  Mark them, and refuse purchase for their drafts with a clear message.
- **Record source changes against a draft.** When a re-import changes a Shipment that has
  a Package Draft (items, quantities, address, shipping method, status), flag the draft
  as needing review instead of dropping the change or applying it silently. Show the
  flag on the Pack page, View Package and the Packages list, and refuse unattended
  purchase until someone clears it.
- **An explicit hold.** Let a manager put a Package Draft on hold with a reason (awaiting
  approval, awaiting customer, other) and an optional note. A held draft is excluded
  from batch shipping and auto-ship, shows as On hold in the Packages list, and needs a
  release before anyone buys for it.
- **Re-check at purchase.** Just before buying, optionally re-read the order from its
  source for channel orders, and refuse if the order is cancelled or no longer matches.

## Open questions

1. **Which channels can report cancellation cheaply?** Shopify exposes cancelled orders
   and closed fulfillment orders; Amazon reports cancellation on the order. A database
   source may have no notion of it beyond its query. Is a per-source "cancelled" field
   mapping enough there?
2. **What happens to a cancelled order's draft?** Keep it for someone to unpack and
   restock, as CONTEXT.md keeps drafts until someone deletes them, or mark the Shipment
   `void` and leave the draft as history?
3. **Should the source-change guard in `ShipmentBatchWriter` stay?** It protects packed
   work from being overwritten. The alternative is to apply the change and flag the
   draft.
4. **Who may place and release a hold?** Managers only, or shippers too, with release
   limited to managers?
5. **Does a live re-check at purchase cost too much?** One API call per label, against
   rate limits and batch-ship throughput.
6. **Stale weight.** Should a draft untouched for longer than some period need
   re-weighing before an unattended purchase, rather than only showing the age?
