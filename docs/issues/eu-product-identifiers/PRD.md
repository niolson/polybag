# EU Product Identifiers on customs declarations

Status: reference

Repo: `polybag`

Background for the issues in this directory. Not a work item.

> *This was generated by AI during triage.*

## Where this came from

A FedEx Compatible notice received 2026-09-17, and the UPS Ship API developer guidance
(*EU Product Identifier (PID) Requirements*, v1.0, August 2026) linked from the UPS
developer portal header. USPS has published nothing yet.

## The regulation

From **1 November 2026** EU customs will hold any B2C consignment whose commodity lines
do not carry three product identifiers. The EU accepts them from 1 July 2026 and both
carriers ask for them to be sent early.

| Identifier | Meaning | Required |
|---|---|---|
| **M-PID** — Merchant Product Identifier | The seller's own SKU | Yes |
| **NS-PID** — Non-Standardized Manufacturer Product Identifier | The manufacturer's part / model number | Yes |
| **S-PID** — Standardized Manufacturer Product Identifier | GTIN / UPC / EAN | If one exists; otherwise a literal placeholder (FedEx) or omitted (UPS) |

Applies when the origin is outside the EU, the destination is inside it, the consignee is
a consumer (FedEx phrases it as "non-VAT-registered"), and the shipment is a sale. FedEx's
documentation ties it to a customs value under €150 — the de minimis band whose exemption
is being removed — but the FedEx notice does not, so treat every EU B2C line as in scope.

## What each carrier wants

### FedEx Ship API — mandatory on or after 1 Nov 2026, fields live in the docs now

Per commodity, under `requestedShipment.customsClearanceDetail.commodities[]`:

```json
"regulatoryDetails": [{
  "regulationCode": "EU_DE_MINIMIS",
  "productId": "SKU-12345",
  "productIdType": "SKU",
  "details": {
    "merchantProductId": "SKU-12345",
    "nonStandardManufacturerProductId": "MFG-67890",
    "standardManufacturerProductId": "01234567890128"
  }
}]
```

`productIdType` is one of `SKU`, `PART_NUMBER`, `GTIN`, `UPC`, `EAN`, `MPN`, `OTHER`.
The other `regulationCode` is `CPSC`, which is not this work.

**Discrepancy:** the FedEx notice says write `"NO"` when there is no standard
identifier; the Ship API docs say `"NA"`. The docs describe the field and the notice
describes the EU rule, so `02` sends `"NA"` and `05` confirms it with the Compatible
integrator mailbox.

### UPS Ship API — effective 25 Oct 2026, fields **not yet in production**

Per product, under `ShipmentServiceOptions.InternationalForms.Product[]`:

```json
"productIdentifierExemptIndicator": "false",
"ProductIdentifier": [
  { "ProductID": "SKU-12345", "ProductIDTypeCode": "0100" },
  { "ProductID": "MFG-67890", "ProductIDTypeCode": "0200" },
  { "ProductID": "01234567890128", "ProductIDTypeCode": "0300" }
]
```

`ProductID` is up to 100 characters. `0100` and `0200` are required when the exempt
indicator is false; `0300` is optional — no placeholder. UPS decides whether the rule
applies from three existing fields: `InternationalForms.ReasonForExport` (we send
`SALE`), `Shipment.ShipperType` and `Shipment.ConsigneeType` (Business / Consumer — we
send neither today, so UPS's default is deciding for us). The exempt indicator defaults
to false for qualifying shipments; nothing here needs it set to true.

The guidance names both `/ShipmentRequest/...` and `/ShipmentConfirmRequest/...` paths.
The JSON Ship API uses the former; the latter is the legacy XML shape and is not ours.

### USPS — no support as of 2026-09-17

Checked against the International Labels OpenAPI spec the developer portal serves
(declared version 3.3.10, copy in `.scratch/eu-product-identifiers/`). A customs
content item is `itemDescription`, `itemQuantity`, `itemValue`, `itemTotalValue`,
`weightUOM`, `itemWeight`, `itemTotalWeight`, `HSTariffNumber`, `countryofOrigin`,
`itemCategory`, `itemSubcategory` — what `UspsAdapter` already sends. The base
`ShippingContents` schema is `additionalProperties: true` (the `InternationalShippingContents`
wrapper says `false`, but with no properties of its own that is inert; Redoc shows the
merged `true`), so an unknown key is most likely accepted and dropped rather than
rejected — there is no named field for an identifier and nowhere in the Shipping
Services File or the CN22/CN23 for one to land. USPS's public
EU-changes page covers the July 2026 €3-per-HS-code duty and asks only for accurate
descriptions. Postal-channel customs data reaches the EU through the UPU's ITMATT
message rather than a carrier API, which is the likely reason USPS trails FedEx and UPS.
`05` watches for a change.

### Shopify Shipping and Amazon Buy Shipping

Pass-through. Both platforms build the customs declaration from their own order and
catalog data; the PIDs come from the merchant's Shopify or Amazon product records, not
from us. No adapter change. Worth a line in the self-hosting docs so a tenant does not
expect PolyBag's product fields to reach a Shopify-bought label.

## What the app has today

`CustomsItem` (`app/DataTransferObjects/Shipping/CustomsItem.php`) carries description,
quantity, unit value, weight, HS tariff number and country of origin. Three adapters map
it — `FedexAdapter::buildCustomsClearanceDetail()`, `UpsAdapter::buildCustomsDetail()`,
`UspsAdapter`'s `contents[]` — and none sends any product identifier.

| Identifier | Source today | Gap |
|---|---|---|
| M-PID | `products.sku` | None. Always set on Shopify, Amazon and Database imports; a product without a SKU is skipped at import |
| NS-PID | — | **No column.** Nothing imports it: Shopify variants have no MPN field, Amazon orders do not carry one, the Database mapping has no slot |
| S-PID | `products.barcode` | It is the *scan* barcode. Usually a UPC/EAN, but a client can print internal Code 128 labels, so it is not a GTIN by construction |

Related: `products.hs_tariff_number` and `products.country_of_origin` are also missing
from the Database driver's item mapping (`docs/data-sources/database.md`), so today they
can only be typed into the product form. The same mapping gap is what `01` fixes for
the new fields, and it should take those two with it.

The app has no representation of "is the consignee a business" beyond a non-empty
`company` on the shipment, and no EU membership test — `AddressData::sharesCustomsZoneWith()`
answers "does this cross a customs border", not "into which territory".

## Decisions taken here

- **Send identifiers on every EU-bound line whenever the product has both required
  ones**, business consignee or not, above or below €150. An identifier on a B2B line is
  harmless; a missing one on a B2C line is a held parcel. A line with only one of the
  two mandatory identifiers gets no identifier block at all — both carriers' shapes
  make a partial block an invalid body, not a partial declaration. The B2C question only
  decides whether that *absence* refuses the purchase (`04`).
- **The identifier check and the identifier blocks apply only where our declaration is
  sent** — never on a blind Shopify/Amazon offer, never between addresses in one customs
  zone. `ShipRequest::zeroValueCustomsItems()` already has those two gates; `04` reuses
  them.
- **A consignee with no company name is a consumer.** That is the only signal the app
  has; it is what the pack slip and the carriers' own address forms already assume. A
  `vat_number` on the shipment is not added now — nothing imports one.
- **`gtin` is a new column, not a reinterpretation of `barcode`.** S-PID is populated from
  `gtin`, falling back to `barcode` only when it validates as a GTIN-8/12/13/14 with a
  correct check digit. A Code 128 internal barcode is never sent as a standard identifier.
- **EU membership is the EU27 country list**, as a predicate on `AddressData`. Northern
  Ireland (GB, `BT` postcodes) is inside the EU customs territory for goods and Monaco
  ships as France; both are out of scope until a tenant ships there.

## Issues

- `01` — product identifier fields: columns, product form, `CustomsItem`, import mapping
- `02` — FedEx: `EU_DE_MINIMIS` regulatory details on every EU-bound commodity
- `03` — UPS: `ProductIdentifier` on every EU-bound product, plus `ShipperType`/`ConsigneeType`
- `04` — refuse an EU consumer label when a line has no M-PID or NS-PID
- `05` — verify against the carrier sandboxes, resolve `NO`/`NA`, answer the FedEx form

## Effort

Roughly three to four developer-days of code across `01`–`04`, each slice testable with
the existing adapter schema tests and fixtures. The calendar is set by `05`: FedEx's
sandbox already accepts the fields so that half can be verified as soon as `02` lands;
UPS's fields are not in production and the guidance does not say whether CIE has them,
so `03` ships against the documented shape and is re-verified when UPS turns it on.

The larger cost is not code. Every client shipping to EU consumers has to supply an
NS-PID per product before November, and the only paths into the app are the product
form and a Database import column. That is a customer-communication task to start in
parallel, not after.

Readiness date to give FedEx: **15 October 2026** for PID transmission over the Ship
API, with the UPS half following UPS's own production date.
