# A SKU or part number made only of punctuation passes the refusal and then reaches USPS with no identifier block

> *This was generated by AI during release-polish pass 4.*

Status: done

Page or flow: USPS international purchase to an EU consumer

Severity: low — needs an identifier with no letter or digit

Verified: plausible. Line numbers are at `12592f33`; this area is unchanged on `dfd842c5`.

## Problem

The refusal counts an identifier as present when it is non-blank
(`CustomsItem.php:69-72`, `CustomsReadiness.php:136-138`). `UspsAdapter::alphanumericProductIdentifier()`
(`app/Services/Carriers/UspsAdapter.php:1639-1648`) strips everything outside
`[A-Za-z0-9]` and treats an empty result as missing, so `euProductIdentifiers()` returns
null and the line is sent with `incoterm` `"1"` and no `europeanUnionProductID`, which
USPS's definitions in `07` make required. `07` assumed "`04` already refuses a consumer
label with such a line", which holds only for null identifiers. The result is a USPS
rejection after the Offer is claimed (or, if USPS does not validate, a held parcel)
instead of the named refusal. A part number written entirely in a non-Latin script
behaves the same.

## Evidence

Scenario: Product SKU `MUG-1`, part number `---` (or `—`), Shipment to a
consumer in France, USPS international rate. Readiness passes; the label request's
content line has no `europeanUnionProductID`.

## What to build

Product decision with `07`'s pending USPS answer: either refuse a
USPS EU consumer label whose stripped identifier is empty (a carrier-specific check in
`CustomsReadiness::carrierFindings()`, reusing the adapter's stripping), or accept the
carrier error. Recommend the refusal.

## Comments

### 2026-10-15: refused, as recommended

USPS International Labels 3.4.1 (the 2026-10-28 release) keeps the letters-and-digits
patterns, so the stripping stays and an identifier with no letter or digit cannot be sent.

- The stripping moved out of `UspsAdapter` into `App\Support\UspsProductIdentifier`, so
  the adapter and the readiness check agree on which identifiers survive, as
  `FedexRecipientEmail` does for FedEx.
- `CustomsReadiness::carrierFindings()` adds `usps_product_identifier_unusable`: for an
  EU consumer label (the same gates as `linesMissingProductIdentifiers()`, now shared as
  `declaresEuConsumerIdentifiers()`), a line with both identifiers where either strips to
  nothing. It blocks a USPS rate and is a warning before a carrier is chosen, since FedEx
  and UPS take the identifier as entered. A null identifier is still reported only by
  `product_identifier_missing`.
- `CustomsReadinessTest` covers USPS (block), no rate (warning), UPS, a business
  consignee, and a sendable SKU.
