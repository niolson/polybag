# UPS: `ProductIdentifier` on every EU-bound product, plus shipper and consignee type

Status: ready-for-agent
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md). Needs `01` and `02`'s `isInEuropeanUnion()`.

## Problem

`UpsAdapter::buildCustomsDetail()` sends description, unit, origin, weight and commodity
code per `Product` and nothing that identifies the product. UPS enforces the identifiers
on qualifying shipments from 25 October 2026. It also decides *whether* a shipment
qualifies from `Shipment.ShipperType` and `Shipment.ConsigneeType`, which the adapter
has never sent, so today UPS is classifying our shipments by its own default.

## Desired behaviour

On every EU-bound shipment with a customs declaration, each `Product` gains:

```json
"productIdentifierExemptIndicator": "false",
"ProductIdentifier": [
  { "ProductID": "<merchantProductId>",     "ProductIDTypeCode": "0100" },
  { "ProductID": "<manufacturerProductId>", "ProductIDTypeCode": "0200" },
  { "ProductID": "<standardProductId>",     "ProductIDTypeCode": "0300" }
]
```

The block — indicator and list together — is sent only when the product has **both** a
merchant and a manufacturer identifier, since `0100` and `0200` are each required
whenever the indicator is `false` and the app never has grounds to say `true`. A
product missing either gets neither key, exactly today's body, and UPS applies its own
default; `04` refuses that shipment for a consumer consignee, and for a business
consignee it is bought as it would be today. The `0300` entry is omitted when the
standard identifier is null — UPS has no placeholder and the entry is optional.
`ProductID` is truncated to 100 characters. Whether the JSON API takes the exempt
indicator as the boolean `false` or the string `"false"` is unknown until `05` runs it;
the UPS guidance shows XML and the vendored spec does not have the field. Write it the way the rest of the body writes its flags and
note the assumption.

Independently of the destination, every `createShipment` body sends:

- `ShipperType: "01"` (Business) — the shipper is always a warehouse
- `ConsigneeType` — `"01"` when the destination has a company name, `"02"` (Consumer)
  when it does not

The codes are confirmed in the vendored `tests/Fixtures/Schemas/upsShipping.json`:
`01` Business, `02` Consumer/Individual, `NA` Not Applicable — and the schema already
marks both *"Required for EU Inbound Shipments"*, so UPS has been tolerating their
absence on every EU label the app has bought. Sending them on domestic labels too is
deliberate: it is one rule, and the alternative is UPS's default deciding on the day
the fields start mattering.

The rate request is not touched; UPS rates without the product list.

## Acceptance criteria

- [ ] `upsShipping.json` still validates the new body. The vendored spec has
      `ShipperType`/`ConsigneeType` but no `ProductIdentifier` — the test that guards
      the schema extends it under `InternationalForms.Product` from the UPS guidance and
      says so, to be replaced when UPS republishes the spec
- [ ] `UpsAdapterTest`: a shipment to France with all three identifiers sends three
      `ProductIdentifier` entries and the exempt indicator; one with no standard ID
      sends two; one with no manufacturer ID sends neither the list nor the indicator
      on that product while the other products keep theirs; one to Canada sends none
      and no exempt indicator
- [ ] `UpsAdapterTest`: a shipment with a company sends `ConsigneeType` `01`, one
      without sends `02`; both send `ShipperType` `01`; a domestic label sends both
- [ ] The label request in `Log::channel('ups-validation')` shows the block

## Out of scope

- The exempt indicator ever being true. No product category the app knows about is
  exempt, and the app has no place to record one
- USPS — nothing published to implement
