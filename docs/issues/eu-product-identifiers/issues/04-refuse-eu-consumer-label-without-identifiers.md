# Refuse an EU consumer label when a line has no M-PID or NS-PID

Status: ready-for-agent
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md). Needs `01` and `02`'s `isInEuropeanUnion()`. Mirrors
`shopify-shipping-carrier/26`, which refuses a zero-value customs line the same way.

## Problem

Once `02` and `03` send whatever identifiers the product has, a product with none
produces a label that clears the carrier's API today and is held at EU customs in
November. The operator finds out from a customer, weeks later. The zero-value guard
already establishes that a defective customs line is refused *before* the purchase, per
line, in front of every adapter; a missing identifier is the same class of defect.

## Desired behaviour

`ShipRequest` gains `customsItemsMissingProductIdentifiers(): array<CustomsItem>`,
non-empty when the destination is in the EU, the consignee has no company name, and any
line lacks a merchant or manufacturer identifier. The standard identifier is never
required — both carriers accept its absence.

It opens with the same two gates as `zeroValueCustomsItems()` and returns empty for
either: a `blindOffer` (Shopify and Amazon build their own declaration from their own
catalog, so ours is never sent) and a pair of addresses that share a customs zone (an
intra-EU label from an EU warehouse carries no declaration at all). Without the second
gate an EU location shipping domestically would be refused on every consumer label.

`EloquentPackageShippingWorkflow` checks it immediately after the zero-value check and
throws `MissingProductIdentifierException`, carrying the offending items, which the Ship
page, batch ship and auto-ship surface exactly as they surface the zero-value one: each
line named, the missing field named, nothing bought, the offer not consumed. A line is
named by its SKU when it has one and by its description otherwise — a missing SKU is
one of the two things being reported, so the message cannot lean on it.

Business consignees and non-EU destinations are never refused by this check.

There is no operator override. An identifier the operator types at ship time would be
typed once per label; the product form is where it belongs, and the refusal message says
so.

## Acceptance criteria

- [ ] `ShipRequestTest`: EU + no company + a line without `manufacturerProductId` is
      listed; the same with a line whose product has no SKU is listed; EU + company is
      empty; Canada + no company is empty; EU + no company with
      all lines complete is empty; a line missing only the standard identifier is empty;
      the same incomplete line under a `blindOffer` is empty; the same line from a
      German origin to a German consumer is empty
- [ ] `MissingProductIdentifierTest` beside `ZeroValueCustomsItemTest`: the Ship page
      refuses with the SKU and the missing field named; a product with no SKU is
      refused with its description named; the offer is still unclaimed afterwards;
      batch ship records the refusal against the package and continues
- [ ] The refusal names the product form as where to fix it

## Out of scope

- A warning mode before November. The carriers accept incomplete data until then, but
  a label that will be held is not one a 3PL wants to sell at any date; if a client
  needs the softer behaviour it is a per-client setting to add when asked
- Refusing on a missing standard identifier
