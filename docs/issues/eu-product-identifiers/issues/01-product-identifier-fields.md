# Product identifier fields

Status: ready-for-agent
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md). First slice; `02`–`04` all read what this adds.

## Problem

The app can name a product's SKU and scan barcode but has nowhere to keep a
manufacturer part number or a GTIN, and `CustomsItem` — the one DTO every customs
declaration is built from — carries neither. Nothing an adapter does in `02` or `03`
can send what the model does not hold.

## Desired behaviour

Two new nullable columns on `products`:

- `manufacturer_part_number` — the NS-PID. Free text, up to 100 characters (the UPS
  limit; FedEx publishes none).
- `gtin` — the S-PID. Digits only, 8, 12, 13 or 14 long, with a valid GS1 check digit;
  rejected by the form otherwise.

Both on the product form beside `hs_tariff_number` and `country_of_origin`, in a
*Customs* section if the form does not already group them.

`CustomsItem` gains three readonly `?string` properties, each null when the product
has nothing to say, resolved in `fromPackageItem()`:

- `merchantProductId` — `products.sku`, which is nullable
- `manufacturerProductId` — `products.manufacturer_part_number`
- `standardProductId` — `products.gtin`, else `products.barcode` when it validates
  as a GTIN, else null

The GTIN check lives in one place — a small value object or a static on `CustomsItem`,
whichever the surrounding code prefers — so the form and the DTO agree on what counts.

`ShipRequest::withScaledCustomsWeights()` rebuilds every `CustomsItem` by hand to scale
the weight. The three new fields must be copied through, or accepting a customs-weight
override — a prompt the operator answers immediately before purchase — silently strips
the identifiers from the label that is then bought. Prefer a `withWeight()` on
`CustomsItem` that clones the rest, so the next field added cannot be forgotten the
same way.

The Database driver's item mapping gains `manufacturer_part_number`, `gtin`,
`hs_tariff_number` and `country_of_origin` as *fields with no default mapping*, written
to the Product like `weight` is, and `docs/data-sources/database.md` lists them. The
Shopify and Amazon sources are untouched: neither carries a manufacturer part number,
and the barcode they already import is what the GTIN fallback reads.

## Acceptance criteria

- [ ] Migration adds both columns; `Product` fillable and factory updated; the factory's
      default `gtin` is a synthetic value with a valid check digit
- [ ] Product form saves both; an invalid `gtin` is refused with a message naming the
      check digit
- [ ] `CustomsItemTest`: `fromPackageItem()` resolves all three identifiers; a product
      with `gtin` null and a 12-digit UPC `barcode` yields that barcode; with a Code 128
      `barcode` yields null; with no SKU yields null for the merchant ID
- [ ] `ShipRequestTest`: `withScaledCustomsWeights()` on an over-weight request returns
      items carrying the same three identifiers as before scaling
- [ ] Database import with all four columns mapped — `manufacturer_part_number`, `gtin`,
      `hs_tariff_number`, `country_of_origin` — writes each to the Product on first
      import, and a re-import with changed values updates each. One assertion per field:
      `ImportReferenceResolver` copies product fields one by one, so a test that checks
      only one of them passes with the other three forgotten
- [ ] `docs/data-sources/database.md` lists the four fields under *Fields with no default
      mapping*

## Out of scope

- Sending anything to a carrier — `02`, `03`
- Pulling a part number from the Amazon catalog (`part_number` / `model_number`
  attributes exist there) or from a Shopify variant metafield — a follow-up once a
  client asks, not before
- A bulk product editor. Clients with many SKUs and no ERP will need one before
  November; that is a separate issue to open when the first client says so
