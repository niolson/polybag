# USPS: `incoterm` and `europeanUnionProductID` on EU-bound international labels

Status: ready-for-human
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), *USPS — no support as of 2026-09-17*, which this supersedes. Needs
`01`'s identifiers on `CustomsItem` and `02`'s `AddressData::isInEuropeanUnion()`. `05`
said to open a USPS issue once USPS published something; this is that issue.

## Problem

`UspsAdapter::buildCustomsForm()` sends description, quantity, value, weight, origin and
HS code on each `contents[]` line, and nothing that identifies the product. On
2026-10-07 a USPS developer posted the fields in a public GitHub thread, to be published
in the International Labels spec on **2026-10-14**. USPS's *International Customs Changes
Release Overview* says the API will reject EU business-to-consumer merchandise requests
that lack them. EU customs holds such parcels from **1 November 2026**.

USPS adds two things:

- **`customsForm.incoterm`**: `"1"` Business to Consumer, `"2"` Business to Business,
  `"3"` Consumer to Consumer, `"4"` Consumer to Business. Required for EU destinations
  when `customsContentType` is `MERCHANDISE` or `COMMERCIAL_SAMPLE`.
- **`customsForm.contents[].europeanUnionProductID`**, required when `incoterm` is `"1"`:

  | Field | Pattern | Required |
  |---|---|---|
  | `merchantProductIdentifier` | `^[A-Za-z0-9]{1,50}$` | Yes |
  | `nonstandardizedManufacturerProductIdentifier` | `^[A-Za-z0-9]{1,70}$` | Yes |
  | `standardizedManufacturerProductIdentifier` | `^[A-Za-z0-9]{1,50}$` | Only when one exists; no placeholder |

**USPS's `incoterm` is not an Incoterm.** It holds the commerce type, not DDP/DDU, and it
has nothing to do with `international-customs-terms`' `duties_terms` (ADR-0008). Name it
for what it holds in our code, for example `commerceType`. Never derive it from, or map
it to, the duties term.

## Desired behavior

When the destination is in the EU (`isInEuropeanUnion()`), the customs form gains
`incoterm`. Every other destination's body stays as it is today.

- The adapter always sends `customsContentType: MERCHANDISE`, and the shipper is always a
  business (a warehouse), so `incoterm` is `"2"` when the destination has a company name
  and `"1"` when it does not. This is the same rule `UpsAdapter` uses for
  `ConsigneeType`. `"3"` and `"4"` are never sent.
- With `incoterm` `"1"`, each line whose `CustomsItem` has both a merchant and a
  manufacturer identifier gains `europeanUnionProductID`. The standard identifier is
  added only when it is not null. A line missing either required identifier gets no
  block. `04` already refuses a consumer label with such a line before the adapter is
  reached, so this only happens on a business label. That matches what FedEx and UPS do.
- With `incoterm` `"2"`, the block is sent anyway whenever the line has both
  identifiers. The PRD's rule is to send identifiers on every EU-bound line that has
  them. Whether USPS rejects the block on a B2B form is a question for the verification
  below. If it does, send the block only with `"1"`.

### The alphanumeric pattern

All three patterns allow only letters and digits, so `ABC-123`, `ABC 123` and `A/B` all
fail validation. Most real SKUs and part numbers contain punctuation, so this decides
whether USPS works for EU consumers at all. The question has been asked in the USPS
GitHub thread. Until USPS answers:

- Remove every character outside `[A-Za-z0-9]` and cut the result to the field's length.
  This is a USPS-only transformation. `CustomsItem` and the FedEx and UPS bodies keep
  the identifier as entered.
- An identifier that is empty after removal counts as missing, and that line gets no
  block.
- Keep the transformation in one small, named method, so that whatever USPS answers
  changes only that method.

Refusing the label instead would block every client whose SKUs contain a hyphen. Sending
the raw value would turn the API's rejection into a purchase error with no clear fix.

The rate request is not touched.

## Out of scope

- `COMMERCIAL_SAMPLE`, gifts, and consumer shippers: the adapter declares only
  merchandise from a business
- USPS's guidance that the UI should ask the shipper for content type and commerce type.
  PolyBag works both out from the shipment instead
- How a missing GTIN is declared as `Y081`, which is `06`'s question. USPS's "omit when
  unavailable" is the same answer UPS gives
