# Demo never writes back to a live Shopify or Amazon store

Status: ready-for-agent
Category: bug
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), decisions 1 and 2. Uses `AppMode` from `connection-onboarding/01`, and
the development-store check from `02` (build it here if this lands first).

## Problem

`PackageExportService::exportPackage()` exports a shipped Package to the Shipment's
originating connection when its export is enabled, and in multi-client mode to every
active connection with global export on. For a Shopify connection,
`ShopifySource::exportPackage()` runs `fulfillmentCreate` against the live store, with
`notifyCustomer` taken from the connection's `notify_customer` setting. No step on the way
checks the mode.

So in Demo a sandbox Label on a real order fulfills the real order at Shopify, and can
email the real customer a sandbox tracking number.

Other writes to a store that need the same guard:

- Voiding a Label on a Shopify order cancels the fulfillment PolyBag's export made
  (`ShopifyFulfillmentCanceller`). That mutation is a write. What follows it is not:
  `ShopifyFulfillmentOrderReplacer` reads the order from Shopify and moves the Shipment
  onto the replacement fulfillment order locally. It must keep running in Demo. A
  Shipment still naming the closed fulfillment order cannot be bought for again, so
  suppressing the read breaks re-shipping after a development-store test label is voided
  (`02`).
- `demo:reset`'s write-back step (`exportFabricatedPackages()`) goes through
  `PackageExportService`. Its fabricated Packages belong to the Database source, but in
  multi-client mode a live store connection with global export on would receive them.
- Amazon `confirmShipment` goes to the sandbox host in Demo today. Guard it anyway, so `03`
  cannot route it to production by accident.

## Desired behavior

- In Demo, an export to an Amazon connection, or to a Shopify connection whose store is
  not a development store, is not sent. The `package_exports` row is marked skipped, or
  succeeded with a "not sent in demo" note, so no retry picks it up and nothing shows as a
  failed export.
- In Demo, the Shopify fulfillment cancel mutation is not sent to a live store. The local
  void proceeds, and the replacement lookup (a read) runs as today.
- A development store gets both, as in production. A plan that cannot be read counts as
  live, so the write is skipped.
- A Database connection's export runs in Demo as before.
- A Shopify Shipping purchase is not this issue's to block. It is a write, but `02`
  decides it: allowed on a development store, refused on a live one.
- Enforce it in one place on the export path, not per connection. A per-connection
  setting is one someone forgets to set.

## Notes

- Grep for every Shopify mutation the app sends (`fulfillmentCreate`,
  `fulfillmentCancel`, the label purchase mutation, anything on a fulfillment order) and
  list which are covered here and which are `02`'s. Reads stay allowed.
- The Shipment stays `Open` locally in neither case: shipping it in PolyBag already moves
  it to shipped. Only the store is left alone.
