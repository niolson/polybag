# Use consistent residential classification for UPS and FedEx rating and purchase

Status: implemented
Category: bug
Repo: `polybag`

## Parent

[Rate accuracy background](../PRD.md).

## Problem and evidence

`RateRequest::fromPackage()` resolves residential status using
`validated_residential ?? residential`. UPS rating sends its presence indicator
only when that value is true. FedEx rating ignores the value entirely.

Neither UPS nor FedEx Label purchase sends a residential flag. `AddressData` does
not carry classification, and the purchase address builders therefore cannot use
it. Quotes and purchases describe different information about the same destination.
UPS rating also omits street lines; FedEx rating sends only postal/country codes.

New imported Shipments already inherit `residential = true` from the database
schema. Missing validation does not inherently mean commercial. The shared import
writer currently drops explicit residential input (tracked in issue 03).

UPS's official Rating schema defines indicator presence as true and absence as
false. Omitting it is not a documented request for automatic classification:
[UPS Rating specification](https://raw.githubusercontent.com/UPS-API/api-documentation/main/Rating.yaml).
Do not treat a sandbox surcharge as proof that carrier classification always repairs
an incomplete request.

## Proposed behavior

- Resolve classification server-side once and carry the same result through quote
  and purchase DTOs, using validated classification before imported classification.
- Send the appropriate UPS presence indicator and FedEx boolean on recipient
  addresses in both requests, preserving explicit commercial (`false`) values.
- Supply available destination address detail to rating where supported, using the
  same validated/original address selection as purchase.
- Keep unknown distinguishable from confirmed residential. Proposed fallback:
  assume residential for quoting and purchase when neither validation nor import
  supplies classification, to avoid optimistic commercial pricing. This is a
  proposed policy, not yet an approved schema migration or classification service.
- Preserve Offer validity: changing effective classification or relevant address
  inputs must invalidate a stale Offer before purchase.

## Decisions for triage

Confirm how unknown and classification provenance are represented, how existing
rows with the historical `true` default are treated, and whether the conservative
fallback is fixed or configurable. Do not relabel historical defaults as verified
residential. Additional carrier-specific classification API calls are outside this
issue unless explicitly approved during triage.

## Acceptance criteria and verification

Add request-body tests for validated true/false, imported true/false with no
validation result, and unknown fallback. Check that validation wins, explicit false
survives serialization, and UPS/FedEx rate and purchase payloads agree. Cover Offer
invalidation when effective classification changes and ensure classification comes
from server state rather than browser purchase inputs.

Start with `RateRequest`, `AddressData`, `ShipRequest`, both carrier adapters,
`RateRequestFingerprintTest`, `AddressDataTest`, and the adapter/workflow tests.
Use existing schema validation and run the affected suites. No paid purchase needed.

## Implementation notes

2026-09-20: Made imported residential classification nullable without a backfill,
preserving unknown separately from explicit commercial and residential values. Unknown
destinations conservatively resolve to residential in the server-side address DTO.
UPS and FedEx rate and purchase requests now send that resolved classification, and rate
requests include the validated/original destination street, city, state, postal code, and
country. Those address inputs and the effective classification participate in Offer
fingerprints, so changing either requires a fresh quote. Shipping-rule evaluation uses the
same conservative residential fallback, and FedEx applies the same 35-character street-line
normalization to rate and purchase requests. The rate service also reuses its destination DTO
instead of parsing the shipment address twice.
