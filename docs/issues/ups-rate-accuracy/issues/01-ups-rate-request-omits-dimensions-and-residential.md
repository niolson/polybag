# Send package dimensions in UPS and FedEx rate requests

Status: done
Category: bug
Repo: `polybag`

## Parent and scope

[Rate accuracy background](../PRD.md). This expands the original UPS dimensions
issue to FedEx. The existing filename is retained for incoming links; residential
handling now belongs to [issue 02](02-residential-classification-rate-purchase-consistency.md).

## Problem and evidence

Both `UpsAdapter::buildRateApiRequest()` and `FedexAdapter::buildRateApiRequest()`
send actual Package weight without dimensions. Both adapters send dimensions at
Label purchase. A light, bulky Package can therefore be quoted without the inputs
needed to calculate its dimensional weight, undermining price comparisons and
cheapest-service selection.

Confirmed by inspection of the request builders, including FedEx's additional
line-item fields, which do not supply dimensions. The original UPS probe reported
$16.96 quoted versus $39.13 purchased, but dimensions are only one potential
contributor; this issue must not claim to explain or eliminate the whole difference.
Sandbox prices alone are not proof of production pricing behavior.

## Acceptance criteria

- Send actual weight and length/width/height, with correct units, on eligible UPS
  and FedEx rate requests. Let the carrier calculate billable dimensional weight.
- Rating and purchase use consistent dimension normalization. Cover fractional
  measurements explicitly so integer conversion cannot silently understate size.
- Preserve carrier-supplied packaging semantics from ADR-0005, including UPS
  Letter's documented dimensions exemption; verify FedEx packaging exceptions.
- Cover all request paths sharing these builders, including applicable One Rate
  and SmartPost paths, without changing packaging eligibility or service selection.
- Handle unavailable or invalid dimensions deliberately and consistently with
  Package preparation validation; do not invent measurements.
