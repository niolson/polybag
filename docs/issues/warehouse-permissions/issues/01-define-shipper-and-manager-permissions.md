# Define shipper and manager permissions and role-appropriate dashboards

Status: needs-triage
Category: enhancement
Created: 2026-09-28

## Problem

PolyBag needs an explicit account of what warehouse workers, managers, and admins
may see and do. Navigation, dashboard widgets, and action authorization should follow
the same decisions. A shipper should not have to navigate business configuration or
management reports to complete routine work.

The product initially targets Shopify and Amazon sellers, with more marketplaces and
3PLs later. Permissions must reflect those different operating models rather than the
practices of one warehouse. In particular, exception handling, spending discretion,
and access to commercial information may vary between companies.

## Established direction

- Retain the existing `User`, `Manager`, and `Admin` roles initially. In this issue,
  **shipper** means the existing `User` role; a code or UI rename is not yet decided.
- Manual Ship should require Manager or Admin access. Prefer Label purchases in the
  context of an existing Shipment/order wherever possible.
- Carrier Accounts and Special Services should not be exposed to shippers. **Done**:
  both are Admin-only, consistent with Carrier and Carrier Service configuration —
  Carrier Accounts through `CarrierAccountPolicy` (#294), Special Services through
  `SpecialServicePolicy` (#296).
- Most current management-oriented dashboard widgets should be hidden from shippers.
  Candidate retained information includes unshipped Shipment counts and the signed-in
  account's Package counts for today and this week.
- Document the action matrix before expanding authorization implementation. Hiding a
  link or button is not sufficient: direct routes and Livewire actions must enforce it.
- Keep open a future move to configurable roles and granular permissions if customer
  needs justify it. The app already has fixed role-based authorization; the deferred
  option is a more flexible permission system, not the first introduction of roles.

## Proposed responsibility boundaries

| Role | Responsibility |
|---|---|
| Shipper (`User`) | Complete routine picking, packing, and shipping work |
| Manager | Allocate work, handle exceptions, correct mistakes, and supervise operations |
| Admin | Configure credentials, integrations, access, and system-wide rules |

The following matrix is a starting proposal, not an approved implementation spec.
Only Manual Ship's Manager-or-Admin restriction above is settled for these actions.

| Action | Proposed shipper access | Company-specific decision |
|---|---|---|
| View Shipments and Packages | Within assigned scope | Assigned work only or all work at a Location; Client boundaries for 3PLs |
| Pack items and record box, dimensions, and weight | Allow before Label purchase | Treatment of discrepancies and overrides |
| Change recipient address | Manager by default | Whether trained shippers may correct addresses; effect on source-system data |
| Change ordered items or quantities | Manager by default | Whether changes must originate in the external order system |
| Buy a Label for an existing Shipment | Allow within approved workflow | Whether packing and purchase belong to separate staff |
| Choose service or override selection | Limit to approved choices | Service allowance, spending limits, and explicit override authority |
| Reprint an existing Label | Allow | Duplicate-shipment prevention and reprint audit requirements |
| Void a Label | Manager by default | Whether shippers may void their own recent purchases; reason and time limits |
| Create pick batches | Undecided | Self-directed picking versus supervisor allocation |
| Print an existing pick batch | Allow within work scope | Whether batches belong to a person, team, or Location |
| Print pack slips | Allow | Whether documents expose prices or commercial information |
| Print invoices or other priced documents | Separate permission | Distinguish customer invoices, customs commercial invoices, and 3PL billing |
| Report missing, damaged, or short items | Allow reporting | Reporting a discrepancy is separate from changing the order or approving shipment |
| Split or partially fulfill an order | Undecided | Fulfillment rules, upstream system authority, and manager approval |
| Batch purchase and end-of-day manifests | Undecided | Supervisor responsibilities, unattended purchasing, and Location scope |
| View costs, reports, and other workers' activity | Manager by default | Whether shippers need cost comparisons or team-level visibility |
| Configure workstation printers and scales | Allow | Workstation-local preferences versus shared business configuration |

Do not collapse these into one "modify shipments" permission. Editing a Shipment's
order instructions is distinct from preparing its Package or Package Draft. Voiding
a Label retains Label history and returns the Package to unshipped; permissions must
follow that lifecycle rather than treating a void as deleting a Shipment.

## Dashboard proposal

- Show a small number of useful counts: unshipped Shipments, Packages shipped by this
  account today, and Packages shipped by this account this week.
- Decide whether the Shipment count means all unshipped work or only work ready to
  pack, and apply the user's Location and Client scope consistently.
- Consider a prominent Scan & Pack entry point, resumable Package Drafts, and compact
  printer/scale status. These are candidates, not committed requirements.
- Move cost charts, carrier breakdowns, tracking exceptions, and configuration
  problems to the appropriate manager/admin view.
- Define attribution before displaying personal counts: packer versus Label purchaser,
  completed Packages versus Label purchases, void/rebuy handling, and Location timezone.
  Shared logins must not be described as individual worker productivity.

## Decisions still needed

1. Approve a complete action-by-role matrix, distinguishing read, create, edit, purchase,
   void, print, and override capabilities. Audit the existing policies against it.
2. Decide which exceptions deserve company-wide shipper settings initially. Candidates
   are address correction, pick-batch creation, Label voids, partial fulfillment,
   priced documents, and service selection. Do not introduce all of them by default.
3. Define visibility scope independently of role: own work, assigned Location(s), and
   permitted Client(s). Manager status should not implicitly mean every 3PL Client.
4. Decide the correction workflow when a shipper lacks permission: manager takeover,
   an approval request, or another explicit path. Do not assume an approval system exists.
5. Define audit requirements for sensitive changes, including actor, reason, affected
   record, and before/after values where appropriate.
6. Set migration behavior for existing installations and determine whether any current
   workflows would become inaccessible under the defaults.

## Future flexibility

Custom roles, named capabilities, and individual or Client-specific exceptions remain
possible if fixed roles plus a few company settings prove insufficient. Triggers include
separate packing/purchasing teams, supervisors with different responsibilities, or 3PL
contracts requiring different access for different Clients.

Keep authorization decisions in Laravel policies and shared action boundaries so a future
permission resolver can replace role checks without rebuilding every page. Do not select
a permissions package, add a role editor, or design a full permission schema in this issue.
Document any future expansion and migration in a separate decision once requirements exist.
