# The client's EIN goes with every export ITN

Status: ready-for-agent
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md), *Carrier field mapping* (export ITN). Found by `02`. Needs `03`; `06`
and `07` need this before they send an ITN.

## Problem

When a parcel needs Electronic Export Information (EEI), the exporter files it in AES and
the label carries the ITN that comes back. Both express carriers want the exporter's EIN
alongside that ITN:

- **UPS** takes an ITN only on the EEI form (`FormType` `11`), which wants the shipper's
  tax ID (`ShipFrom.TaxIdentificationNumber` with `TaxIDType` `EIN`, deprecated in favor
  of `GlobalTaxInformation`).
- **FedEx**'s Ship API guide: *"As the shipper, your tax identification information must
  be uploaded to FedEx for EEI shipments. Specify the Employer Identification Number
  (EIN)."*

`03` stores the ITN on the Shipment, but nothing holds an EIN, so neither adapter can
send one.

**Whose EIN.** The USPPI, the US principal party in interest: for a 3PL, normally the
client that sold the goods, not the 3PL. 15 CFR 30.6(a)(1)(iii) requires the USPPI's own
EIN and says *"Use of another company's EIN is prohibited."* So it belongs to the
client, and a 3PL must not fall back to its own.

**When.** Only for parcels that carry an ITN. An exemption such as `NO EEI 30.37(a)`
needs no EIN, so most clients never fill this in.

## Desired behavior

**Data.** A nullable `exporter_ein` on `clients`: nine digits, stored without the
hyphen, shown as `XX-XXXXXXX`, edited in the client form's customs section next to
the tax registrations. It is not a `client_tax_registrations` row. Those are
destination regimes that an order's own registration can replace (ADR-0008 decision
4); an EIN is origin-side and never comes from an order.

**Readiness (`05`).** A Shipment with an ITN whose client has no EIN is blocked. The
finding names the client form as the fix. Same reach problem as `05`'s Manual Ship note:
a floor user cannot edit a client.

**Carriers.** Wherever an ITN is sent, the EIN goes with it:

- UPS: on the EEI form request, in `GlobalTaxInformation` if CIE accepts it there for
  the shipper, else `ShipFrom.TaxIdentificationNumber` + `TaxIDType` `EIN`. `06` builds
  the rest of the EEI form.
- FedEx: in `shipper.tins`. The `tinType` is in the FedEx email from `02` (`FEDERAL` or
  `BUSINESS_NATIONAL`). Send it after any seller registration, because FedEx prints only
  the first shipper TIN in the invoice's tax ID field.
- USPS: nothing. `AESITN` carries the ITN alone.

**Out of scope.** A foreign client with no EIN: there the US agent files with another
party ID (30.6 allows a CBP-assigned or passport number). The readiness finding should
say that such a client needs its filer to supply the ITN, not offer a field for it.
