# Import duties terms and recipient tax IDs from Shopify orders

Status: done — 2026-10-12
Category: enhancement
Repo: `polybag`

> *This was generated by AI during triage.*

## Parent

[PRD](../PRD.md). Needs `03`.

## Problem

A Shopify Markets store that charges duties at checkout must ship DDP or the customer
pays twice, and stores selling to Brazil may collect a CPF at checkout. Neither reaches
the Shipment today.

## Needs info

- Which Admin GraphQL order field reliably says duties were charged at checkout —
  `originalTotalDutiesSet` is the likely one — and is it set on orders where duties were
  included in the price rather than added?
- Where a CPF or PCCC collected at checkout lands on the order (a checkout field, a note
  attribute, the shipping address's company line), and whether it is consistent enough to
  import

Answer against a development store before writing code.

## Findings so far

Probed read-only on `polybag-test` (Shopify Plus development store, API 2026-07, scopes
include `read_orders`) on 2026-10-12. The store's 100 orders are all seeded and none
carries duties or a localized field, so the **field names and semantics below come from the
schema, not from a real checkout**.

- **Duties.** `Order.originalTotalDutiesSet` is "the total amount of duties calculated when
  an order was created, before any modifications" (`currentTotalDutiesSet` is after
  returns, refunds and edits, so it is the wrong one). `Order.dutiesIncluded` is a separate
  boolean: "whether duties are included in the subtotal price", i.e. the store's
  duties-included pricing. `LineItem.duties` lists per-line `Duty` records. So the likely
  rule is `originalTotalDutiesSet` greater than zero, and it still needs a real order to
  show what a duties-included order reports in it. All 100 seeded orders return null
  duties and `dutiesIncluded: false`.
- **Recipient tax ID.** It is not a note attribute or the address's company line. Shopify
  has `Order.localizedFields` (`key`, `countryCode`, `purpose`, `title`, `value`),
  "additional fields required by certain countries on international orders". Keys include
  `TAX_CREDENTIAL_BR` and `SHIPPING_CREDENTIAL_BR` (Brazil), `SHIPPING_CREDENTIAL_KR`
  (Korea), `TAX_CREDENTIAL_IT`, `_PT`, `_ES`, `_MX`, `_CO`, `_CL` and others. Whether a
  Brazil CPF lands in the tax or the shipping credential, and how a CPF is told from a CNPJ
  (length, or a `_TYPE_` key as Colombia and Mexico have), needs a real order. The seeded
  Italy orders have none.
- **Why no real order.** The Admin API cannot create one: `orderCreate` takes no duties and
  no localized fields. Only a checkout in a Market with duties collection on, and the
  Brazil/Korea fields enabled, produces them.

**First real EU order, 2026-10-12 (#1261, shipment 7193, DE).** Shopify charged VAT at
checkout: one tax line `DE MwSt` at 0.19, 6.80 on the order. But `originalTotalDutiesSet`,
`currentTotalDutiesSet` and `LineItem.duties` are all null, `dutiesIncluded` is false, and
`localizedFields` is empty. Orders #1259 and #1260 (also DE, before the VAT setting) have no
tax lines at all. So **destination VAT is not reported as duties**: it arrives in
`taxLines`/`totalTaxSet`, and `originalTotalDutiesSet` stays null for a German order. The
imported shipment has `duties_terms` null, as `ShopifySource` does today. This changes the
question: the signal that the customer already paid import VAT is a destination-country tax
line, not a duties amount. Whether to treat it as DDP (and whether this store is collecting
VAT as IOSS or as ordinary local tax, which the order does not say) is a decision, and
duties proper may only appear for non-EU markets or non-EU origin pricing. Not yet probed:
a UK or CH order, which are the markets where Shopify collects duties.

**Order with duties, 2026-10-12 (#1263, shipment 7198, IT).** This one carries them:
`originalTotalDutiesSet` is 3.00 EUR presentment (3.36 USD shop), equal to
`currentTotalDutiesSet`, and the one line item has a `Duty` of 3.36 USD with
`countryCodeOfOrigin` VN and `harmonizedSystemCode` 3304990000. So the EU €3 customs duty is
reported as a duty, separate from the 22% VAT (22.17, one tax line titled `TAX`, so the tax
line's title is not a reliable signal). `dutiesIncluded` is **false** even though duties
were charged: it describes duties-included pricing, so it must not be the test.
**Answer to question 1: `originalTotalDutiesSet` greater than zero**, confirmed on this
order; it is null (not zero) when none were charged. The imported shipment has
`duties_terms` null, so the import does not read it yet. The duty lines also carry origin
country and HS code per item, which `ShopifySource` could import for customs content.
**Brazil and Korea, 2026-10-12 (#1264 shipment 7199, #1265 shipment 7200).** Question 2 is
answered. Both orders carry duties in `originalTotalDutiesSet` (BR 6.18 USD; KR 37,323 KRW,
27.82 USD) and per-line `Duty` records with origin and HS code, so the rule holds for
non-EU destinations too. The tax IDs are in `localizedFields`:
- **BR:** `SHIPPING_CREDENTIAL_BR`, purpose `SHIPPING`, title `CPF/CNPJ`, value
  `007.408.869-67`: **with punctuation**, and the same key for a CPF and a CNPJ, so the
  type has to come from the digit count (11 or 14) after stripping. `TAX_CREDENTIAL_BR`
  was not populated here.
- **KR:** `SHIPPING_CREDENTIAL_KR`, title `Personal Customs Code`, value `P123456789012`
  (the `P` plus 12 digits form). This is the PCCC, which FedEx's advisory says the foreign
  shipper need not supply; it is imported only because the buyer already gave it.
- Neither order has a note, custom attribute or company line holding the ID.
Still unanswered: an order where duties were included in the price, and a CNPJ order.

## Desired behavior (once answered)

`ShopifySource` sets `duties_terms: ddp` when the order carries duties, and leaves it null
otherwise — never `ddu`, since "no duties on the order" is not a decision to ship DDU. It
fills `recipient_tax_id_type` and `recipient_tax_id` where the store collects them.
Amazon is out of scope here: Amazon orders bought on Amazon postage are `09`'s concern.

## Acceptance criteria

- [x] An order with duties imports as `ddp`; one without imports null
- [x] A collected CPF imports with its type, and an invalid one is reported, not stored

## Comments

- **2026-10-12, built.** `ShopifySource` now asks for `originalTotalDutiesSet` and
  `localizedFields` on the order and sets `duties_terms: ddp` when the duties are above zero.
  With no duties it leaves the key out rather than sending null, so a term a manager set
  (say `ddu`) survives the next import; the cost is that a `ddp` stays if Shopify later
  removes the duties. `SHIPPING_CREDENTIAL_KR` imports as a PCCC and
  `SHIPPING_CREDENTIAL_BR` (or `TAX_CREDENTIAL_BR`) as a CPF, or a CNPJ at 14 characters;
  `ShipmentRowPreparer` does the format check, so a bad ID imports the order with a warning
  and no ID. Tests in `ShopifyCustomsFieldsImportTest`. Not run against the dev store: a
  sync would update shipments 7198-7200 in the local database. `read_orders`, already
  required by the install guide, covers the new fields. Left for a human: sync once and
  check 7198-7200 show `ddp` and the BR and KR IDs; a CNPJ order and a duties-included
  order are still untested against Shopify.
- **2026-10-12, verified.** After a sync on the dev store, shipment 7198 (IT) shows `ddp`
  with no tax ID, 7199 (BR) shows `ddp` and a CPF (11 digits), and 7200 (KR) shows `ddp` and a
  PCCC. Untested against Shopify: a CNPJ order and an order with duties included in the price.
