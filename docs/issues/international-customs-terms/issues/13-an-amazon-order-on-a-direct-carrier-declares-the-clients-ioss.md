## Problem

ADR-0008 decision 3 rejects combining registrations. When a marketplace is the deemed
supplier, it "collected the VAT under its own number, and the client's number would declare
the wrong seller". The ADR's consequences also say every importer writes the order-level
columns.

`ShopifySource` and the Database driver write those columns.
`app/Services/ShipmentImport/Sources/AmazonSource.php` writes none of them: no
`duties_terms`, no `seller_tax_regime`, no `seller_tax_number`.
`international-customs-terms/10` scoped Amazon out, on the grounds that Amazon orders are
bought on Amazon postage (`09`). But direct carriers also quote Amazon orders.

For such an order, `CustomsTermsResolver::registration()`
(`app/Services/Customs/CustomsTermsResolver.php:244`) finds no order registration and falls
back to the client's. A direct label then declares the client's IOSS number on a sale where
Amazon, as deemed supplier, collected the VAT.

## Scenario

1. A client has an IOSS registration and `EU → ddp`.
2. An Amazon order to Germany under €150 is imported by `AmazonSource`.
3. The packer picks a UPS rate on the Ship page, or batch ship rate-shops to one.

`ResolvedCustomsTerms::$registration` is then the client's IOSS, with origin `client`.
`UpsAdapter` sends it in `ShipFrom.VendorInfo` (`0356`), and the Label snapshot records it.
Nothing on the path knows the order is a marketplace sale.

## What to build

This needs a product decision first. Either:

- `AmazonSource` writes the marketplace's registration as the order's, if the Orders API
  exposes it, or
- a Shipment from an Amazon connection suppresses the client's registration, and the
  readiness check warns that Amazon collected the VAT.

For the regression test: an Amazon-sourced Shipment to DE, with a client IOSS, resolves no
client registration.
