# Say when a scan claimed by the prefix is an existing identifier

Status: wontfix
Category: enhancement
Created: 2026-09-29

## Problem

ADR-0007 decision 2: a scan that begins with the install's `SCAN_CODE_PREFIX` (default
`PB`) is always read as a PolyBag code and never looked up as an order reference, box
alias, SKU or barcode. If the code does not resolve, Scan & Pack says "Unrecognized Code"
or "Not Found". When the text is really a SKU such as `PBJ100`, that message is misleading.
The packer cannot tell that the prefix is the problem, and nothing tells the admin to
change it, which is the remedy `01` was closed in favor of.

Collisions arrive with imported data, usually long after the prefix was chosen, so the
moment to catch one is the first time someone scans it and it fails.

## Work

When `Pack::openScanCode()` is about to report an unrecognized code, or a Shipment,
Package or Box Size code that names no record, look the trimmed scan up as an external
identifier first, case-insensitively:

- order references (`shipments.shipment_reference`)
- product SKUs and barcodes, scoped to the loaded Shipment's client while packing
- box aliases (`box_sizes.code`), for aliases created before the prefix changed

If any match, replace the error with one that says what the text is and why it was not
used. For example: "PBJ100 is a product SKU, but scans beginning with PB are read as
PolyBag barcodes. An admin can change the barcode prefix (Self-hosting → Barcode prefix)."
Name the kind of identifier only, never the matching record, so the message reveals
nothing the scan would not have opened anyway. If nothing matches, keep the current
errors as they are.

This adds lookups only to scans that are already failing. It does not cover a SKU shaped
exactly like a live code (`PBS100` while Shipment 100 exists): that resolves to the
record, by design.

Global search is out of scope. Its "nothing" result for a claimed code already sends
people to the list pages' searches, which are not intercepted.

## Acceptance

- [ ] An unrecognized `PB…` scan matching a SKU, barcode, order reference or box alias
      gets the explanatory message naming the kind and the prefix, both with nothing
      loaded and while packing.
- [ ] A well-formed code naming no record (`PBS999999`) that matches an identifier gets
      the same message.
- [ ] No match: the existing "Unrecognized Code" / "Not Found" errors are unchanged.
- [ ] Matching is case-insensitive and honors a non-default prefix.
- [ ] While packing, product matching is limited to the Shipment's client.
- [ ] `docs/self-hosting.md` ("Choosing one") and ADR-0007 decisions 2 and 6 describe this
      message instead of a check command.

## Comments

### 2026-10-06 — rewritten

This issue first proposed `php artisan scan-codes:check {prefix?}`, to be run by the
on-prem installer before it writes `.env`. That command would have done nothing useful.
The installer writes `.env` before the database exists, and a fresh install has no
shipments, products or custom boxes, so the check always passes at the one moment the
prefix is chosen. Collisions come in later with imports, when nobody thinks to run a
command. New box aliases are already rejected by `02`, and searching the list pages
covers the rare case of checking before a prefix change. Rewritten to report the
collision when a scan fails because of it.

### 2026-10-06 — wontfix

Superseded the same day. ADR-0007 now uses the fixed prefix `%`, which order references,
SKUs, UPCs and box aliases practically never begin with, so the collisions this message
would explain no longer arise. Nothing was built.
